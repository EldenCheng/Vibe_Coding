# 版本变更

## v0.10.0（2026-10-01）

> 主题：**下载前自动判定"这集要不要重下"** —— 不加任何命令行参数。
> 起因：用户问"我想重新下载第1集，我要怎么做？理论上我用 batch，下载器会直接跳过第1集不下载的哦"。

### 需求（用户原话）

> "下载前，读取到 m3u 之后，好像是能读取到未下载的视频的长度、分辨率这些数据的吧，
> 如果能读取，那就这样：首先判断已下载好的视频的线路信息，如果线路信息不一样的，重下；
> 如果线路信息一样，分辨率与时长不一样，重下；如果都一样，就跳过，这样可以实现吗？"
>
> "不想加参数啊"

### 已确认的决策（2026-10-01）

| 议题 | 决策 |
| --- | --- |
| 实现形态 | **不加参数**，判定内建在 batch 的重跑流程里 |
| 判定数据来源 | **只用清单声明值**（用户选 B：零额外流量；更准的"抓首个切片读真实分辨率"约 2MB/集，本次不采用） |
| 旧成品 | 重下时**改名 `<名>.bak` 保留**（不删除） |
| 第13集 | 保留新下的（960×720/1501.8s），旧 IDM 那份 `.bak` 删除 |

### 实测依据：清单声明值**不可信**（所以必须带"保险丝"）

临时探针（`parser` + 首个切片 + ffprobe）在 ikanbot/牙狼garo 上实测：

| 集 | 清单声明 | 首个切片**真实**分辨率 |
| --- | --- | --- |
| 第01集（线路5/13） | `1080x608` | **2880×2160**（线路6 同样声明 1080x608，真实只有 640×480） |
| 第13集（线路5/13） | `1080x608` | **960×720**（13 条线路里该集最好的版本） |
| 第18/24集（线路5） | `1080x608` | **2880×2160** |

- 声明**两头都会错**：偏低（第01集）与偏高（线路6）都实测到了；`BANDWIDTH` 同样不可信
  （全声明 800 kbps，实际约 2.3~2.4 Mbps）。
- `EXTINF` 求和的时间也对不上：声明 1475 秒 / 自家成品 1503 秒 / 用户 IDM 那批 1456 秒。
- 所以若把"声明值 vs 实际值"直接相比：21 个 4K 成品（声明 0.66 Mpx < 实际 6.2 Mpx）会被判
  "分辨率不同" → **每次运行都重下、甚至死循环**；25 集又会因"时长不同"被整体重下（约 10GB）。

### 新增 / 变更

- **`parser.py`**：`#EXTINF` 时长不再丢弃 → `Segment.duration` / `Playlist.declared_duration`（求和）；
  `load_playlist()` 跟进 master 变体时把**选中变体声明的分辨率**带回到 media 清单
  （`variant_resolution` / `variant_bandwidth`），新增 `quiet=True`（判定时不打 `[清单] …` 噪音日志）。
- **新模块 `m3u_down/precheck.py`**：
  - `probe(session, url)` → `{resolution, duration_sec, segments}`，失败返回 `{}`（**绝不抛**）；
  - `pixels("1080x608")` → `656640`；`same_declared()` 判"是否同一份源"；
  - `decide(record, probed, line_name)` → `(action, reason)`，`action ∈ {skip, redo}`，`reason` 是中文说明。
- **`batch.py`**：
  - 已完成的集先过 `_judge_redo()`（只对 m3u8 直链的内嵌站点集，嗅探型列表页保持旧行为）；
  - 命中重下时 `_backup_existing()` 把旧成品改名 `.bak`（已有 `.bak` 则 `.bak2`…）；
    **同名改名失败 → 放弃本次重下**（否则会覆盖唯一一份），异名失败只告警继续；
  - 下载成功后把**清单声明值**一并写进 `批量进度.json`（`declared_resolution` / `declared_duration`）；
  - 汇总多一行"其中重新下载 N 集（判定为清单有更高清版本 / 线路变化 / 疑似缺内容）"。
- `_download_episode()` 改为返回 `(成品路径, 清单声明值)`：下载本来已经拉了清单，记录零成本。

### 判定规则（对"进度 done 且文件存在"的集，按序命中即定）

| # | 条件 | 动作 |
| --- | --- | --- |
| 1 | 清单读不到（网络/结构变化/无变体/无切片） | **跳过**（绝不因探测失败去重下） |
| 2 | 记录里的 `declared_*` 与本次声明一致 | **跳过**（同一份源 → 杜绝死循环） |
| 3 | 记录 `line` 非空且 ≠ 本次线路名 | **重下** |
| 4 | 声明像素数 ≥ 现有像素数 × 1.2 | **重下**（清单有更高清版本） |
| 5 | 声明像素数 ≤ 现有像素数 × 0.8 | **跳过**（**不降级**） |
| 6 | 声明时长 − 现有时长 > max(60 秒, 现有 × 5%) | **重下**（现有疑似缺内容） |
| 7 | 其余 | **跳过** |

### 边界

- 只影响 `batch` 的内嵌直链站点；yt-dlp 批量路径、`get/sniff/play` 与 `--no-adopt` 均不受影响。
- 这是"声明值"对比，不是"真实值"对比：声明偏低时可能**漏判**升级机会（不误判成重下）。
- 时长是**粗检**（容差 `max(60 秒, 5%)`），抓"大块缺失"，抓不到几秒级差异。
- 每次探测**新建 session**：实测一个 session 连续访问多条线路时，前几条死链会让会话降级到
  代理（`127.0.0.1:10808` 未开）而让后续请求**全部**失败 —— `_probe_alive()` 早有同样的做法。

### 实测（牙狼garo，2026-10-01）

- 单元自测 22 项全过（`pixels` 7 例、`declared_duration` 与 `Segment.duration`、`decide` 12 种输入：
  升级/降级/同档/线路变化/声明记忆/时长粗检/记录缺字段/清单无声明值/探测失败）。
- **真机第一轮**（全部 25 集、`--line 5`）：**只有第01集重下**（640×480 → **2880×2160**，
  136.9 MB → 425.0 MB，1502.8 秒），其余 24 集跳过 —— 21 集"清单声明低于现有，不降级"、
  第13集"清单声明与现有成品相当"。汇总 `完成 1 / 失败 0 / 跳过 24`，
  `其中重新下载 1 集: 第01集`；旧成品改名为 `牙狼garo-01-….mp4.bak2`
  （`.bak` 这个名字当时被我手工复制的同内容备份占着，事后删了那份，改名成 `.bak` 时又被
  那个占用进程拦了一次，就保留 `.bak2` 这个名字）。
- **真机第二轮（幂等）**：同一命令再跑 → **0 下载**，第01集走"清单声明与上次一致（同一份源）"
  —— 证明**声明记忆确实切断了"声明 1080x608 vs 实际 4K"这种死循环**。
- **开销实测**：25 集全跳过的这一轮（含解析、纳管扫描、25 次清单探测）约 **114 秒**（≈4 秒/集，
  每集 2 个清单请求，站点 CDN 单请求 1~2 秒）；**零额外流量**（不抓切片）。
- 设计见《Design/项目设计文档.md》§24。

## v0.9.0（2026-10-01）

> 主题：把已下载视频的**线路 / 分辨率 / 时长**记进批量进度与 简介.md 表格（用户提出"看回不用猜"）。

### 需求（用户原话）

> "下载完，在标记批量与在简介中修改已下载时，顺便把下载好的视频的线路（如果有）、
> 分辨率、长度这些简短信息也放到表里去，到时我可以重新看回，不用猜。"

### 新增

- **新模块 `m3u_down/mediainfo.py`**：
  - `probe(path)` → `{resolution, duration_sec}`：用 **ffprobe 读成品文件本身**
    （不是清单里声明的 `RESOLUTION` —— 声明与实际编码未必一致，且外部纳管的文件根本没有清单可读）；
  - `format_duration(sec)` → `25:06` / `1:25:06`（>1 小时）；
  - `fill_progress()` → 给"已完成但缺信息"的记录补录，**只探测缺的**，
    结果写回 `批量进度.json`，第一次补齐、之后 0 成本（实测每个文件 0.3~3 秒）。
- **`简介.md` 剧集清单表新增三列**：`下载线路` / `分辨率` / `时长`，未知一律填 `—`。
  列名用"下载线路"以区别于「链接」列里的线路号：**链接**列是本次解析出的线路（可能因探活/换线而不同），
  **下载线路**列是这个文件**实际来自哪条线**（历史事实）。
- **`批量进度.json` 每条记录新增可选字段**：`line`（仅下载器自己下的那集有）、
  `resolution`、`duration_sec`（存秒数，渲染时格式化，便于机器读）。
- 本集下载完成时立即记录（与 `mark(done)` 同一次写入）；已存在的旧文件由
  `fill_progress()` 在首次刷新简介前一次性补录（含外部纳管的文件）。

### 修复（实测中现形的一个 bug，v0.9.0 同版修掉）

- **`_BatchProgress.mark()` 未接收新增关键字参数**：第一次真机跑"换线路重下第24/25集"时，
  两集**其实已下载成功**（日志有"成品完整性通过"、文件也确实落到盘上，2880×2160），
  但紧接着写进度时抛 `mark() got an unexpected keyword argument 'line'`，
  被 `except` 吞掉后把两集标成了**失败**（任务显示"部分失败 25/27"）。
  已修：`mark(ep, status, file="", **extra)`。**教训**：单元测试只覆盖了 `mark_url()`，
  没覆盖 `mark()` 的新签名 —— 是新写的调用点先于测试被真机执行才暴露出来。
- 顺带把 `mark_url()` 改成**在已有记录上合并**而不是整条替换：
  这样"先失败、后被纳管补记为完成"时不会把已记下的 `line`/`resolution`/`duration_sec` 抹掉。
- 收尾补一次按文件名去重（下载循环之后）：换线路重下会让同一成品文件同时挂在旧线路 URL
  与当前线路 URL 下，只留一条，免得"完成 X/X 集"虚高。

### 实测（牙狼garo，2026-10-01）

- `fill_progress()` 首轮补录 23 个既有文件（17 个 IDM 命名 + 6 个自家命名）→ `已补录 23/23`；
  第二次运行不再探测（日志里没有"[媒体信息] 读取 N 个…"）。
- 换线路重下第24、25集（`--line 5`）：两集从 640×480/135-170 MB 变成 **2880×2160/440-448 MB**，
  时长 25:04/25:03，记录里 `line="线路5 (dyttm3u8)"`。
- **表格立刻发挥作用的证据**：补录后一眼看出用户手上 25 集里
  **第01集 = 640×480（130.5 MB）、第13集 = 960×720（223.8 MB）**，其余 23 集都是 2880×2160
  —— 这两集正是 IDM 那批里体积明显偏小的（此前只能靠猜体积）。
- 补记任务的最终状态：`completed` / 25/25 集完成，0 下载（纳管 2、清理 2 条换线路重复记录）。
- 设计见《Design/项目设计文档.md》§23。

## v0.8.0（2026-10-01）

> 主题：外部已下载文件纳入批量进度（用户 IDM 存量 + 本下载器混装场景驱动）。

### 需求（用户原话）

> "我之前已经使用 IDM 下载了一部分的视频，放在 `m3u-get-down\Download\牙狼garo` 里，
> 现在使用了我们自己的下载器继续下载了一部分，这两部分名称不一样，我看批量进度方面好像
> 也只标记了我们自己下载器下载的那一部分为完成……看看能不能把我复制进去的、与真正使用
> 下载器下载的集数，能更新到批量进度中，这样我再使用下载器下载时，就不用重复下载了。"

### 新增

- **新模块 `m3u_down/external.py`**：扫番剧目录顶层的 `*.mp4` → 从文件名猜"第几集" →
  与本次解析出的剧集清单**唯一**匹配 → 写入 `批量进度.json`（`status=done`、`file=外部文件名`）。
- **CLI 新增 `--no-adopt`**：关闭该扫描（**默认开启**，用户 2026-10-01 决定）。
- 简介.md 状态列沿用 **"完成"**（不引入 `完成(外部)`），与下载器产物一致。
- 扫描/匹配全过程打印明细（哪些文件算第几集、哪些跳过及原因、哪些在子目录里没扫），
  便于人工核对。

### 集号识别（宁可漏，不可错）

有序规则：`第N集/話/回` → `S01E05` → `2x01` → `E05/EP05` → `[05]` →
"两边被分隔符包夹的数字"（**唯一**时才采信）→ 结尾裸数字。识别前剥掉画质/编码/来源/字幕噪声
（`1080p`、`x264`、`WEB-DL`、`CHS`…），并排除分辨率与年份。
`牙狼garo-08-…ikanbot.com_2.mp4` 取 **8** 而不是结尾的 `_2`；
`魔法师.2024.1080p.WEB-DL.mp4`、`HD.mp4`、`魔法师 第一季.mp4` 一律**猜不出**（不纳管）。

### 变更

- **跳过判断放宽**：由"期望文件名 `第NN集.mp4` 存在"改为"进度里记录的文件存在 **或**
  期望文件名存在" —— 外部命名的文件才能被正确跳过；反过来**删掉那个文件即会重新下载**
  （手动补下的方式，已写进使用指南）。`batch` 与 yt-dlp 批量路径共用 `episode_done()`。
- **进度按成品文件名去重**：站点换线路会让同一集的 m3u8 URL 变化，同一集被记在多条 URL 下会让
  "完成 X/X 集"虚高。纳管后按**同一文件名**只保留一条（优先保留出现在当前剧集清单里的那条，
  即当前线路的 URL）；判据严格到文件名，不会误删别的集。

### 实测（真实目录，2026-10-01）

`Download/牙狼garo`：顶层 23 个 mp4（17 个 IDM 命名 + 6 个自家命名），
`批量进度.json` 原本只有自家 6 集。

- 干跑：23 个文件 → 第01~23集**一一对应**，0 歧义、0 未识别。
- 实跑 `batch <url> --yes --episodes 1-23`：
  `[纳管] 23 个并入批量进度` + `清理了 6 条重复记录`，
  随后 `完成 0 / 失败 0 / 跳过 23` —— **一次下载都没发生**，
  进度文件变成 23 条全 `done`（1-17 指向 IDM 文件名、18-23 指向自家文件名），
  简介.md 表格 23 个"完成" + 2 个"未选择"，无 `.part` 残留。
- 顺带发现：该清单**其实有 25 集**（第24、25集用户还没下）——纳管不会掩盖缺口，
  简介表如实显示 2 集未选择。
- 另一个实测发现：进度里原本的 URL 是**线路5** 的，而本次解析默认**线路1**，
  两者完全不同 —— 证明"按 URL 对账"对不上，只有按集号匹配才行（这也是去重逻辑的由来）。
- **线路决定清晰度**（同一次实测的副产品）：管理器真机跑完 25 集后对比发现，
  线路1 下出来的第24、25集是 **640×480 / 约 0.6-0.8 Mbps / 135-170 MB**，
  而当初线路5 下的第18-23集是 **2880×2160 / 约 2.3 Mbps / 410-436 MB** ——
  时长与视频包数几乎一致（35613/35570 vs 35518），即**都是完整的，只是源不同**。
  已写进《使用指南.md》§3.4（想换清晰度：删掉那一集的文件再用 `--line N` 重下）。

### 边界

- 只影响 `batch`（含 yt-dlp 批量路径复用）；`get`/`sniff`/`play` 无进度表，不涉及。
- 只扫顶层 `*.mp4`；`.part`/`.ts`(含 `_work/`)/`.mkv` 不管，子目录里的视频只在日志里提示"未扫描"。
- 0 字节文件不当成品；猜不出集号/有歧义/清单里没有的，一律**只报告、不写进度**。
- **不用体积判断"是否下完"**：实测那批里 130 MB 与 223 MB 的两个文件，可读视频包数
  （35612/35516）与 430 MB 的正常文件（35518）几乎一致、容器时长同样 24.3 分钟 ——
  它们是完整的低码率版本，按体积过滤会白白重下 800 MB。
- `--no-adopt` 或无相关文件时，行为与 v0.7.4 完全一致（零回归面）。
- 设计见《Design/项目设计文档.md》§22。

## v0.7.4（2026-10-01）

> 主题：封面图防盗链的 Referer 逐档回退 —— 管理器 + 油猴脚本真站实测驱动。

### 修复

- **封面下载在"只认自家域名 Referer"的图床上一律失败**。v0.7.3 只带页面 Referer 请求一次，
  实测 ikanbot（封面托管在豆瓣图床）直接 403：

  ```
  [封面] 下载失败，已跳过（不影响剧集下载）: 403 Client Error: Forbidden for url:
        https://img3.doubanio.com/view/movie_poster_cover/lpst/public/p2308783641.jpg
  ```

  逐档实测（同一 URL 只改 Referer）：页面 Referer → **403**；不带 Referer → **418**（反爬）；
  图片自身完整 URL → **418**；图片站根地址 `https://img3.doubanio.com/` → **200**；
  `https://movie.douban.com/` → **200**。
  —— 存在"**只接受自家域名 Referer**"的一类图床，且 Referer 必须是**根地址**而非图片完整 URL。

### 变更

- **`cover.py` 新增 `_referer_plans()` 三档回退**：页面 Referer → 图片站自身 Referer
  （`scheme://host/`）→ 不带 Referer。成功时日志会注明用了哪一档：
  `[封面] 已保存本地: image/cover.jpg（改用图片站自身 Referer）`。
- **重试策略细化**：同一档内只对网络层/5xx 退避重试；**4xx（防盗链）立刻换下一档**，
  不浪费退避时间；响应不是图片（图床失效常见的 200+HTML）同样换档；
  **连接层彻底不通则不再换档**（换 Referer 救不了，避免 3 档×3 次超时白等）。

### 验证

- 本地 `http.server` 回归：第一档成功=1 次请求；第二档成功=2 次请求且第二次 Referer
  为图片站根地址；假图=三档各 1 次（共 3 次，无退避浪费）；幂等命中 0 请求；连不上不逐档重试；
  均无 `.part` 残留。
- 真站（豆瓣图床，同一 URL）：修复后一次命中，55049 字节。
- 同时完成一次**跨项目真站联调**：管理器（v0.3.0 运行时）+ 新油猴脚本提交
  `ikanbot play/432956` 批量第2-3集 → 任务正常解析 9 条线路、第02集下载完成

## v0.7.3（2026-10-01）

> 主题：封面图本地化（番剧目录下 `image/` + 简介相对引用）——用户提出，防图床先于视频失效。

### 新增

- **封面图落盘**：批量流程抓到的封面（站点 `detail.cover` 规则或通用 `og:image`；
  yt-dlp 路径为 `thumbnail`）会下载到 **番剧目录/`image`/`cover.<ext>`**，
  `简介.md` 改用相对路径引用（`![封面](image/cover.jpg)`）。
  背景：封面是**远程链接**，站点清理图床后会**先于视频**失效，简介页只剩裂图。
- **新模块 `m3u_down/cover.py`**：`existing()` / `fetch()` / `prepare()` 三个函数，
  `prepare()` 是幂等入口（已存在即复用、**不发任何请求**），
  在 batch 与 yt-dlp 批量两条路径的「选定集数后、首次刷新简介前」各调用一次。

### 实现要点

- **扩展名按 `Content-Type` 判定**（`image/png` → `cover.png`），URL 后缀兜底，再兜底 `.jpg`；
  基名固定 ASCII `cover`（Markdown 相对链接无中文编码坑）。
- **必须校验 `Content-Type` 以 `image/` 开头**：图床失效/防盗链常见「HTTP 200 + HTML 错误页」，
  只看状态码会把网页存成 `.jpg`。
- **原子落盘**：先写 `cover.<ext>.part` 再 `os.replace()` 改名 —— 中途 Ctrl+C 不留半截文件
  （否则下次运行会把 0 字节文件误判为"已完成"）；失败路径顺手清掉 `.part`。
- **URL 容错**：协议相对（`//img/…`）补 `https:`、站点相对（`/img/…`）按列表页 `urljoin` 补全。
- **重试**：最多 `min(config.retry_times, 3)` 次、间隔 `config.retry_backoff` 秒；
  最终失败**只打印一行警告，不抛异常**（封面是附加资料，不能中断整季下载）。
- **会话一致**：走 `build_session(referer=页面URL, insecure, proxy, direct_first=站点出口偏好)`，
  与页面抓取/下载同出口、同请求头（防盗链大多只看 Referer）。

### 已确认的决策（用户 2026-10-01 答复）

1. 只本地化**当前那**一张封面，不新增"页面上所有剧照"的多图提取规则；
2. 文件名用 ASCII 的 `image/cover.<ext>`；
3. 下载失败时**不显示图片**，只在简介留一行文字提示（不保留远程链接，宁缺毋滥不显示裂图）；
4. **不回填**已有番剧目录：只改代码，新下载生效；旧目录重跑同一 batch 命令时自动补上。

### 简介.md 渲染（`batch._write_info()`）

- `meta["cover_local"]` 为路径 → `![封面](image/cover.jpg)`；
  为 `""`（尝试过但失败）→ 一行引用块提示「封面图未能保存到本地，此处不再显示（原图链接可能已失效）。」；
  键不存在（旧调用方）→ 原行为（远程链接），**零回归**。
- `cover_local` 从「视频信息」附加键列表排除，不会当标签渲染成一行。

### 验证（本地 `http.server`，不依赖真实站点）

真图 → `cover.png` 落盘、内容字节一致、简介渲染相对路径、**二次运行请求数为 0**（幂等）；
无扩展名 URL → 按 Content-Type 修正为 `.png`；假图（200 + `text/html`）/ 0 字节图 / 坏域名 →
均返回 None、无 `.part` 残留、简介留文字提示且流程继续；
已有 `image/cover.jpg` 的目录重跑 → 未覆盖（直接复用）。
另用真实公网图片（`python.org` 的 logo）跑通一次真实下载链路（15770 字节 PNG）。
设计见《Design/项目设计文档.md》§21，用法见《使用指南.md》§2 目录结构 + §3.4 可靠性机制。

## v0.7.1（2026-09-26）

> 主题：cookie 读取失败的容错修复（实测发现）+ JS 运行时预置 + 小红书/YouTube 文档。

### 修复

- **cookie 读取失败时“自动降级”失效（bug）**：v0.7.0 的
  `_is_cookie_error()` 只认 `Could not copy Chrome cookie database`，
  而新版 Edge/Chrome 报的是 `Failed to decrypt with DPAPI`（整句里没有“cookie”），
  导致降级逻辑根本不触发 —— **只要 `cookies_from_browser` 非空，任何 yt-dlp 下载都直接失败**。
  现已放宽判定（`dpapi` / `app-bound` / `decrypt` / `cookies database` 等特征）。
- **`cookies_file` 路径坏掉也不再直接崩**：yt-dlp 打不开 cookies.txt 时抛的是
  `[Errno 2] No such file or directory: '<路径>'`（丢了 cookie 语境），
  新增 `_cookie_failure()` 用路径特征补判；降级时同时去掉
  `cookiesfrombrowser` 与 `cookiefile`。
- **日志不再“先喊两声错误再下载成功”**：`_Logger.error` 不直接打印 cookie 类报错，
  改由降级逻辑给一次性中文提示；真正不可恢复时异常会传到 CLI 顶层打印 `[失败]`。

### 新增 / 变更

- **默认预置 JS 运行时**：`ytdlp_sites.json` 的 `extra_opts` 默认变为
  `{"js_runtimes": {"deno": {}, "node": {}}}`（deno 优先，没装则用 node）——
  YouTube 必需，以前默认只启用了 deno（本机没装 → 报
  `No supported JavaScript runtime could be found`）。实测指定未安装的运行时只告警不报错。
  注：已存在的 `ytdlp_sites.json` 会覆盖默认值，因此本次已同步更新本机该文件。
- **默认预置 EJS 挑战脚本**（`remote_components: ["ejs:github"]`）：实测发现即使有 cookie + JS
  运行时，YouTube 仍会因 `n challenge solving failed`（默认不允许联网拉 EJS 求解脚本）
  而报 `The page needs to be reloaded.`；开启后首次自动拉取并缓存到
  `~/.cache/yt-dlp/challenge-solver`，解析/下载均成功。
- **本机配置改用 Firefox 读 cookie**：实测 **Firefox cookie 可读**
  （`Extracted 60 cookies from firefox`，能认出账号）——而 Edge/Chrome 因 App-Bound
  加密必败。已将本机 `cookies_from_browser` 设为 `firefox`。
- 降级提示文案升级：说明 App-Bound（v20）这个已知原因、附 yt-dlp issue **#10927**，
  并给出两条可行路径（扩展导出 cookies.txt / 改用 Firefox）。

- 《Design/项目设计文档.md》§19（本次设计 + 根因证据链 + 实测结论）；设计文档 §18 头部引用同步。

    把"当前窗口长度"当全集，捕获满一个窗口（3 个）就提前退出。
  - 修复：`resolve_playlist` 改为取最新清单（`>=`）+ 累计期望集合 `all_expected`；
    切片改用 `seg.seq`（真实媒体序列号）去重/命名/补拉；结束判定分两类——
    VOD（清单带 ENDLIST）捕获完即停；滑动窗口（无 ENDLIST）等浏览器播放结束
    （`video.ended`，附 3 秒宽限抓最后窗口），否则靠超时/手动结束。
  - 本地验证：滑动窗口模拟服务器（3 切片窗口实时前移）捕获 15+ 切片连续不丢；
    VOD 回归（ENDLIST）捕获完 3 切片立即停止。
- **新增"不推荐站点"机制**：`sites/*.json` 可配置 `unsupported: true` +
  `unsupported_reason`；任何命令（sniff/get/play/batch）命中该域名时打印原因并
  退出（退出码 3），不执行下载。用于记录"研究过但无法/不值得支持"的站点。
- **新增 `sites/javdock.json`**：javdock.com 研究结论存档（详见文件 `_说明`）——
  单视频页站点；三道防护（Cloudflare Turnstile 有头可过、data-ts-live AES 密文需
  浏览器解密、滑动窗口 HLS 只暴露最近约 6 秒切片且过窗即删）；免费流仅 240p。
  结论：不推荐用本下载器下载，标记 unsupported=true。

  **直接手动用 `py -m m3u_down ...` 调用时，请改用 `py -3.14 -m m3u_down ...`**（或其它 GIL 构建），
