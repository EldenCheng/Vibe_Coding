# m3u-get-down 项目设计文档

> 版本：v0.1.0（初始设计）
> 日期：2026-09-24
> 本文档是项目的唯一设计权威来源，设计变更时须先更新本文档。

## 1. 项目背景与目标

用户常在动画聚合网站看片，稀有资源随时可能失效，希望把正在播放的视频保存到本地。

技术路径：网页视频多为 HLS（m3u8）分发——服务器把视频切成小切片（.ts/.m4s），
播放器按清单顺序拉取拼接播放。本工具即围绕 m3u8 做"嗅探 → 下载 → 合并"。

## 2. 需求对照

| # | 需求 | 对应设计 |
|---|------|----------|
| 1 | 从播放页嗅探 m3u8 | `sniffer.py`（Playwright 有头浏览器网络监听） |
| 2 | 流式下载切片 + ffmpeg 自动合并 | `downloader.py` + `merger.py`（断点续传，长中断可恢复） |
| 3 | 直接下载被"版权限制"拒绝时模拟播放器缓存 | `player_capture.py`（被动捕获浏览器拉取的切片） |
| 4 | 更好的想法 | 请求头自动继承（见 §8）、三种入口、DRM 边界明确化 |

## 3. 已确认的关键决策（详见 讨论记录.md）

1. 下载引擎：**纯自研 Python**（requests + ThreadPoolExecutor），不封装外部下载工具
2. 嗅探形态：**有头浏览器**（用户可手动点播放/过验证）
3. 入口范围：**第一版三种入口全做**（sniff / get / play）
4. 第一版**不集成 yt-dlp**，作为二期候选
5. 加密边界：**支持 AES-128**；检测到 Widevine/FairPlay 真 DRM 时明确报错退出

## 5. 模块设计

### 5.1 config.py — 默认参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| DEFAULT_CONCURRENCY | 6 | 切片并发下载数（过高易被站点封禁） |
| RETRY_TIMES | 3 | 单切片重试次数 |
| TIMEOUT | (15, 60) | requests 超时（连接, 读取）秒 |
| OUTPUT_DIR | downloads | 相对当前目录的输出根目录 |
| FFMPEG_PATH | shutil.which | 系统安装的 ffmpeg |

### 5.2 utils.py — 通用工具

- `sanitize_name()`：Windows 文件名非法字符清洗（输出目录名用）
- `is_m3u8_url()` / `looks_like_segment()`：按 URL 后缀 + Content-Type 判定清单/切片

### 5.3 session.py — 请求会话与请求头继承

**背景**：多数"版权限制不能下载"实为服务器校验 Referer/UA/Cookie，
带上浏览器的请求头即可直接下载，因此请求头继承是本工具的隐形主力。

- `build_session()`：构造 requests.Session，设置 UA/Referer/Cookie/verify
- `headers_from_request()`：从 Playwright 抓到的浏览器请求头中挑选
  `user-agent / referer / origin / cookie` 四个关键字段
- `set_cookies_from_playwright()`：把浏览器 context cookies 灌入 requests 会话

### 5.4 parser.py — m3u8 解析（纯手写，无第三方 m3u8 库）

解析规则：
- **master 清单**：含 `#EXT-X-STREAM-INF`，提取 BANDWIDTH/RESOLUTION/CODECS 与变体 URI
- **media 清单**：`#EXTINF` + URI 成对；相对地址用 `urljoin(清单真实URL, uri)` 解析
- **加密标签**：`#EXT-X-KEY:METHOD=AES-128,URI="key",IV=0x...`
  - IV 缺省时按 HLS 规范用切片媒体序列号（16 字节大端）
  - 引号内含逗号的属性用小型状态机切分，不能简单 split(',')
- **fMP4**：`#EXT-X-MAP`（初始化段）单独记录，合并时排在首位
- **DRM 检测**（硬边界，命中即报错退出）：
  - KEYFORMAT 含 Widevine UUID `edef8ba9-...` 或 FairPlay `com.apple.streamingkeydelivery`
  - METHOD=SAMPLE-AES（无已知可解 KEYFORMAT 时视为疑似 DRM）

数据结构（dataclass）：`Key / Segment / Variant / Playlist`

`load_playlist()`：get/sniff 的高层入口——拉清单文本（以重定向后的最终 URL 为解析基准），
若是 master 自动选码率最高变体（可 `--quality worst` 或 `--variant-index N` 覆盖），
递归跟进直到 media 清单。

### 5.5 downloader.py — 并发下载 + 断点续传 + 解密

流程：
1. 建输出目录 `downloads/<安全标题>/segments/`，原始清单存为 `playlist.m3u8`
2. 去重下载所有 KEY 文件（16 字节）
3. `progress.json` 记录已完成切片（参考 e-download 的续传模式）：
   `{segments: {序号: {file, done, size}}, finished}`
   重跑同一命令时跳过已完成切片 → 支持"长时间下载中断后恢复"
4. ThreadPoolExecutor 并发下载（默认 6），单切片失败退避重试 3 次
5. 加密切片：AES-128-CBC 解密 + PKCS7 去填充（非标填充容错处理）
6. 全部成功后调用 merger 合并；任一切片最终失败则报错并提示重跑续传

### 5.6 merger.py — ffmpeg 合并

- concat demuxer：写 `filelist.txt`（`file 'segments/000000.ts'`），首次合并失败
  自动带 `-bsf:a aac_adtstoasc` 重试（TS→MP4 的 AAC 位流问题）
- 命令：`ffmpeg -y -f concat -safe 0 -i filelist.txt -c copy -avoid_negative_ts make_zero out.mp4`
- fMP4 场景把 init 段排在 filelist 首位
- 未找到 ffmpeg 时给出安装提示

### 5.7 sniffer.py — 有头浏览器嗅探

- Playwright 启动顺序：chromium → msedge 通道 → chrome 通道（本机未装内核时自动回退 Edge）
- `context.on("response")` 被动监听：URL 后缀 `.m3u8/.m3u` 或 Content-Type 含 `mpegurl` 即捕获，
  同时记录该请求的浏览器请求头（供下载继承）
- **线程模型**：Playwright 跑在子线程，主线程做交互（input 阻塞会冻结事件分发，
  导致候选列表不刷新，故拆线程 + queue 通信）
- 交互：候选实时打印，输入编号选择 / r 刷新 / q 退出；`--auto N` 供脚本化测试
- 选择后取 `context.cookies()` 一并交给下载会话

### 5.8 player_capture.py — 播放器兜底模式（三种入口之一）

适用：直接下载被拒（真 403/盗链校验复杂），但浏览器能正常播放。

原理：**不做请求改写，纯被动旁观**——`response.body()` 在监听器里取响应体落盘，
不干扰页面播放（比 route 拦截+fulfill 兼容性好，不会破坏站点的 CORS/流式逻辑）。

流程：
1. 有头浏览器打开播放页，监听所有响应
2. 捕获 m3u8 清单并解析 → 得到"期望切片集合"（URL→序号映射）
3. 浏览器播放过程中按 Content-Type/后缀捕获切片响应体，命中期望集合的立即写盘
4. `--speed N` 每 5 秒把 video 元素 playbackRate 调到 N（最高 16），拉快切片请求
5. 结束条件：全部捕获 / 浏览器关闭 / 超时 / Ctrl+C（用户看完即停）
6. 缺失切片用继承的请求头尝试直接补拉；补不齐则合并到首个断点为止
7. 最终走同一套 merger 合并

限制：耗时≈播放时长（倍速可缩短）；输入若是裸 m3u8 则生成本地 hls.js 页面代播（CORS 不保证成功）。

### 5.9 cli.py — 命令行入口（`py -m m3u_down`）

```
py -m m3u_down sniff <播放页URL>  [--auto N] [--no-download] [--max-wait 秒] [-o DIR]
                                  [--quality best|worst] [--variant-index N]
py -m m3u_down get   <m3u8直链>   [--referer U] [--user-agent U] [--cookie "k=v; ..."]
                                  [-o DIR] [--quality ...] [--variant-index N]
py -m m3u_down play  <播放页URL>  [--speed N] [--max-wait 秒] [-o DIR]
py -m m3u_down batch <列表页URL>  [--interval 秒] [--episodes "1-12,15"] [--yes] [--pick N]
                                  [-o DIR]
通用: [--concurrency N] [--proxy U] [--insecure/--no-insecure]
（CLI 未显式给出的参数回落到 config.json，再回落内置默认）

- `get`：直链 → load_playlist → downloader（全自动）
- `sniff`：嗅探 → 选择 → 自动继承请求头 → 下载（`--no-download` 仅嗅探）
- `play`：播放页 → 被动捕获 → 补拉缺失 → 合并

## 6. 输出目录结构

```
downloads/
└── <标题 sanitized>/
    ├── playlist.m3u8     # 原始清单存档
    ├── progress.json     # 续传进度
    ├── filelist.txt      # ffmpeg concat 列表
    ├── segments/         # 切片（000000.ts ...）
    └── output.mp4        # 成品
```

## 7. 边界与限制（v1.0 明确不支持）

1. **真 DRM（Widevine/FairPlay）**：密文切片无密钥不可解，检测到即报错（详见讨论记录）
2. **直播流（LIVE）**：EVENT/VOD 之外的场景暂不处理，列入二期
3. `#EXT-X-BYTERANGE` 切片：解析时警告，暂不实现
4. DASH（.mpd）：不适用本工具

## 8. 验证方案（不依赖真实站点）

1. **全链路**：ffmpeg lavfi 生成 5 个测试切片 → 明文版 + AES-128 加密版 + master 变体版
   三套本地 m3u8，`http.server` 起本地服务，CLI 逐一下载，ffprobe 校验产物时长
2. **续传**：下载中途 Ctrl+C 后重跑，验证跳过已完成切片
3. **嗅探**：本地测试页（自动 fetch m3u8），`sniff --auto 1 --no-download` 验证捕获与选择
4. **合并**：ffprobe 校验 output.mp4 时长/编码

## 9. 二期候选（不做进 v1）

- yt-dlp 作为首选尝试（命中支持的站点最快）
- 直播录制、DASH 支持、`#EXT-X-BYTERANGE`
- GUI 包装

## 10. v0.2.0 增补设计

### 10.1 统一配置 config.json（项目根目录）

- 加载顺序：内置默认 ← config.json ← CLI 显式参数（优先级递增）
- 首次运行若不存在则自动生成（含 `_readme` 说明键，加载时被忽略）
- 字段：`concurrency`（6）、`proxy`（空=不用，支持 http/socks5）、`retry_times`（3）、
  `retry_backoff`（2）、`timeout`（60，读超时；连接超时固定 15s）、`output_dir`、
  `download_interval`（60，batch 每集间隔）、`ffmpeg_path`（空=PATH 查找）、`insecure`（false）
- 代理同时作用于 requests 会话（`session.proxies`）与 Playwright 浏览器上下文
  （`browser.new_context(proxy=...)`），保证嗅探/下载路径一致；
  requests 走 socks5 需要 pysocks（已加入 requirements）

### 10.2 下载进度条（utils.render_progress，自写无依赖）

- 单行 `\r` 刷新：`[████████░░░░] 45.2% 162/358 | 96.8MB 6.2MB/s ETA 00:31`
- 百分比按切片数、字节数与速度按已完成切片累计，主线程更新（as_completed 回调）避免并发打印错乱
- downloader（get/sniff 路径）与 player_capture（捕获计数）均接入

### 10.3 batch 命令 — 列表页批量下载（batch.py）

流程：
1. **列表页解析（两级策略）**：requests+正则收集 `<a href+文本>`，空结果回退
   Playwright `page.content()` 收集 DOM；过滤同域 → 按"路径数字替换为 {d}"的模板分组
   取最大组 → 仅保留路径中含列表页 ID 数字 token 的链接（剔除其他番剧）→
   **按"集位"（路径末段数字）去重**——聚合站每条线路重复一份完整集表
   （`/p/{id}-{线路}-{集}/`，实测 youknow 为 26 线路 × 集表），同一集位按
   **线路号升序 > 带集数文本 > 页面序** 选取（线路1 是站点默认源），
   集名取该集位任一带集数文本的候选 → 自然排序
2. **简介抓取**：`description`（剧情，`html.unescape`）、`<h1>`/`<title>`（标题清洗）、
   `og:image`（容错：取最后一个 `http(s)://` 起始，修复站点拼接出畸形 URL 的情况）
3. **简介.md**（用户确认选 Markdown）：标题/封面链接/来源列表页/剧情简介/
   剧集清单表格（#、集名、链接、状态：待下载/完成/失败/未选择），状态随下载进度回写重写
4. **选集确认**：列出全部集数 → 回车全下 / 输入 `1-12,15` 选范围 / `q` 退出；
   `--yes` 跳过确认（脚本化）；`--episodes` 等价于预填范围
5. **逐集下载**：每集独立嗅探（浏览器自动选第 N 个候选，默认 1）→ 继承请求头下载；
   工作目录 `downloads/番剧名/_work/集名/`（含 segments/progress.json，集间隔离避免
   续传串台），成功后成品**扁平**移动为 `downloads/番剧名/集名.mp4` 并删除工作目录
6. **调度与容错**：`批量进度.json` 记录每集状态，已完成集（状态 done 且成品存在）自动
   跳过 → 中断后重跑同一命令续跑；单集失败标记后继续下一集，结束打印成功/失败/跳过汇总；
   每集之间 sleep `download_interval` 秒（默认 60，最后一集不等待）

### 10.4 v0.2.0 验证方案（增补）

1. 本地假列表页（含其他番剧干扰链接、同集重复、无文本链接）直接调用解析函数，
   验证过滤/去重/排序与选集范围解析、简介.md 生成
2. 真站 youknow.tv `batch --yes --episodes 1-2 --interval 5` 实测 2 集，
   验证简介生成、成品命名、间隔等待；重跑验证已完成集跳过
3. 修改 config.json `concurrency` 验证配置生效；代理留空验证不破坏现状

## 11. v0.3.0 设计（站点配置化 + failover + 完整性自检 + 单集后处理）

> 背景：youknow 全季 18 集实测通过，但暴露三类问题——① 解析规则按站硬编码，
> 换站（eacg.net）需重写；② 单集瞬时失败（CDN 超时/坏线路）只能等下次重跑；
> ③ 单集 get/sniff 无后处理（output.mp4 + 中间产物残留）。

### 11.1 站点配置层（新模块 sites.py + 项目根 sites/ 目录）

- `sites/` 目录每站一个 JSON 文件（如 `sites/youknow.json`、`sites/eacg.json`），
  内含 `_说明` 键充当注释；`sites.py` 按播放页/列表页域名后缀匹配加载。
- 配置字段（全部可选，缺省回退通用引擎行为）：
  | 字段 | 作用 | 示例 |
  |---|---|---|
  | `domains` | 域名匹配列表 | `["eacg.net"]` |
  | `play_pattern` | 播放页 URL 正则（命中才认为是剧集页） | `/vodplay/(\d+)-(\d+)-(\d+)\.html` |
  | `group` | 正则分组语义：id/line/ep 的组号 | `{"id":1,"line":2,"ep":3}` |
  | `line_preference` | `line_asc`（线路号小者优先，youknow）或 `complete_first`（集数最多且集名序号与集位一致的线路优先，eacg——其线路1集表残缺） | `"complete_first"` |
  | `label_strip` | 集名尾部噪声正则 | `"完结$"` |
  | `title_subs` | 单集成品命名用的标题替换规则 [正则, 替换] 列表 | `[["^正在播放",""],["《",""]]` |
  | `desc_prefix` / `desc_suffix` | 简介前后噪声正则（剥离） | `"^.*?剧情[:：]\\s*"` / `"\\s*\\|.*$"` |
  | `failover_max` | 单集最多尝试线路数（默认 3） | `3` |
- **解析主流程不变**（模板分组 + ID 过滤 + 集位去重 + 自然排序），站点配置做精修：
  1. 配置了 `play_pattern` 时：只收命中正则的链接，集位/线路号直接取分组，
     跳过模板分组启发式
  2. 同集位去重的排序键由 `line_preference` 决定（默认仍为 线路号升序 >
     带集数文本 > 页面序）
  3. `complete_first` 先对每条线路打分（集表条数、集名序号与集位一致数），
     分高者先；eacg 线路1（11 条、4 处错位）输给线路2（12/12 一致）
- 每个 Episode 除主 URL 外保留**按偏好排序的备选线路列表 `alts`**，供 failover 使用。
- 未匹配域名的站点：行为与 v0.2.0 完全一致（通用引擎兜底，仅无标题/简介清洗精修）。

### 11.2 batch 单集 failover（换线路重试）

- `_download_episode` 改为按 `[主URL] + alts[:failover_max-1]` 顺序尝试：
  嗅探失败 / 清单加载失败 / 切片下载失败 → 清空该集工作目录 → 换下一条线路重试；
  全部候选失败才标记该集 failed。
- 每次换线打印 `[批量] 换线重试: <url>`；同一集的多线路尝试共享集名/成品名。
- 已下载切片按"集+线路"隔离：换线时清空工作目录，避免不同清单的进度串台。

### 11.3 下载完整性自检

- **续跑校验**：progress.json 已存每片实际字节数；续跑时文件存在但大小与记录不符
  → 视为未完成自动重下（防截断片混入合并）。
- **下载校验**：响应带 Content-Length 且与实际字节数不符 → 按失败重试。
- **合并校验**：merge 成功后用 ffprobe（与 ffmpeg 同目录或 PATH）验证：
  时长 > 0 且含视频流（音频缺失仅告警）。校验失败 → 删除坏成品、保留切片现场、

## 12. 运行环境与已知坑（v0.3.1 实测补充）

> 本节是接入「统一下载管理器」时实测踩到的环境问题，与站点/代码逻辑无关，
> 但会决定「装好了却跑不起来」，因此单独成节。

### 12.1 依赖清单与安装

`requirements.txt`：`requests` / `playwright` / `pycryptodome` / `pysocks`；
另需外部命令 `ffmpeg`（合并）与 `ffprobe`（成品校验），以及 Playwright 浏览器内核：

```powershell
py -m pip install -r requirements.txt
py -m playwright install chromium      # 嗅探/兜底渲染用
```

- `playwright` 与 `pycryptodome`（`Crypto`）是 **`cli.py` 顶层 import**（经由
  `downloader.py` / `sniffer.py` / `player_capture.py`），**缺任何一个，连
  `get` 直链下载和 `--version` 都跑不起来**，不是等到嗅探才报错。
- `pysocks` 只在 `socks5://` 代理时需要（`http://` 代理不需要）。
- 实测 `py -m playwright install chromium` 若直连 CDN 超时，可走系统代理：
  `HTTPS_PROXY=http://127.0.0.1:10808 HTTP_PROXY=http://127.0.0.1:10808 py -m playwright install chromium`。

### 12.2 free-threading 构建（Python 3.14t）会让 Playwright 同步 API 段错误

**现象（实测）**：在 **Python 3.14t（free-threading，无 GIL）** 下，
`from playwright.sync_api import sync_playwright` 可以导入，但 `sync_playwright().start()`
**直接段错误（segfault，退出码 139）**；`-X gil=1` 与 `PYTHON_GIL=1` **都无法规避**。
异步 API（`async_playwright`）在同一构建上工作正常。

**影响范围**：本项目 `sniffer.py`（§5.7）、`player_capture.py`（§5.8）、`batch.py`（§10.3 每集嗅探）
**全部使用同步 API**，因此在 free-threading 构建下 `sniff` / `play` / `batch` 必然崩溃。
**`get`（直链下载）不使用 Playwright，不受影响。**

**规避**：改用同版本号的**普通（GIL）构建**运行。实测同一台机器上
`py -3.14 -m m3u_down ...`（普通构建）正常，`py -m m3u_down ...`（默认 3.14t）崩溃。

**与统一下载管理器的集成**：管理器 v0.2.0 已内置处理——若管理器自身跑在 free-threading
构建上且本机存在同版本 GIL 构建，会自动改用 GIL 构建运行下载器（其设计文档 §21.4.1）。
但依赖（playwright/pycryptodome/pysocks）必须装在**那个被选中的 GIL 构建**里；
本机已把三个包同时装进普通 3.14，并额外确认它已有 `ebooklib`。

**设计边界**：不改用异步 API 重写嗅探/捕获逻辑（改造面大、收益小）；
正确做法是约束运行环境用 GIL 构建。若将来 Playwright/greenlet 官方修复了
free-threading 兼容性，此约束可放宽。

## 14. v0.4.1 设计（play 滑动窗口修复 + 不推荐站点机制）

### 14.1 play 模式滑动窗口（直播式 HLS）修复

**背景**：分析 javdock.com 时发现部分站点用"滑动窗口"防直接下载——media 清单无
`#EXT-X-ENDLIST`、只列出最近 3 个切片（约 6 秒）、窗口实时前移、过窗切片立即 404。
play 模式原本按 VOD 假设设计，遇到滑动窗口会提前结束。

**三个 bug 与修复（均实测复现/验证）**：
1. `resolve_playlist` 用 `>` 比较切片数 → 滑动窗口每次刷新切片数不变，一直停留在
   第一条清单，新窗口永不命中。改为 `>=` 取最新清单。
2. 解析出的切片 `index` 是清单内位置（每个窗口都从 0 开始）→ 用 `index` 去重/命名，
   后续窗口切片被误判为已保存全部丢弃。改为用 `seg.seq`（真实媒体序列号，来自
   `#EXT-X-MEDIA-SEQUENCE`）去重/命名/补拉；VOD 时 seq==index 行为不变。
3. 结束判定 `saved >= expected` 把"当前窗口长度"当全集 → 捕获满一个窗口就提前退出。
   改为：VOD（ENDLIST）捕获完累计集合即停；滑动窗口（无 ENDLIST）等浏览器播放结束
   （`page.evaluate` 查询 `video.ended`，附 3 秒宽限抓最后窗口），否则靠超时/手动。

同时新增 `all_expected` 累计期望集合（跨清单刷新累加），进度条/命中判定都基于它。

### 14.2 不推荐站点机制（sites 配置）

- `SiteConfig` 新增 `unsupported: bool`（默认 False）与 `unsupported_reason: str`。
- `cli.main()` 在分发命令前检查 `args.url`：命中 `unsupported` 站点的域名即打印原因并
  返回退出码 3（1=通用错误，2=DRM，3=不推荐站点），不执行任何下载。
- 用途：把"研究过、但无法/不值得支持"的站点存档成配置；以后误用时给使用者一句话
  原因而不是徒劳尝试。

### 14.3 新增 sites/javdock.json（研究结论存档）

- 单视频页站点（简介/标题在视频页），batch 不适用。
- 三道防护：① Cloudflare Turnstile 拦截无头/自动化浏览器，但有头可用；
  ② 视频 URL 以 AES 密文写在 `data-ts-live`，需浏览器解密（页面加载即有头浏览器
  自动解密并拉取 master m3u8）；③ 滑动窗口 HLS：master 仅 240p、media 无 ENDLIST、
  只暴露最近约 6 秒切片、过窗即删（实测旧切片 404）。
- 结论：get/sniff 无法整片直下；play 可跟窗捕获但耗时≈视频时长且仅 240p。
  标记 `unsupported=true`，命中即提示退出。

## 13. v0.4.0 设计（弹窗/广告页嗅探 + 内嵌播放器直链 + 线路名展示）

> 背景：三个需求——① 部分站点点击播放后把原页面跳转到广告页、真视频在自动
> 新开的窗口播放，sniff 应对不了；② 新增站点 mvffm.net 结构全新（全部线路与
> 剧集的 m3u8 直链直接写在播放页 JS 里，无剧集 `<a>` 链接），旧通用引擎对其
> 完全无效（实测只解析到页面自引用链接"第154431集"且嗅探失败）；
> ③ 使用者在网页里看到的是**线路名**（如"FLV 22 推薦31"）而非序号，需要一个
> 把线路名与序号展示出来、且能按名传参的机制。

### 13.1 弹窗/广告页嗅探（sniffer.py 改造）

**问题诊断（实测/代码审查）**：
- `context.on("response")` 是**上下文级**监听，自动新开窗口（弹窗）里的 m3u8
  请求**本来就能被捕获**——真正的缺口在交互与存活判定：
- worker 循环只对主 `page` 调 `wait_for_timeout(200)`；主页面跳广告页后一旦被关闭
  （广告页常自动关，或使用者手动关），该调用抛异常 → 循环立刻 `break` →
  嗅探提前退出，即使弹窗里的视频还在播、m3u8 已入候选。`--auto N` 同样中断。
- 无任何弹窗/跳转检测与提示，使用者不知道真视频在新窗口、也不知道工具还在工作。

**方案：页面池 + 弹窗跟踪**：
1. `context.on("page")` 捕获自动新开的窗口，纳入**存活页面池** `live`；
   打印 `[嗅探] 检测到新窗口: <url>（真视频可能在此播放）`
2. 主页面 `framenavigated` 检测跳转：URL 变化时打印跳转地址；离开原域名时提示
   "可能为广告页，真视频在自动新开的窗口播放，候选会自动捕获"
3. 循环改为对页面池中**任一存活页面** tick；主页面关闭但弹窗仍存活 → 继续等候选，
   并打印"原页面已关闭；仍在监听新窗口的播放请求"；全部页面关闭才结束
4. 内嵌播放器站点（见 §13.3）嗅探时，把候选标注上线路名/集名：
   `[N] <url>（线路: FLV 22 推薦31 · 第1集）`

### 13.2 内嵌播放器直链解析（新模块 embedded.py）

**站点结构（mvffm.net 实测）**：WordPress + Dooplay 主题 + Vue.js 播放器，
播放页 `/drama/{id}/` 的静态 HTML 内嵌：
- `videourls`：二维数组 `线路 × 剧集`，每项 `{name, url}`，url 为 m3u8 直链
  （实测 22 线路 × 24~25 集，529 条直链全部 `.m3u8`，无需嗅探、无需 Referer 即可下载）
- `tables`：线路名数组（HTML 形式，如 `FLV 22 <font>推薦31</font>`）

**设计（配置驱动，回答"怕每站加参数"的顾虑）**：
- `sites/*.json` 新增可选字段 `player_embedded`：
  值 = 内置解析器类型名（目前 `dooplay_vue`），空 = 不用（旧行为）
- 新模块 `m3u_down/embedded.py`：
  - `_PARSERS` 注册表：`kind → 解析函数`；`parse(html, kind)` 分发
  - `parse_dooplay_vue()`：括号配平提取 `videourls`/`tables` JSON（不依赖
    固定数组长度），容错失败返回空
  - `line_match(line_names, spec)`：把 `--line` 参数匹配到 0 基线路下标——
    纯数字=1 基序号；线路名=去空白/大小写/NFKC 归一化后精确匹配；
    `FLV\s*(\d+)` 提取匹配（"FLV22 推薦31"可命中"FLV 22 推薦31"，
    覆盖繁简差异）；仅含一个数字时按 1 基序号兜底
  - `url_label_map()`：直链 URL → (线路名, 集名)，供 sniff 候选标注
- **扩展方式**：同结构站点（Dooplay 主题很常见）只需新建 `sites/*.json`
  写 `player_embedded: "dooplay_vue"`，零代码；播放器结构真正不同时才需
  新增一个解析函数 + 注册一行。**新站点永远不需要改 CLI 参数。**

### 13.3 batch 内嵌播放器流程（batch.py 改造）

`batch()` 入口检测到 `site.player_embedded` 非空时走新流程 `_parse_embedded_page`：
1. `_fetch_html`（requests；mvffm 的直链在静态 HTML，无需浏览器）
2. `embedded.parse` → 线路名 + 线路×剧集直链
3. **列出全部线路**（序号+名字，第1条标"默认"），按用户确认：默认第 1 条，
   `--line` 指定序号或名字覆盖（不匹配则打印提示并回退默认）
4. 按选中线路构建 `Episode`：主 URL = 该线路各集 m3u8；
   `alts` = **同集在其他线路的 m3u8**（前 `failover_max-1` 条），
   复用现有换线重试机制（选中线路 CDN 挂了自动换同集其他线路）
5. 标题/简介/封面仍走 `_extract_info`（mvffm 的 h1/og 标签齐全）
6. 选集、简介.md、批量进度、逐集下载、汇总——全部复用现有逻辑

**`_download_episode` 增强**：`ep.url` 是 m3u8 直链时**跳过嗅探**，
`build_session(referer=播放页URL)` 直接 `load_playlist` → 下载（
比开浏览器快得多，且不依赖站点是否自动播放）。

### 13.4 cli 与配置

## 15. v0.5.0 设计（新增 ikanbot.com：API 型内嵌直链 + 默认线路探活）

### 15.1 站点分析结论（ikanbot.com，实测）

- `/play/{videoId}` 为播放页：静态 HTML 含三个隐藏域——`e_token`（
  36 位随机串）、`current_id`（=videoId）、`mtype`（1=电影/2=剧集）。
- 页面 JS 拿到数据靠单一 API：`GET /api/getResN?videoId=&mtype=&token=`，
  一次返回**全部线路 × 全部剧集**的 m3u8 直链。不带 token 返回
  `{"state":-401}`。
- **token 算法（混淆 JS get_tks，已逆向，纯客户端）**：
  取 `current_id` 末 4 位数字，逐位 `d`：`k = d % 3 + 1`，从 `e_token`
  头部取 `[k, k+8)` 的 8 字符作为一段，然后 `e_token = e_token[k+8:]`；
  4 段拼接即 32 位 token。Python 三行可复现，实测命中。
- API 响应 `data.list[]` 每项 `{id, resData}`；`resData` 是 JSON 字符串
  （页面用 eval 执行，内容为合法 JSON 数组）`[{flag, url}]`；`url`
  字段为 `第01集$m3u8直链#第02集$…` 经典格式。
- 防护弱：无 Cloudflare、无 Referer 校验（切片实测裸下载成功）、
  清单为 VOD（ENDLIST）无加密。部分线路 CDN 已失效（实测 9 条中 4 条连不上）。

### 15.2 新解析器 `ikanbot_api`（embedded.py）

与 `dooplay_vue`（直链写在页面 HTML）的本质差异：直链在 **API 响应**里，
需要先算 token 发一次请求——这正是"播放器结构真正不同"的情形，按约定
新增解析器函数注册进 `_PARSERS`，CLI 参数零增加。

- `parse(html_text, kind, session=None, page_url="")` 增加可选参数；
  所有解析器统一签名 `(html_text, session=None, page_url="")`，
  dooplay_vue 忽略多余参数，行为不变。
- `_parse_ikanbot_api`：抽隐藏域 → 算 token → `urljoin(page_url, "/api/getResN")`
  请求 → 解析 JSON → 返回与 dooplay_vue 相同的 `(line_names, video_urls)` 结构。
  线路名用 `线路N (flag)`（flag 如 gsm3u8/lzm3u8，便于使用者辨认）。
  集名归一化：`第N集` → `第0N集`（部分线路不补零，避免文件名排序混乱）。
- `session` 为 None 时（sniff 标注场景）退化为裸 requests，失败仅影响
  候选标注，不影响主流程。

### 15.3 默认线路探活（batch.py）

聚合站线路死链常见（本片 9 条线路 4 条失效），若固定默认第 1 条，
每集都要先撞死链再 failover，白付超时代价。改为：

- 未指定 `--line` 时，按序探测各线路第一集直链（GET，5s 连接超时，
  校验响应以 `#EXTM3U` 开头），**第一条存活的线路作为默认**；
  全部失效时回退第 1 条（由既有 failover 逐集重试）。逐行打印探测结果。
- 显式 `--line` 时直接采用，不探活（死链交给 failover）。
- 探测使用与下载一致的 session（referer=播放页、代理/证书参数一致）。

### 15.4 sites/ikanbot.json

`domains: ["ikanbot.com"]`（www1 子域自动覆盖）、
`player_embedded: "ikanbot_api"`、`title_subs` 清洗标题后缀。
播放页 meta description 为搜索噪声（"搜到N条…"），无真实简介可取，
不做 desc 精修。

### 15.5 验证方案

1. 离线：已保存的播放页 HTML + 假 session（返回已保存的 API JSON）
   验证 token 计算、解析器输出（9 线路 × 13 集）、集名补零。

## 16. v0.5.1 设计（代理故障切换：连不上自动直连）

### 16.1 背景与目标

本机代理（127.0.0.1:10808）不稳定，经常 down 机；此前配置代理后一旦代理挂了，
所有命令整单失败（ProxyError），必须手动改 `--proxy ""` 或等代理恢复。目标：
**配置了代理但代理连不上时，自动降级直连**，代理恢复后自动回到代理。

### 16.2 requests 层：ProxyFallbackSession（session.py）

- 自定义 `requests.Session` 子类，重写 `send()`：首次捕获到
  `requests.exceptions.ProxyError`（代理进程拒绝/连不上等连接层失败）时——
  ① `self.proxies = {}`；② `self.trust_env = False`（不读系统/环境代理，
  确保是真正的直连）；③ 提示一次（进程级标志，batch 每集新建会话不刷屏）；
  ④ 同一请求重试。
- **关键坑**：`Session.request()` 会把预先合并好的代理 dict 塞进 `send()`
  的 `kwargs['proxies']`，它会覆盖 `self.proxies`——降级后必须
  `kwargs.pop("proxies", None)`，否则重试仍走死代理。
- 会话级降级而非进程级：batch 每集新建会话，代理中途恢复时后续集自动回到
  代理；`ProxyError` 只代表代理连接层失败，目标站自身的报错不触发降级
  （直连也无益，且可能引入出口 IP 变化风险）。
- `build_session()`：解析出的显式代理非空时用 `ProxyFallbackSession`，
  否则普通 Session（行为不变）。所有 requests 路径（下载/内嵌 API/探活/
  页面抓取）均经此入口。
- batch 的 `_fetch_html` 同步改走 `build_session`：此前页面抓取从不走
  config 代理（与下载出口不一致的旧账一并解决）。

### 16.3 浏览器层：启动前探测（sniffer.context_kwargs）

浏览器代理在 context 创建时固定，无法逐请求降级。改为**启动前取舍**：

- `probe_proxy(url)`（session.py）：requests 经代理 GET 目标页——任何 HTTP
  响应（含 403/跳转）算代理可用返回 True；连接层失败（ConnectionError，
  含 ProxyError/ConnectTimeout）返回 False；读超时/TLS 等说明 TCP 已通，
  返回 True。未配置代理返回 None。
- `context_kwargs(probe_url=None)`：配置了代理且探测返回 False 时不带代理
  创建 context 并提示，否则照旧带代理。调用点：sniffer 工作线程、
  player_capture、batch._render_html。
- 探测目标用目标页 URL 本身：若代理连不上目标站点，直连正是想尝试的方案。

### 16.4 验证

1. 单测：本地 HTTP 服务器 + 死代理端口（127.0.0.1:9）——首请求 ProxyError
   后降级直连成功、后续请求不再试代理、build_session 包装生效、
   probe_proxy 三分支、无代理普通会话回归、context_kwargs 三分支。
2. 真实环境：config 代理处于挂机状态，batch 全流程（页面/API/探活/清单）
   与 get 下载在不加 `--proxy ""` 时均自动降级直连完成。

## 17. v0.6.0 设计（站点级出口偏好 proxy_policy）

### 17.1 需求与实测依据

不同站点对代理的依赖不同，固定“代理优先”不合适：ikanbot 直连稳定、实测代理反而
可能下载失败；而部分站点不用代理连页面都打不开（代理不稳时体验差）。
故在站点配置里增加出口偏好，让下载器**按站点**决定先走哪个出口，失败再切另一个。

实测（本机，代理健康时）：

| 站点 | 直连 | 代理 | 结论 |
|---|---|---|---|
| youknow / eacg | 403（反爬，TCP 可达） | 403 | 出口无关 → proxy_first |
| mvffm | 页面 200；22 个 CDN 主机两方向结果完全一致 | 同左 | 出口无关 → proxy_first |
| ikanbot | 页面+CDN+真实切片全通 | 本次也通，但使用者实测曾下载失败 | → direct_first |
| javdock | 403（unsupported） | 403 | 不适用 |

### 17.2 配置字段

`SiteConfig.proxy_policy`（字符串，`sites/*.json` 的 `proxy_policy`）：

- `proxy_first`（默认）：推荐代理——先代理，连接层失败再直连；
- `direct_first`：不推荐代理——先直连，连接层失败再代理。

非法值告警并回退默认。CLI 显式 `--proxy URL` 视为用户明确意图，优先于站点偏好
（此时固定为“先代理后直连”）；`--proxy ""` 仍为纯直连。

### 17.3 实现

- **ProxyOrderSession**（替代 v0.5.1 的 ProxyFallbackSession）：构造时接收
  “出口顺序表” `[(proxies_dict, 名称), ...]`，`send()` 遇
  `requests.exceptions.ConnectionError`（含 ProxyError/ConnectTimeout/SSL）即
  切到下一档并粘住（会话内不再回切）；提示只打一次。读取超时不触发（站点慢≠出口不可达）。
- **session.py**：`build_session`/`session_from_sniff` 增 `direct_first` 参数；
  `probe_proxy(url, direct_first)` 改为双向探测并返回可用出口 'proxy'/'direct'（直连探测用
  `trust_env=False` 的临时会话，避免读系统/环境代理）。
- **sniffer.context_kwargs(probe_url, direct_first)**：浏览器启动前按偏好探测取舍；
  `sniff()` 工作线程与 `player_capture.capture()`、`batch._render_html()` 均按站点偏好传参。
- **batch.py**：`_fetch_html`/`_parse_embedded_page`/`_download_episode` 增 `direct_first`；
  `_probe_alive` 改为接收会话工厂（每条线路新建会话）——否则某条死链导致的出口粘性会污染
  后续线路的出口选择（实测：代理挂机时 ikanbot 会误判后续线路也失效）。
- **cli.py**：sniff 下载会话与 get（best-effort 站点匹配）均按站点偏好。

### 17.4 验证

1. 单测：ProxyOrderSession 三态（死代理→直连；直连失败→代理；直连可用不碰代理）、
   probe_proxy 四分支、四站点配置解析、_probe_alive 工厂语义。
2. 真站：ikanbot（直连优先）解析/探活/下载全链路正常；将代理指向死端口仍能正确选中
   存活线路 2；mvffm（代理优先）解析正常；代理优先路径 get 切片下载正常。

## 18. v0.7.0 设计（yt-dlp 引擎：主流站点自动路由 + B站批量）

### 18.0 已确认的决策（用户 2026-09-26 答复）

- cookie 默认从 **Edge** 读取（用户主力浏览器；Chrome 偶尔、Firefox 几乎不用）。
- **`mode` 默认 `auto`**：凡 yt-dlp 有专用解析器的站点都自动走 yt-dlp，免维护域名表，
  保持"给个 URL 就能下"。`list`（仅清单命中）作为可选严格模式。
- **不新增任何命令行参数**（追求零配置使用）；cookie/格式等全部走配置文件。
- 站点清单只预置**高可用站**，低可用（DRM 受限的长视频平台）不预置。
- yt-dlp 命中**优先于** `sites/` 的 `unsupported` 拦截。
- 缺 yt-dlp 依赖：报错退出 + 安装提示，**不静默回退**自研。
- batch 复用现有 `简介.md` / `批量进度.json` / `_work/` / 集间隔约定。

### 18.1 需求与背景

用户希望下载器直接支持 B 站等主流站点。B 站的关键难点（wbi 签名、DASH 音视频分离、
清晰度与登录鉴权、番剧地区限制）自研复刻成本极高，而 yt-dlp（youtube-dl 社区分支，
Unlicense）已实现 1800+ 站点解析器并持续适配，故采用**库集成**复用 yt-dlp。

路由规则（用户指定，顺序即优先级）：

1. URL 命中 `ytdlp_sites.json` 的域名 → 走 **yt-dlp 引擎**（`import yt_dlp` 直调）；
2. 否则命中 `sites/*.json` 的专用解析器（如 ikanbot 的 API 解析器）→ 走**自研内嵌直链引擎**；
3. 否则走**通用自研引擎**（嗅探 / 列表页正则解析）。

> 优先级说明：yt-dlp 命中优先于 `sites/` 的 `unsupported` 拦截（即某站被本下载器标为
> unsupported，但只要用户显式把它列进 yt-dlp 清单，就以 yt-dlp 为准）。
> 【待确认 4】

### 18.2 新配置文件 `ytdlp_sites.json`（项目根，与 config.json 同级）

不放入 `sites/`（那是自研 SiteConfig 格式，会被 `sites.load_all()` 当作站点配置解析）。
首次运行自动生成默认文件。

```jsonc
{
  "_说明": "…字段说明…",
  "enabled": true,                       // 总开关
  "mode": "auto",                       // auto=yt-dlp 有专用解析器的站都走 yt-dlp（默认）；
                                         // list=只有下面 sites 列出的域名才走 yt-dlp
  "cookies_from_browser": "edge",        // 默认 Edge；""/"chrome"/"firefox" 或 "chrome:Profile 1"
  "cookies_file": "",                    // cookies.txt 路径（非空则优先于 cookies_from_browser）
  "format": "bestvideo[height<=720]+bestaudio/best[height<=720]/bestvideo+bestaudio/best",
  "merge_output_format": "mp4",
  "extra_opts": {},                      // 透传给 yt-dlp 的逃生舱（如 extractor_args）
  "sites": [                            // 仅放"需要覆盖默认行为"的站点；auto 模式无需列域名
    { "name": "ikanbot", "domains": ["ikanbot.com"], "engine": "m3u" },
    { "name": "mvffm",   "domains": ["mvffm.net", "movieffm.net"], "engine": "m3u" },
    { "name": "eacg",    "domains": ["eacg.net"], "engine": "m3u" },
    { "name": "youknow", "domains": ["youknow.tv"], "engine": "m3u" }
  ]
}
```

- 逐站点可覆盖 `engine`（`m3u`=强制走自研，`ytdlp`=强制走 yt-dlp）/ `format` /
  `cookies_from_browser` / `cookies_file` / `extra_opts` / `proxy_policy`。
- **预置清单只放"守卫"条目**：已精修过的 4 个自研站点 pin 成 `engine: "m3u"`，
  避免 auto 模式下被 yt-dlp（若恰好也支持）抢走、导致 `--line` 等既有能力丢失。
  其余站点靠 auto 自动覆盖，不需维护域名表。低可用（DRM 受限）站点一律不预置。
- 清晰度语义：format 串表达"**优先 ≤720P；没有 720P 则取能下到的最清晰**"，
  与用户需求一致（未登录 B 站常只给 360/480P，自动落到最清晰）。

### 18.3 新模块 `m3u_down/ytdlp_engine.py`

职责（`import yt_dlp` 全部延迟到函数内，缺依赖时本工具其余功能不受影响）：

  ① 站点若 pin 了 `engine` 则强制；② `mode=list` 时仅清单命中走 yt-dlp；

## 19. v0.7.1 设计（cookie 读取失败的容错修复 + JS 运行时/小红书补充）

### 19.1 背景（实测发现的两个问题）

用户在浏览器登录 YouTube 后要求验证 cookie 是否可用，实测得到两条结论：

**问题 1（我们的 bug）**：`ytdlp_engine._is_cookie_error()` 写得太窄——

```python
return "cookie" in s and ("could not" in s or "unable" in s or "failed" in s)
```
它只能认出 `Could not copy Chrome cookie database`（浏览器占用），认不出
`Failed to decrypt with DPAPI. See .../issues/10927`（整句里没有 "cookie" 这个词）。
后果：v0.7.0 设计的"cookie 读不到 → 警告一次 → 去掉 cookie 重试"失效，
**任何 yt-dlp 下载都会直接失败**（只要 `cookies_from_browser` 非空）。

**问题 2（yt-dlp 侧，不可修）**：本机 Edge 3216 条 / Chrome 102 条 cookie
**100% 是 `v20` 前缀**（App-Bound Encryption，Chrome/Edge 127+ 起），
而 yt-dlp 2026.08.19 的 `cookies.py` 只认 `v10`，其余一律当 DPAPI 密文去
`CryptUnprotectData` → 失败并 `raise DownloadError` 强退（连跳过那条 cookie 都不做）。
已排除的猜测：终端不是管理员、`os_crypt.encrypted_key` 用 DPAPI 能正常解开
（所以不是密钥坏，是**每个 cookie 值**被 ABE 保护）。→ 对应 yt-dlp open issue **#10927**。

**附带发现（YouTube 第二道门槛）**：yt-dlp 的 `--js-runtimes` 默认只启用 `deno`；
本机没装 deno 但有 node v24。实测把 JS 运行时指为 node 后
`No supported JavaScript runtime could be found` 警告消失、提取继续。
实测指定"未安装的运行时"只会告警不会崩 → 可以安全地写进默认配置。

### 19.2 代码变更

1. **`_is_cookie_error()` 放宽**（同名函数，改判定）：

```python
_COOKIE_ERR_HINTS = ("dpapi", "app-bound", "app_bound", "decrypt",
                     "cookies database", "cookie database")
def _is_cookie_error(err):
    s = str(err).lower()
    if any(h in s for h in _COOKIE_ERR_HINTS):
        return True
    return "cookie" in s and any(w in s for w in ("could not", "unable", "failed", "error"))
```
  误判代价低：重试只是"再去掉 cookie 跑一次"，真失败仍是同一个错误。

4. **`cookies.txt` 路径坏掉也算 cookie 失败**：yt-dlp 打不开 cookies.txt 时抛的是
   `[Errno 2] No such file or directory: '<路径>'`（已丢掉"cookie"语境），
   新增 `_cookie_failure(err, opts)` 用"报错里含 cookiefile 路径 + 典型文件不存在文案"补判，
   降级时**同时**去掉 `cookiesfrombrowser` 与 `cookiefile`。

5. **`_Logger.error` 不再直接打印 cookie 类报错**：否则一次下载会先喊两遍"错误"
   再成功，看着像挂了。这类错误由 `_extract` 统一降级并给一次性中文提示；
   真到了不可恢复的地步，异常会传到 CLI 顶层打印 `[失败] …`，不会丢信息。

2. **警告文案升级**：说明 ABE(v20) 这个已知原因 + 附 issue #10927 链接 +
   给出两条可行替代（扩展导出 cookies.txt → `cookies_file`；有 Firefox 就用
   `cookies_from_browser: "firefox"`，官方也说这条路对 Firefox 效果最好、对 Edge 常出问题）。

3. **默认 `extra_opts` 预置 JS 运行时与 EJS 挑战脚本**：
   `{"js_runtimes": {"deno": {}, "node": {}}, "remote_components": ["ejs:github"]}`
   （deno 优先，没装则用 node；两个都没有只告警不报错）。
   注意 `load_config()` 是"用户文件里的键覆盖默认值"，所以**已存在的
   `ytdlp_sites.json` 必须同步更新**，否则改默认值对它无效。

6. **YouTube 需退三道关（用户装好 Firefox 后实测完成）**：
   ① cookie（`cookies_from_browser: firefox` 或 `cookies_file`）
   ② JS 运行时（`js_runtimes`）③ **EJS 挑战求解脚本**（`remote_components`）。
   证据链（同一视频逐个变量对照）：
   - 仅 Firefox cookie（无 EJS）→ `Extracted 60 cookies from firefox` 成功读到 cookie，
     但 `n challenge solving failed` + `Some web client https formats have been skipped…
     YouTube is forcing SABR streaming`，最终报 YouTube 自己的文案 `The page needs to be reloaded.`；
   - verbose 里关键三行：`[pot] PO Token Providers: none`（未装 PO token 插件但不致命）、
     `[jsc] JS Challenge Providers: … node …`（node 被识到）、
     `Remote component challenge solver script (node) was skipped`（**根因**：默认不允许联网拉 EJS）；

   - 端到端：`Me at the zoo` 19s 下载+合并成功；
     4K 源（`dQw4w9WgXcQ`）列出 2160/1440/1080/720/480… 并按设计选中 **720P**。
   - 无 cookie 时即使有 EJS 仍报 `Sign in to confirm you're not a bot` → **cookie 不可替代**。
   - 另：默认会选到 **AV1 + Opus**（mp4 容器合法，但部分老播放器不认）；
     想换 h264+aac 需改 `format`（已在使用指南给出示例，未改默认值）。

## 20. v0.7.2 设计（站点配置驱动的视频详情解析：`detail` 字段）

### 20.1 背景与问题

用户用 `https://www1.ikanbot.com/play/968393`（奴隶船）实测：详情信息只拿到标题，
**年份/地区/主演全丢**。查证：这些信息就在播放页静态 HTML 里，但通用提取逻辑
`batch._extract_info()` 只认 `<h1>`/`<title>`、`meta description`、`og:image` 三样：

```html
<div class="item-root">
  <img alt="奴隶船" class="cover lazy" data-src="https://tyyswimg1.com/….jpg">
  <div class="detail">
    <h2 class="meta title">奴隶船</h2>
    <h3 class="meta">2010</h3>          <!-- 年份：丢 -->
    <h3 class="meta">日本</h3>          <!-- 地区：丢 -->
    <h3 class="meta">吉岡睦雄/爱染恭子,,友田真希,,諏訪太朗</h3>  <!-- 主演：丢 -->
  </div>
</div>
```

且 `meta description` 是搜索噪声（"搜到1条…线路"，v0.5.0 已知）、`og:image` 倒是有。
各站详情块结构差异大，硬编码进 batch.py 会让通用代码长满特例——**解析方法下沉到站点配置**。

### 20.2 设计：`detail` 字段（sites/*.json 新增顶层键）

```jsonc
"detail": {
  // 保留键（结构与通用逻辑对接，缺省时回退通用提取）：
  "title":       {"pattern": "<h2[^>]*class=\"[^\"]*\btitle\b[^\"]*\"[^>]*>([^<]+)</h2>"},
  "cover":       {"pattern": "class=\"cover[^\"]*\"[^>]*data-src=\"([^\"]+)\""},
  "description": {"pattern": "…"},   // 本站没配；另用 desc_prefix 把整条搜索噪声清空（宁缺毋滥）
  // 附加键：键名即显示标签，原样写入 简介.md 的「视频信息」小节：
  "年份": {"pattern": "<h3[^>]*class=\"meta\"[^>]*>\s*(\d{4})\s*</h3>"},
  "地区": {"pattern": "<h3[^>]*>\s*\d{4}\s*</h3>\s*<h3[^>]*>\s*([^<]+?)\s*</h3>"},
  "主演": {"pattern": "<h3[^>]*>\s*([^<]*/[^<]*?)\s*</h3>", "replace": [[",,", "/"]]}
}
```

**规则字段**（每条）：

| 字段 | 默认 | 说明 |
|---|---|---|
| `pattern` | 必填 | Python 正则，`re.search(..., re.S)`；捕获组为值 |
| `group` | `1` | 取第几个捕获组 |
| `strip_tags` | `true` | 去内层标签 + 迭代 HTML 实体解码（与 batch 同款） |
| `replace` | `[]` | 值上的字面替换序列 `[[from, to], …]`（如 `,,` → `/`） |
| `multi` | `false` | true 时 `findall` 全部匹配，用 "，" 连接（适配每项一个元素的站点） |

**键名约定**：`title` / `cover` / `description` 是保留键，分别覆盖标题/封面/简介的
通用提取结果；**其余键一律视为附加信息，键名即简介页里的显示标签**（如 "年份"）。
用中文键省掉一层 label 映射，简介.md 里直接可读。

### 20.3 提取与回退流程（batch.py）

1. `site.extract_detail(html)` 返回 `{键: 值}`（坏正则在 sites.parse() 编译期拦截并告警，
   运行期不再抛错）。
2. `title = detail.pop("title")`，为空 → 原有 `<h1>` → `<title>` 兜底链；
3. `description`、`cover` 同理（cover 仍走 og:image 兜底 + `rfind("http")` 畸形修复）；
4. 剩余键原样并入 meta；`_write_info()` 在「来源列表页」之后渲染：

   ```markdown
   ## 视频信息

   - 年份：2010
   - 地区：日本
   - 主演：吉岡睦雄/爱染恭子/友田真希/諏訪太朗
   ```

5. 没配 `detail` 的站点（eacg/mvffm/…）行为与 v0.7.1 完全一致（零回归面）。

### 20.4 边界

- 仅影响**批量/内嵌流程的 简介.md 与 meta**；单集 `get` 命名仍走 `clean_title(title)`，
  标题本身两处一致。
- 规则匹配不到时**逐字段静默回退**通用提取，不告警（详情块本就是尽力而为）。
- `play_pattern`/线路解析等其余站点字段不受影响。

## 21. v0.7.3 设计（封面图本地化：番剧目录下 `image/` + 简介相对引用）

### 21.1 背景与问题

用户提出：batch 抓到的封面（剧照）是**远程链接**，`_write_info()` 直接把它写进 简介.md
（`![封面](https://图床/…jpg)`）。图片托管在站点的图床/CDN，视频下完放一段时间后**图床先清理**
——链接一失效，简介页就只剩一个裂图占位。视频文件本身没问题，但随片资料不完整。

需求（用户原话）：*"在剧集目录下建立一个 image 目录，把从视频简介里的剧照放在这个目录，
然后简介里引用这个剧照"*。

现状代码：封面唯一来源是站点 `detail.cover` 规则或通用 `og:image`（§20），
`batch._write_info()` 第 3 行渲染 `meta["cover"]`；yt-dlp 批量路径（§18）复用同一个
`_write_info()`，封面取自 `info["thumbnail"]`。

### 21.2 已确认的决策（用户 2026-10-01 答复）

| 议题 | 结论 | 说明 |
|---|---|---|
| 图片范围 | **只本地化当前那一张封面** | 不新增"页面上所有剧照"的多图提取规则（各站结构不同，成本高） |
| 文件名 | **`image/cover.<ext>`（ASCII 名）** | Markdown 相对链接无编码坑；扩展名按 Content-Type 判定，判不出兜底 `.jpg` |
| 下载失败 | **不显示图片，只在简介留一行文字提示** | 用户选择"宁缺毋滥"：不保留远程链接（跳过老链接的裂图，也跳过已失效链接） |
| 存量目录 | **不回填** | 只改代码，新下载生效；旧番剧目录重跑同一 batch 命令时顺带补上 |

### 21.3 新模块 `m3u_down/cover.py`

封面落盘与简介引用解耦成独立小模块（batch 只管调用），对外三个函数：

| 函数 | 职责 |
|---|---|
| `existing(anime_dir)` | 扫 `image/` 找 `cover.*` → 返回相对路径（`image/cover.jpg`）或 None |
| `fetch(anime_dir, url, …)` | 真正下载：探测扩展名 → 落盘 → 返回相对路径；失败返回 None |
| `prepare(anime_dir, meta, …)` | 幂等入口：已存在直接复用（**不发请求**）→ 否则 fetch → 结果写回 `meta["cover_local"]` |

实现要点：

1. **幂等**：`简介.md` 每集结束都整文件重写（`flush_info()`），封面若跟着重下就是每集
   多一次请求 → 以 `image/cover.*` 是否存在为唯一判据，存在即复用，连 HTTP 都不发。
2. **不落半截文件**：先写 `cover.<ext>.part`，成功后 `os.replace()` 改名为正式文件。
   否则下载中途 Ctrl+C 会留下一个大小为 0 的 `cover.jpg`，下次运行被误判为"已完成"。
3. **校验 Content-Type**：响应必须以 `image/` 开头才算成功。图床失效/防盗链常见
   **HTTP 200 + HTML 错误页**，只看状态码会把网页存成 .jpg。
4. **URL 容错**：协议相对（`//img/…`）补 `https:`、相对路径（`/img/…`）用 `urljoin`
   按列表页补全；这两类畸形地址在 `_extract_info()` 的 `rfind("http")` 修复之后仍可能出现。
5. **重试**：最多 `min(config.RETRY_TIMES, 3)` 次，间隔 `config.RETRY_BACKOFF` 秒；
   最终失败**只打印一行警告，不抛异常**——封面是锦上添花，不能因它中断整季下载。
6. **会话一致 + Referer 逐档回退（v0.7.4）**：走 `session.build_session(insecure=…,
   proxy=…, direct_first=站点出口偏好)`，与页面抓取/下载同出口；Referer 按
   `_referer_plans()` 三档依次尝试——**页面 Referer → 图片站自身 Referer（origin）→ 不带 Referer**。
   同一档内只对网络层/5xx 退避重试；**4xx（防盗链）直接换下一档**，不浪费退避时间；
   连接层彻底不通则不再换档（换 Referer 救不了）。

### 21.3.1 实测发现：豆瓣图床的防盗链（v0.7.4 修复的由来）

v0.7.3 上线当天用管理器实测 ikanbot 页面（`play/432956`），封面托管在豆瓣图床，
v0.7.3 的"单档 Referer"直接失败：

```
[封面] 下载失败，已跳过（不影响剧集下载）: 403 Client Error: Forbidden for url:
      https://img3.doubanio.com/view/movie_poster_cover/lpst/public/p2308783641.jpg
```

逐档实测（同一 URL，只改 Referer）：

| Referer | 结果 |
| --- | --- |
| 页面 Referer（`https://www1.ikanbot.com/play/432956`） | **403**（豆瓣只认自家域名） |
| 不带 Referer | **418**（反爬） |
| 图片自身完整 URL | **418** |
| 图片站根地址 `https://img3.doubanio.com/` | **200**（55049 字节）✅ |
| `https://movie.douban.com/` | **200** ✅ |

结论：存在"**只接受自家域名 Referer**"的一类图床，故引入第二档
"图片站自身 Referer = `scheme://host/`"（注意是**根地址**，不是图片完整 URL——
后者同样被 418）。修复后实测同一 URL 一次命中：`[封面] 已保存本地: image/cover.jpg
（改用图片站自身 Referer）`，55049 字节。

### 21.4 简介.md 渲染（`batch._write_info()`）

按 `meta["cover_local"]` 三态渲染（保留旧行为，零回归）：

| `cover_local` | 渲染 |
|---|---|
| 相对路径 | `![封面](image/cover.jpg)` |
| `""`（`cover` 非空） | `> 封面图未能保存到本地，此处不再显示（原图链接可能已失效）。` |
| 键不存在（旧调用方） | 原逻辑：`![封面](远程链接)` |

`meta["cover_local"]` 需从「视频信息」附加键列表里排除（否则会当标签渲染成一行）。
远程 URL 仍留在 `meta["cover"]`（`批量进度`/调试可用），只是不再出现在简介页。

### 21.5 调用点（两处，都在首次 `flush_info()` 之前）

- `batch.batch()`：选定集数后、首次刷新简介前 → `cover.prepare(anime_dir, meta,
  referer=列表页URL, insecure=…, proxy=…, direct_first=df)`。
  放在选集之后：用户 `q` 退出时不做无谓请求。
- `ytdlp_engine.download_entries()`：同位置；`proxy` 传 `_decide_proxy()` 的结果
  （None=探测结论为直连 → 传 `""` 强制直连，避免 `build_session` 回落到 config 再走一遍代理优先）。

### 21.6 影响面与边界

- 每部番剧最多多 **1 次** HTTP 请求（幂等：第二次运行起为 0 次）。
- `image/` 与 `_work/`、`批量进度.json`、收尾清理逻辑**无耦合**（清理只删 `_work/`）。
- 失败不改变退出码与批量汇总；单集下载逻辑完全不动。
- download-manager 只读 `批量进度.json`（判断状态），不受影响。
- 仅批量/内嵌与 yt-dlp 批量路径有 `简介.md`；`get`/`sniff`/`play` 单集模式无简介页，不涉及。

### 21.7 验证方案（本地，不依赖真实站点）

1. `http.server` 起本地服务：一张真 PNG/JPG + 一个 `Content-Type: text/html` 的假图。
2. 真图 → 落盘 `image/cover.png`（扩展名按类型修正）、简介渲染相对路径；
   二次运行日志无请求（幂等命中）。
3. 假图 → 无产物、简介留一行提示，退出码仍为 0。
4. 坏域名/连不上 → 打印警告后流程继续，删掉半截 `.part` 无残留。
5. 已有 `image/cover.jpg` 的目录重跑 → 文件 mtime 不变（未覆盖）。

**实际验证结果**：

- v0.7.3（本地）：真图 1 次请求成功并落盘、幂等二次运行 0 请求、假图/0 字节图/坏域名
  均返回 None 且无 `.part` 残留、简介三态渲染正确；另用公网图片
  （`python.org` 的 logo，15770 字节）跑通一次真实下载。
- v0.7.4（本地回归，加 Referer 回退链后）：第一档成功=1 次请求；第二档成功=2 次请求且
  第二次 Referer 为图片站根地址；假图=三档各 1 次（共 3 次，无退避浪费）；幂等命中 0 请求；
  连接层不通=不逐档重试。见 §21.3.1 的真实图床实测。
- **真站（管理器 + 油猴脚本，2026-10-01）**：`ikanbot play/432956` 批量第2-3集，
  任务正常解析 9 条线路并下载完成（第02集 344 MB / 2595 秒，ffmpeg 校验通过），
  同时暴露并修复了豆瓣图床的 Referer 问题（上表）。

## 22. v0.8.0 设计（外部已下载文件纳入批量进度）

### 22.1 背景与问题

用户在接入本下载器**之前**已用 IDM 下过一部分（`Download/牙狼garo/`）：

```text
牙狼garo-01-免费在线观看-爱看机器人-ikanbot.com.mp4      ← 用户用 IDM 下的（1-7 集）
牙狼garo-02-免费在线观看-爱看机器人-ikanbot.com.mp4
……
牙狼garo-08-免费在线观看-爱看机器人-ikanbot.com_2.mp4    ← 08-17 集（同目录重名，IDM 加了 _2）
……
第18集.mp4                                            ← 本下载器下的（18-23 集）
第19集.mp4
```

`批量进度.json` 只记录了下载器自己下的 6 集（键=剧集 URL）。于是重跑 `batch`
会把 1-17 集**再下一遍**（每集约 400 MB）——正是需求要避免的。

### 22.2 需求（用户原话）

> "在下载任务完成的时候，顺便扫描一下原目录，看是否有其它已下载的文件在，有的话就对应一个
> 代表集数的数字，看看能不能把我复制进去的、与真正使用下载器下载的集数，能更新到批量进度中，
> 这样我再使用下载器下载时，就不用重复下载了。"

### 22.3 已确认的决策（用户 2026-10-01）

| 议题 | 结论 |
| --- | --- |
| 默认行为 | **默认开启**（`batch` 每次都扫），另给 `--no-adopt` 关闭 |
| 简介.md 显示 | 状态列显示 **"完成"**，与下载器产物一致（不引入 `完成(外部)` 这类新取值） |
| 扫描范围 | 番剧目录**顶层** `*.mp4`（不递归；`_work/`、`image/` 是目录，天然被排除） |
| 扫描时机 | **下载循环开始之前**（理由见 22.5） |
| 体积判据 | **不做**：实测证明"体积小"不等于"没下完"（见 22.4 末） |

### 22.4 集号识别（新模块 `m3u_down/external.py`）

把一个文件名映射成"第几集"，按**有序规则**取第一个命中（宁可漏，不可错）：

| # | 规则 | 例（真实文件） |
| --- | --- | --- |
| 1 | `第\s*(\d+)\s*[集话話回]` | `第18集.mp4` → 18 |
| 2 | `S01E05` | `Show.S01E05.mp4` → 5 |
| 3 | `E05` / `EP05` / `Ep.5` | `Title.EP05.mp4` → 5 |
| 4 | 方/圆括号内数字 | `[01][1080p].mp4` → 1 |
| 5 | **分隔符包夹的数字**（取最后一个） | `牙狼garo-01-免费在线观看-爱看机器人-ikanbot.com.mp4` → 1 |
| 6 | 结尾裸数字 | `Title 05.mp4` → 5 |

- 识别前先剥掉噪声串：`1080p/720p/…`、`x264/x265/HEVC`、`WEB-DL/BDRip/…`、
  `CHS/CHT/中字/双语`、`\d+fps` 等；
- 再排除"绝不是集号"的数字：常见分辨率（240/360/480/576/720/1080/2160…）与
  四位数年份（19xx/20xx）。因此 `魔法师.2024.1080p.WEB-DL.mp4` **不会**被误认成第 2024 集；
- 规则 5 取**最后一个**候选：`Show 2 01.mp4`（第2季第1集）→ 1 而不是 2；
- 一条都不命中（如 `HD.mp4`、`魔法师 第一季.mp4`）→ **不纳管**，只在日志里列出，供用户人工确认。

**反向匹配**同样保守：外部文件的集号必须能在"本次解析出的剧集清单"里**唯一**命中某一集，
才写入该集的进度（多季混排页里同一集号可能对应多个 Episode → 有歧义就跳过并报告）。

**为什么不用文件体积判断"是否下完"**：用户那批文件里
`牙狼garo-01-…mp4` 只有 130 MB、`-13-…_2.mp4` 只有 223 MB（其余约 430 MB），
但实测**可读视频包数**几乎一致（35612 / 35516 / 35518 …，用
`ffprobe -count_packets` 数），且容器时长都是 24.3 分钟 —— 它们是**完整的低码率版本**，
不是半截文件。任何基于体积的过滤都会把这两集判成"没下完"而重下 400 MB。

### 22.5 时机：为什么放在"下载循环之前"而不是"任务完成后"

跳过判断是"进度=done **且**成品文件存在"（`batch()` 的循环开头）。
若只在整个任务结束后才纳管，**本轮**依然会把 1-17 集重下一遍 —— 与需求目的完全相反。
故纳管放在：解析出剧集清单 + 加载 `批量进度.json` 之后、进入下载循环之前。
用户原话的"任务完成时顺便扫一下"由"每次运行都扫"覆盖，且效果更强（当轮即生效）。

### 22.6 与批量进度的对接

- `_BatchProgress` 增加 `file_of(url)` 与 `mark_url(url, label, status, file)`
  （原 `mark(ep, …)` 改为调用 `mark_url`，行为不变）；
- **不覆盖**已有的 `done` 记录（下载器自己的成品优先）；
- **跳过判断放宽**：由"期望文件名 `第NN集.mp4` 存在"改为
  "进度里记录的文件存在 **或** 期望文件名存在"——
  这样外部文件（名字不同）也能被正确跳过；反过来，
  **删掉那个外部文件就会重新下载该集**（符合直觉的手动干预方式，写进使用指南）。
- **按成品文件名去重**（`dedupe_by_file()`）：站点换线路会让同一集的 m3u8 URL 变化
  （实测牙狼garo：早先下载走线路5、本次解析默认线路1，URL 完全不同），
  同一集于是被记在多条 URL 下，让"完成 X/X 集"虚高。
  纳管后按**同一个文件名**只保留一条，优先保留"出现在当前剧集清单里"的那条
  （即当前线路的 URL）；判据严格到文件名，不会误删别的集。
- `_BatchProgress` 另增 `done_urls()` / `save()`；`mark()` 内部改调 `mark_url()`，行为不变。

### 22.7 边界

- 只影响 `batch`（含 yt-dlp 批量路径复用同一 `batch.py` 逻辑）；`get`/`sniff`/`play` 单集无进度表，不涉及。
- 只扫顶层 `*.mp4`：`.part`/`.ts`/`.mkv` 等一律不管；子目录内容在日志里提示"已忽略"。
- 0 字节文件不纳管（视为占位/失败残留）。
- 识别错的风险被三重限制：唯一命中才写、找不到对应集不写、不覆盖已完成记录；
  且每次运行都会把"纳管结果 + 未识别文件"打印出来。

### 22.8 验证方案

1. 单元：用**真实文件名**（上面那批 IDM 命名 + 本下载器命名 + 各种常见命名 + 反面样本
   `HD.mp4`/`魔法师.2024.1080p.mp4`）断言 `episode_number()`。
2. 目录级：在临时目录造"3 个外部 + 2 个自家 + 1 个无法识别 + 1 个子目录"的混合场景，
   断言纳管集合、未识别清单、以及**已存在 done 记录不被覆盖**。
3. 真机：`Download/牙狼garo`（17 外部 + 6 自家 = 23 集齐）跑一次 `batch --yes`，
   断言"0 集被下载"、`批量进度.json` 变成 23 条、`简介.md` 全为"完成"、
   删掉某个外部文件后该集会被重新下载。

**实际验证结果（2026-10-01）**：

- 单元 21 例集号识别全部符合预期（含 6 个"必须猜不出"的反面样本）；
  目录级混合场景 15 项断言全过（含二次运行幂等、0 字节跳过、子目录不扫、
  歧义不写、删文件后可重下、同文件跨线路记录去重）。
- 真机 `Download/牙狼garo`：干跑 23 个文件 → 第01~23集一一对应（0 歧义 0 未识别）；
  实跑 `batch <url> --yes --episodes 1-23` → 纳管 23、清理 6 条换线路重复记录、
  **完成 0 / 失败 0 / 跳过 23**（真的一次都没下），进度 23 条全 done、
  简介表 23 完成 + 2 未选择（该清单其实有 25 集，第24、25集用户尚无 —— 纳管不掩盖缺口）。
- 反面对照：v0.7.4（无纳管）在同一目录上会把 1-17 集**整段重下**（约 7 GB）。

## 23. v0.9.0 设计（已下载视频的简要信息：线路 / 分辨率 / 时长）

### 23.1 需求（用户原话）

> "下载完，在标记批量与在简介中修改已下载时，顺便把下载好的视频的线路（如果有）、
> 分辨率、长度这些简短信息也放到表里去，到时我可以重新看回，不用猜。"

起因是 v0.8.0 实测暴露的一件事：同一部剧不同线路的清晰度能差 3 倍
（牙狼garo：线路1 = 640×480 / 135 MB，线路5 = 2880×2160 / 430 MB），
而此前 `简介.md` 只记"完成/失败"，事后根本看不出哪一集是什么货色。

### 23.2 已确认的决策（用户 2026-10-01）

| 议题 | 结论 |
| --- | --- |
| 表格形态 | **拆成三列**：`线路` / `分辨率` / `时长`（列名用「下载线路」以免与"链接"列里的线路号混淆） |
| 时长格式 | `25:06`；超过 1 小时 → `1:25:06`；未知 → `—` |
| 线路的来源 | **只记录下载器自己下载的那一集**；外部纳管进来的文件**不猜**（无从得知，猜就是错），填 `—` |
| 缺信息的行 | 未下载/失败/未选择的集一律填 `—` |

### 23.3 新模块 `m3u_down/mediainfo.py`

- `probe(path)` → `{"resolution": "640×480", "duration_sec": 1512.3}`（读不出来返回 `{}`）；
- `format_duration(sec)` → `25:06` / `1:25:06`；
- `fill_progress(progress, anime_dir)` → 给进度里"已完成但缺分辨率/时长"的记录补录，返回补录条数。

**为什么用 ffprobe 读成品、而不是 m3u8 里声明的 `RESOLUTION`**：

1. 声明与实际编码未必一致（站点标 1080p 而实际是 480p 的情况并不罕见），
   我们要记的是"我手上这个文件到底是什么"；
2. 外部纳管进来的文件**根本没有清单**可读，走声明值就补不了它们；
3. `ffprobe` 本来就是硬依赖（合并后校验要用），不引入新依赖。

**探测成本与缓存**：实测每个文件 0.3~3 秒（400 MB 的 4K 文件 3.3 秒）。
结果写回 `批量进度.json`，**只探测缺信息的**，所以只有第一次运行会付出这个代价；
后续运行 0 成本。

### 23.4 数据落地：`批量进度.json`

每条记录新增三个可选字段（有值才写，保持文件整洁）：

```jsonc
"https://…/index.m3u8": {
  "label": "第24集", "status": "done", "file": "第24集.mp4",
  "line": "线路5 (dyttm3u8)",   // 仅下载器自己下的才有
  "resolution": "2880×2160",     // ffprobe 读成品
  "duration_sec": 1512.3         // 秒（渲染时格式化）
}
```

时长存**秒数**而不是字符串：进度文件同时给机器和眼睛看，渲染格式（`25:06`）随时可改。

### 23.5 探测时机（两条路径）

| 场景 | 时机 | 说明 |
| --- | --- | --- |
| 本次下载的集 | 下载完成、成品改名之后立即 `probe()` | 与 `mark(done)` 同一次写入，简介状态表刷新时就有信息 |
| 已存在的旧文件（含外部纳管） | 纳管之后、**首次刷新简介之前** 跑一次 `fill_progress()` | 一次性补齐；只补缺的，后续运行不再探测 |

`fill_progress()` 放在纳管之外（不受 `--no-adopt` 影响）：它只补记录、不改判定。

### 23.6 简介.md 渲染（`batch._write_info`）

```markdown
| # | 集名 | 链接 | 状态 | 下载线路 | 分辨率 | 时长 |
|---|------|------|------|----------|--------|------|
| 1 | 第01集 | 直链·线路5 | 完成 | — | 640×480 | 24:18 |
| 24 | 第24集 | 直链·线路5 | 完成 | 线路5 (dyttm3u8) | 2880×2160 | 25:13 |
```

- 「下载线路」与「链接」列的区别：**链接**列是**本次解析**出来的线路（用于换线/failover），
  **下载线路**列是**这个文件实际来自哪条线**（历史事实）——
  两者不同正是需要区分的地方（实测就遇到过：文件来自线路5，而本次默认线路1）。
- `_write_info()` 新增可选参数 `records`（url → 记录 dict）；不传时退回旧的
  `status_by_url` 行为（yt-dlp 批量路径同步传入）。

### 23.7 边界

- 只影响 `batch`（含 yt-dlp 批量路径复用的 `_write_info`）；单集 `get/sniff/play` 无简介表格。
- 读不出信息（无 ffprobe、文件损坏、超时）只留 `—`，**不影响下载与状态判定**。
- 探测只对"进度里 status=done 且文件确实存在"的记录做，绝不因为探测失败而把集标记为失败。
- `--no-adopt` 仍会补录信息（那是两件事）。

### 23.8 验证

1. 单元：`format_duration()` 的 `25:06` / `1:25:06` / 0 / None；`probe()` 对真实文件
   （4K 与 480p 各一个）读出的分辨率与时长；对不存在的文件返回 `{}`。
2. 渲染：构造带/不带 `line`/`resolution`/`duration_sec` 的记录，断言表格三列与 `—` 兜底。
3. 真机：牙狼garo 用 `--line 5` 重下第24、25集 → 新记录带 `line`/`resolution`/`duration_sec`；
   1-23 集（含 17 个 IDM 文件）由 `fill_progress()` 补录分辨率与时长、
   线路列因来源未知而保持 `—`；第二次运行不再重复探测（日志无"[媒体信息] 读取 N 个…"）。

**实际验证结果（2026-10-01）**：

- 单元：`format_duration()` 9 例全过（含 `1:25:06`/`0:59`/`0`/`None`/非法值）；
  `probe()` 对真实 4K 文件读出 `2880×2160 / 1503.8s`、对 480p 文件读出 `640×480 / 1457.1s`、
  对不存在文件返回 `{}`；`fill_progress()` 只补缺的、第二次 0 条；三列渲染与 `—` 兜底全过。
- 真机：`fill_progress()` 首轮补录 **23/23** 个既有文件（17 个 IDM 命名 + 6 个自家命名），
  二次运行不再探测；`--line 5` 重下第24/25集后从 640×480/135-170 MB 变成
  **2880×2160/440-448 MB**，记录 `line="线路5 (dyttm3u8)"`；补记任务终态 `completed`/25 集全完成。
- **实测抓到并修掉一个 bug**：新增的 `mark(..., line=…)` 调用点没给 `mark()` 加 `**extra`，
  导致"文件已下好、写进度时抛异常"，两集被误标为失败（任务报"部分失败 25/27"）。
  修法是给 `mark()` 加 `**extra`，并把 `mark_url()` 改成合并而非替换。
  **教训**：单元测试只覆盖了 `mark_url()`，没覆盖新写的 `mark()` 调用签名 ——
  真机先于测试执行了它。以后给"底层写接口"加参数，必须在同一轮里补一条断言。
- **副产品（表格的价值实证）**：补录后一眼看出 25 集里
  **第01集 640×480 / 130.5 MB、第13集 960×720 / 223.8 MB**，其余 23 集均为 2880×2160
  —— 这两集正是此前只能靠体积猜的那两个。

## 24. v0.10.0 设计（下载前自动判定"这集要不要重下"）

### 24.1 需求（用户原话）

> "我想重新下载第1集，我要怎么做？理论上我用 batch，下载器会直接跳过第1集不下载的哦"
>
> "下载前，读取到 m3u 之后，好像是能读取到未下载的视频的长度、分辨率这些数据的吧，
> 如果能读取，那就这样：首先判断已下载好的视频的线路信息，如果线路信息不一样的，重下；
> 如果线路信息一样，分辨率与时长不一样，重下；如果都一样，就跳过，这样可以实现吗？"
>
> "不想加参数啊"（否掉了 `--redo` 这类显式开关）

### 24.2 已确认的决策（用户 2026-10-01）

| 议题 | 决策 |
| --- | --- |
| 实现形态 | **不加任何命令行参数**，改成下载前自动判定 |
| 判定数据来源 | **只用清单声明值**（零额外流量），不抓切片探测真实分辨率 |
| 旧成品处理 | 重下时**就地改名成 `<名>.bak` 保留**（不删除） |
| 第13集 | 保留新下的（960×720/1501.8s），旧 IDM 那份 .bak 删除 |

### 24.3 实测依据（为什么必须带"保险丝"）

用临时探针（`m3u_down.parser` + 首个切片 + ffprobe）在 ikanbot/牙狼garo 上实测：

| 集 | 清单声明 | 首个切片**真实**分辨率 |
| --- | --- | --- |
| 第01集（线路5/13） | `1080x608` | **2880×2160**（线路6 同样声明 1080x608，真实只有 640×480） |
| 第13集（线路5/13） | `1080x608` | **960×720**（13 条线路里最好的就是它） |
| 第18/24集（线路5） | `1080x608` | **2880×2160** |

- **声明值两头都会错**：既会偏低（第01集声明 1080x608、实际 4K），也会偏高（线路6 声明
  1080x608、实际 640×480）；`BANDWIDTH` 同样不可信（全声明 800 kbps，实际约 2.4 Mbps）。
- **时长也对不上**：清单 `EXTINF` 求和 = 1475 秒；下载器自己下的成品 = 1503 秒（+1.9%）；
  用户 IDM 那批 = 1456 秒（−1.3%）。三个数互不相等。
- 因此"声明 vs 实际"直接相比会出两种事故：21 个 4K 成品（声明 0.66 Mpx < 实际 6.2 Mpx）
  被判"分辨率不同"而**每次重下**、甚至**死循环**（重下后仍然 4K vs 1080x608）；
  25 集全部因"时长不同"被整体重下（约 10GB）。→ 必须有 24.4 的保险。

### 24.4 判定规则（只对"进度里 status=done 且文件存在"的集）

按顺序，命中即定；**任何一步值取不到都按"未命中"处理**（即跳过）：

| # | 条件 | 动作 |
| --- | --- | --- |
| 0 | `ep.url` 不是 m3u8 直链（嗅探型列表页/yt-dlp 路径） | 不判定，保持 v0.9.0 行为 |
| 1 | 清单读不到（网络失败/无变体/无切片/解析异常） | **跳过** + 一行提示（绝不因探测失败去重下） |
| 2 | 记录里已有 `declared_resolution`/`declared_duration` 且与本次声明一致 | **跳过**（同源 → 杜绝死循环） |
| 3 | 记录 `line` 非空且 ≠ 本次线路名 | **重下**（用户的第 1 条规则） |
| 4 | 声明像素数 ≥ 现有像素数 × 1.2 | **重下**（清单里有更高清版本） |
| 5 | 声明像素数 ≤ 现有像素数 × 0.8 | **跳过**（**不降级**） |
| 6 | 声明时长 − 现有时长 > max(60 秒, 现有 × 5%) | **重下**（现有文件疑似缺内容） |
| 7 | 其余 | **跳过** |

三条保险的作用：**②防死循环**（每次重下都会记下当时的目标值）、
**⑤不降级**（保护 21 个 4K 成品）、**①失败即回退**（绝不因探测失败重下）。

### 24.5 实现要点

- `parser.py`：
  - `#EXTINF` 的时长不再丢弃 → `Segment.duration`，`Playlist.declared_duration`（求和，属性）；
  - `Playlist.variant_resolution` / `variant_bandwidth`：`load_playlist()` 跟进 master 变体时
    把**选中变体的声明分辨率**带回到 media 清单上（一次调用同时拿到分辨率与时长）；
  - `load_playlist(..., quiet=True)`：判定时的探测不打 "[清单] …" 噪音日志。
- **新模块 `m3u_down/precheck.py`**：
  - `probe(session, url)` → `{resolution, duration_sec, segments}`，失败返回 `{}`（绝不抛）；
  - `pixels("1080x608")` → `656640`；解析不出返回 0；
  - `decide(record, probed, line_name)` → `(action, reason)`，`action ∈ {skip, redo}`，`reason` 为中文说明。
- `batch.py` 接入点：原 `if episode_done(...): 跳过` 改为
  `episode_done(...)` → `precheck` 判定 → 跳过或继续下载；判定用的声明值在下载成功后
  随 `mark()` 一并写入（`declared_resolution` / `declared_duration`）。
- **旧成品备份**：判定触发重下时，把现有成品改名为 `<名>.bak`（已存在则 `.bak2`、`.bak3`…）：
  - 同名（我们自己的命名，如 `第13集.mp4`）：改名失败则**放弃本次重下**（保持跳过 + 告警），
    避免"覆盖掉唯一一份";
  - 异名（外部纳管，如 `牙狼garo-01-….mp4`）：改名失败只告警、不阻断（新成品文件名不同，不会覆盖）。
- 汇总多一行：因判定而重下的集数单独列出（`重新下载 N 集`）。
- 每次探测**新建一个 session**：实测教训 —— 用一个 session 连续访问 13 条线路时，
  前几条死链会让会话降级到代理（`127.0.0.1:10808` 未开），导致后续**全部**请求失败；
  `_probe_alive()` 早有同样的注释与做法，这里沿用。

### 24.6 边界

- 声明值本身不可信（24.3），所以本规则**只升不降**并记忆声明值：
  最坏后果是"多下一次同档的片"，不会是"越下越差"或"每次运行都重下"。
- 时长比对是**粗检**（容差 `max(60 秒, 5%)`），抓"大块缺失"，抓不到几秒级差异
  （实测 IDM 那批比我们短 3%，低于容差 → 不重下）。
- 不抓切片：真实分辨率拿不到（用切片探测约 2MB/集，本次按用户决策不采用），
  因此**可能漏判**"声明偏低且现有文件正好等于声明值"的升级机会。
- 探测只打主 URL，不走 `alts`（failover 是下载阶段的事）。
- 只影响 `batch`（内嵌直链站点）；yt-dlp 批量路径、`get/sniff/play` 不受影响。
- `--no-adopt` 与判定无关（纳管只写记录，判定只看记录与清单）。

### 24.7 验证方案

1. 单元：`decide()` 覆盖 8 种输入（升级/降级/同档/时长缺失/声明记忆/线路变化/空记录/探测失败）；
   `pixels()` 对 `1080x608`/`2880x2160`/`—`/`''`；`parser.parse()` 的 `declared_duration`
   与 `variant_resolution`。
2. 真机：牙狼garo 跑 `--episodes 1,13,18,24`（线路5）——预期**只有第01集重下**
   （640×480 → 真 2880×2160），第13/18/24 集全部跳过且日志给出各自理由。
3. 幂等：紧接着再跑一次同一命令 → **0 下载**（第01集因声明记忆而跳过）。

**实际验证结果（2026-10-01）**：

- 单元：22 项全过（`pixels` 7 例、`#EXTINF` 求和 7.5 秒与 `Segment.duration`、`decide` 12 种输入：
  升级 / 降级 / 同档 / 线路变化 / 声明记忆 / 时长粗检（缺一半要重下，差 1.3% 不重下）/
  记录缺字段 / 清单无声明值 / 探测失败）。
- 真机第一轮（全部 25 集、`--line 5`）：**只有第01集重下**（640×480 → 2880×2160，
  136.9 MB → 425 MB，1502.8 秒），其余 24 集跳过：21 集走"声明低于现有，不降级"、
  第13集走"声明与现有成品相当"。汇总 `完成 1 / 失败 0 / 跳过 24`，
  `其中重新下载 1 集（判定为清单有更高清版本）: 第01集`；旧成品被改名为
  `牙狼garo-01-….mp4.bak2`（`.bak` 名当时被我手工复制的那份占着）。
- 真机第二轮（同一命令，幂等）：**0 下载**，第01集走"清单声明与上次一致（同一份源）"→
  证明**声明记忆确实切断了"声明 1080x608 vs 实际 4K"这种死循环**。
- 开销实测：25 集全部跳过的这一轮（含站点解析、纳管扫描、25 次清单探测）耗时约 **114 秒**
  （约 4 秒/集，每集 2 个清单请求；站点 CDN 单请求 1~2 秒）。**零额外流量**（不抓切片）。

## 25. v0.11.0 设计（续跑可恢复：进度记入口 URL + batch 支持裸 m3u8）

### 25.1 背景

统一下载管理器（download-manager）的「已下载的产物」列表行有个「续跑/补下」按钮，
原理是"重跑同一条 `batch <url>` 命令"。但它报"缺少地址，无法续跑"——根因在两边：

1. **管理器侧**：`scan()` 给产物条目写死 `extra={"url": ""}`（其它三个适配器都会从
   各自进度文件回填，只有 m3u 适配器没做）；
2. **下载器侧**：即使管理器想回填也拿不到——`批量进度.json` 里只有按剧集 URL 记的
   episodes，没有"我是从哪个入口 URL 来的"；且 `batch` 不接受裸 m3u8，
   当初 `get` 的直链任务连"重跑什么命令"都无解。

### 25.2 设计

- **`批量进度.json` 新增两个顶层键**（不属于任何一集）：
  - `list_url`：本次任务的入口地址（列表页，或裸 m3u8 直链）；每次运行刷新。
  - `resume_hint: {line, pick}`：续跑时要带回的 `--line` / `--pick`。
    不带回的后果：内嵌站点重跑时重新探活，可能换到另一条线路，触发 §24 规则
    "记录线路 ≠ 本次线路 → 重下"，把整季已完成集全部重下一遍（实测 25 集约 10GB）。
    `episodes` 范围**不记**：用户决策"续跑=全选当前列表页"，新集自动下载（追番），
    记了范围反而挡住新集。
- **`batch()` 接受裸 m3u8 URL = 单集 batch**（`_single_episode_plan`）：
  label 取 URL 文件名去扩展名（去 query；路径为空回退域名），meta 只有
  `list_url`，无封面流程（跳过 `cover.prepare`，避免"封面未能保存"误导文案），
  其余进度/跳过/failover/简介框架全部复用。管理器续跑从此统一
  `batch <url> --yes`，四种提交方式（get/batch/yt-dlp/sniff_list）全覆盖。
- **兼容**：旧进度文件无新键，`setdefault("episodes", {})` + `.get()` 读取，
  首次运行即补写；`set_resume_hint` 仅变化时落盘。

### 25.3 实现中现形的 bug（与本次同版修掉）

`batch()` 里纳管循环写成 `for line in external.format_report(...)`，
**循环变量把 `--line` 参数同名覆盖**。此前 `line` 在循环后无人使用，潜伏无症状；
本次 `set_resume_hint(line, pick)` 把纳管日志行当线路名写进进度。
修复：循环变量改名 `report_line`；本地验证加静态断言防回归。

### 25.4 验证

`本地验证/run_resume_test.py`（自包含：ffmpeg testsrc 生成真实切片 + 本地
http 服务，不依赖真实站点），28 项：单集计划 5、进度结构 10（含旧文件/坏 json
兼容）、直链 batch 全流程 9（含简介/封面文案/中间产物清理）、重跑跳过 3
（日志"已完成，跳过" + 成品 mtime 不变 + 无新下载行）+ 防遮蔽静态断言 1。
