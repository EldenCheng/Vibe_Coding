# Google Drive 个人文件同步器 · 可行性研究

> 撰写日期：2026-10-12
> 性质：思维实验 / 技术调研文档，不含可执行项目
> 结论先行：**可行，但不建议自研。** Drive API v3 提供了做同步器所需的全部接口，真正的工程难点在同步算法本身。推荐先用 rclone bisync 跑通，再决定是否自研。

---

## 1. 结论摘要

### 1.1 可行性判定

| 问题 | 结论 |
|---|---|
| Google Drive 能否通过 API 访问？ | **能。** Drive API v3 是公开的、免费的、Tier-1 支持的 REST API，官方文档完整，配额充足 |
| 能否用它实现个人用文件同步器（Nextcloud 类）？ | **技术上能。** 所有同步器必需的零件 Drive 都提供了 |
| 但能否替代 Nextcloud 的完整体验？ | **不能。** Drive 没有文件系统抽象、没有 WebDAV、无法做手机系统级同步服务 |
| 该不该自己写？ | **不该（除非为了学习）。** rclone bisync 已经是一个成熟的、针对 Drive 优化过的双向同步引擎 |

### 1.2 一句话适用性判断

- ✅ **适合**：个人 / 小团队的目录级双向同步、单向上传备份、跨设备文件分发、自动化脚本（把本地目录定期推到 Drive）
- ❌ **不适合**：需要手机原生同步、需要多人实时协作、需要版本控制式历史、需要文件系统语义（硬链接、符号链接、权限位）

### 1.3 本次调研的决定前提

调研目的为学习 API 与同步原理，因此推荐路径是：先跑 rclone bisync 拿到真实体感 → 再读 rclone bisync 源码理解三方合并算法 → 自研与否由读到源码后自行判断。同步语义需求为**双向同步 + 冲突保留双份**。

## 2. 能力对照：同步器需要什么 vs Drive API 有什么

下表逐项核对 Drive API v3 能否满足一个同步器的功能需求。

| 同步器需求 | Drive API 对应能力 | 满足度 |
|---|---|---|
| 列目录 / 全量扫描 | `files.list`，支持 `q` 查询语法、`pageToken`、`fields` 字段裁剪、`spaces=drive` | ✅ 完整 |
| **增量变更检测** | `changes.getStartPageToken` + `changes.list`，token **永不过期** | ✅ 完整，官方同步方案 |
| 变化推送（准实时通知） | `changes.watch` / `files.watch`（webhook 推送） | ⚠️ 需公网 HTTPS 回调地址，本机场景用不了，退化为轮询 |
| 上传（含断点续传） | resumable upload session（`uploadType=resumative`，256KB 最小分片，可中断续传） | ✅ 完整 |
| 完整性校验 | 文件自带 `md5Checksum`（部分文件另有 sha1/sha256）；Google 原生文档需走 `files.export` | ✅ 完整（原生文档除外） |
| 删除 / 回收站 | `files.delete` 默认进回收站（保留 30 天），`trashed` 字段可查 | ✅ 完整 |
| 重命名 | `files.update` 改 `name` | ✅ 可行 |
| 移动（换父目录） | My Drive 下需"添加新父目录 + 移除旧父目录"两步模拟；共享云端硬盘可原子修改 | ⚠️ 不原子，中途失败会留下双父引用 |
| 版本历史 | `revisions`（Google 策略：30 天或 100 个版本，先到先算，不占存储配额） | ✅ 赠送，但非完整版本控制 |
| 权限管理 | `permissions` | ✅ 完整 |
| 共享云端硬盘 | `drives`（原 Team Drives），`spaces=drive` 参数 | ✅ 完整，且更适合当同步后端 |
| 配额信息 | `about.get` | ✅ 完整 |

### 2.1 配额（重要）

2026-05-01 起 Drive API 改用"配额单位（quota units）"计费：

| 限额类型 | 数值 |
|---|---|
| 每分钟 / 每项目 | 1,000,000 units |
| 每分钟 / 每用户 / 每项目 | 325,000 units |
| 每 24 小时 / 每项目（开始计费的阈值） | 400,000,000 units |

单次请求消耗：

| 操作 | units |
|---|---|
| 读（`files.get`） | 5 |
| **列（`files.list`）** | **100** |
| 下载（`files.download`） | 200 |
| 改（`files.update`） | 50 |
| 其他（如 `files.generateIds`） | 5 |

超限返回 `403: User rate limit exceeded`，后端还可能返回 `429: Rate limit exceeded`，必须指数退避重试。

**关键结论：配额消耗与文件数量成正比，与文件体积无关。** 10 万个小文件带来的请求开销，远大于 10 个大文件。这是自研同步器时最主要的性能瓶颈，也是 `changes` feed 增量方案最大的价值所在。

其他硬限制：

- Workspace 用户在 My Drive 与共享云端硬盘之间每天只能上传 **750 GB**（复制同样计入），单文件上限 **5 TB**，单次复制上限 750 GB
- 目前所有标准使用**不额外收费**，但官方声明 2026 年内会对超出配额部分开始计费（会提前 90 天通知）
- 每个 OAuth client_id 有独立的每秒事务数限额，默认 **10 transactions/second**（这也是 rclone 官方建议自建 client_id 的原因之一）

### 2.2 Drive 的"原生文档"是个坑

Google Docs / Sheets / Slides 在 Drive 里不是普通文件：没有原始字节，下载必须走 `files.export` 按格式导出（docx/xlsx/pptx/pdf/odt...）。对同步器的影响：

- 它们**没有 `md5Checksum`**，校验逻辑必须特判
- 导出是**有损**的（xlsx → csv 会掉格式），所以反向导入要极其谨慎
- rclone 用 `--drive-skip-gdocs` 让原生文档在列表里彻底隐身，这是实践中的推荐做法

如果只同步"自己的普通文件"，直接排除原生文档即可，问题就不存在了。

## 3. 关键限制与坑

这一节是本次调研最重要的产出。前 5 条是真正会让项目失败的坑。

### 坑 1：OAuth refresh token 7 天失效 ⚠️ 最容易踩

**现象**：程序跑得好好的，一周后突然全部 API 调用失败，报错 `invalid_grant: Token has been expired or revoked`。

**原因**：Google Cloud 项目的 OAuth consent screen 如果同时满足三个条件：
1. 用户类型是 **External**
2. 发布状态是 **Testing**
3. 请求的 scope 不在基础集合（`name` / `email` / `profile`）内 —— **Drive 不在基础集合内**

那么签发的 refresh token **只有 7 天有效期**。Drive 恰恰不在豁免范围内，所以"External + Testing"这个组合在实践中基本等于"一周失效一次"。

**解法**：把 publishing status 从 `Testing` 切成 **`In production`**。

**关键澄清**（很多教程混淆了这两个概念）：

| 轴 | 是什么 | 影响 | 耗时 |
|---|---|---|---|
| **发布状态**（Testing ↔ In production） | 你自己能点的开关 | **refresh token 寿命**、是否需要测试用户白名单 | 即时 |
| **审核验证**（unverified ↔ verified） | Google 人工审查 | 登录时的"应用未经验证"警告屏、用户数上限、能否向陌生人开放 restricted scope | 数天到数周 |

**应用可以处于「In production + unverified」状态**，这对个人自用完全够用：登录时点一下"高级 → 前往 xxx（不安全）"即可。Google 明确豁免了"个人使用（少于 100 用户）"类应用的强制验证要求。

**其他会导致 token 失效（非定时）的情况**：
- 用户在 Google 账号安全设置里撤销了授权
- token 连续 **6 个月**未被使用
- 修改了申请的 scope（旧 grant 不再匹配）
- 超过 per-user/per-client 的活跃 token 数上限（Google 会静默吊销最旧的，实践中常见上限约 50）
- 改密码 / 发生安全事件

### 坑 2：scope 选择

| scope | 能力 | 验证负担 |
|---|---|---|
| `drive` | 访问所有文件（同步器必须用这个） | restricted scope。**公开分发需 CASA 第三方安全评估（付费）**；单用户自用不受影响 |
| `drive.file` | 只能访问本应用创建的文件 | 轻。但从网页手动上传的文件 rclone 完全看不到，**做通用同步器不可用** |
| `drive.appfolder` | 应用专属隐藏目录 | 轻。但只能看到一个隔离目录 |
| `drive.readonly` | 只读 | 轻 |
| `drive.metadata.readonly` | 只读文件名 | 轻 |

自研同步器基本只能用 `drive`，也就意味着要接受坑 1 的全部约束。

### 坑 3：没有服务端 move

Drive API **没有**"移动/改名"的原子操作：

- 改名 = `files.update` 改 `name`（原子，还行）
- 换父目录 = 一次 `files.update` 同时给出新 parents 列表（My Drive 下可行，因为一个文件在 My Drive 只有一个 parent）
- 但在**共享云端硬盘**里，一个文件可以有多个 parent；模拟移动会经历"短暂存在于两处"的中间态

对同步器的影响：重命名检测（rename tracking）无法用服务端 move 实现，只能本地做 hash/size 匹配再上传删除，或退化为"新建 + 删除"。

### 坑 4：没有文件系统，客户端必须自己维护目录树映射

Drive **不提供** WebDAV、不提供可被 `rclone mount` 直接使用的 POSIX 语义。同步器必须自己：

- 把本地目录树映射成远端 `parents` 关系
- 处理本地不存在但远端存在的空目录（Drive 不存空目录）
- 处理 Windows 保留名（`CON`、`PRN`、`AUX`、`NUL`、`COM1`...）、非法字符、路径长度 260 限制
- 处理**文件名大小写**：Drive 本身不区分大小写，`README.md` 和 `readme.md` 在 Drive 上会撞车

### 坑 5：移动端原生同步做不了

Google 官方的 Drive 手机客户端（iOS/Android）走的是 Google 的**私有 API**，不基于公开的 Drive API v3。第三方工具无法注册为手机系统的同步服务提供者。

结论：**手机端的自动同步是死路**。最多能做到"做一个手机 App 用 Drive API 主动拉取"，那是另一个量级的工程。

### 坑 6：与其他客户端互斥

如果 Google Drive 桌面版同时在同步同一个目录，它和你的工具会在同一份数据上产生并发修改，必然冲突。rclone 官方论坛明确建议：**不要同时用 Drive 桌面版和 rclone/bisync 操作同一个文件夹**。做实验时务必先关掉桌面版。

### 坑 7（好消息）：Google 的 revision 是免费保险

Drive 会为每次内容变更保存历史版本（30 天或 100 个版本，先到先算，且不占存储配额）。这意味着**即使同步器误删了文件，只要在 30 天内发现，都可以从回收站捞回来**。这是 Drive 相比裸 S3 的一个实质性安全优势。

## 4. 安装与上手方法（rclone 路线）

> 这是本文档的操作手册部分。照着做即可，无需阅读前面章节也能跑通。

### 4.1 前置：先建自己的 Google Cloud 项目（2026 年已变成必需）

**背景变化**：rclone 原本自带一个所有用户共用的 OAuth `client_id`，但官方已明确公告：

> "The shared client_id is being retired and will stop working during 2026. To avoid interruption you must create and use your own client_id, so creating one is now required rather than merely recommended."

也就是说，**现在配置时 `client_id` 留空会在后续失效，必须自己建**。而建 client_id 就需要 Google Cloud 项目——这一点对自研路线同样适用，两条路都要过这一关。

#### 建项目的完整步骤

1. 登录 [Google API Console](https://console.developers.google.com/)（用任意 Google 账号即可，不必是要同步的那个 Drive 账号）
2. 顶部选择或新建一个 project
3. 进入 **APIs & Services → Library**，搜索 "Drive"，启用 **Google Drive API**
4. 左侧点 **Credentials**（注意不是 "Create credentials"，那会打开向导）
5. 若没有 OAuth consent screen，点右上 **CONFIGURE CONSENT SCREEN → Get started**：
   - Application name：填 `rclone` 即可
   - User support email：填自己的邮箱
   - **Audience：选 `External`**
     （若你是 Google Workspace 用户可选 `Internal`，但那样 API 只能被本组织用户使用）
   - 填联系方式，同意条款，Create
6. 配置 scope（左侧 **Data Access → Add or remove scopes**，或直接手动粘贴）：

   ```
   https://www.googleapis.com/auth/docs
   https://www.googleapis.com/auth/drive
   https://www.googleapis.com/auth/drive.metadata.readonly
   ```

   加入表后点 **Update**，再点页面底部 **Save**
7. 左侧 **Audience** 页面 → 滚动到底 → **+ Add users**，把自己加为测试用户，保存
8. 左侧 **Overview** 页面 → 点 **Create OAuth client** → 应用类型选 **Desktop app** → Create
9. 记下生成的 **Client ID** 和 **Client Secret**
10. 回到 **Audience** 页面 → 点 **PUBLISH APP** 并确认
    - 若按钮是灰的：Google 现在要求先填 homepage URL 和 privacy policy URL。左侧 **Branding** 里两个 URL 填**同一个地址即可**（没有域名的话，用 GitHub Pages 之类的免费静态页即可），再填 **Authorized domains**，保存后 PUBLISH APP 就可用了
11. 把 Client ID / Secret 交给 rclone（见下节）

> ⚠️ **不要跳过第 10 步**。停在 Testing 状态会踩坑 1 的 7 天失效。
> 登录时出现的"Google 未验证此应用"警告屏是正常的（unverified + In production 的正常组合），点"高级 → 前往 xxx（不安全）"即可。

#### 备选路径

如果 Google API Console 的 consent screen 创建报 "The request failed because changes to one of the fields of the resource is not supported"，可以从 [Python Quickstart](https://developers.google.com/drive/api/v3/quickstart/python) 页面点 "Enable the Drive API" 按钮，会自动建好项目并给出 Client ID/Secret。

#### 为什么建议自建 client_id

除了上面的"必须"，还有一个理由：Google 对**每个 client_id** 有独立的每秒事务数限制（默认 10 transactions/second）。如果以后有多个服务共用 Google Drive，独立 client_id 可以避免互相拖累。

### 4.2 安装 rclone（四选一）

#### 方式 A：winget（Windows 推荐，最省事）

```powershell
winget install Rclone.Rclone
```

- 包 ID：`Rclone.Rclone`（实测本机可用，2026-10 时版本为 1.75.1）
- 安装后需**新开一个 PowerShell 窗口**才能用（PATH 刷新）
- 验证：`rclone version`

#### 方式 B：scoop

```powershell
scoop install rclone
```

- 优点：安装目录干净，卸载彻底，自带 PATH 配置
- 缺点：需要先装 scoop

#### 方式 C：chocolatey

```powershell
choco install rclone
```

- 优点：企业环境常用
- 缺点：包更新有时滞后

#### 方式 D：zip 便携版（完全不动系统）

1. 从 https://downloads.rclone.org/ 下载 `rclone-vX.Y.Z-windows-amd64.zip`
2. 解压到任意目录，例如 `D:\tools\rclone`
3. 把该目录下的 `rclone.exe` 所在路径加入 PATH，或直接用全路径调用：

```powershell
D:\tools\rclone\rclone.exe version
```

- 优点：不污染系统、可多版本共存、卸载即删目录
- 缺点：需手动更新；自更新可用 `rclone selfupdate`（便携版支持）

> **怎么选**：个人单机用选 A；多机或需要干净环境选 B；不想改系统选 D。

### 4.4 验证连通性

```powershell
rclone listremotes                       # 应看到 gdrive:
rclone about gdrive:                     # 看配额使用情况
rclone lsd gdrive:                       # 列出根目录
rclone lsf gdrive:bisync-test/           # 列文件名（扁平，脚本友好）
```

`rclone about` 的输出包含总配额、已用、回收站占用、以及 Gmail 等其他服务占用的空间——这是判断"还剩多少空间"最直接的命令。

### 4.5 常用参数备忘

| 参数 | 说明 |
|---|---|
| `--drive-skip-gdocs` | 让 Google 原生文档在列表中隐身。**实践强烈推荐**，否则会遭遇各种导出格式问题 |
| `--drive-pacer-min-sleep 10ms` | 两次 API 调用之间的最小间隔。默认值 100ms 偏保守，论坛实测调小能显著提速 |
| `--fast-list` | 把多次 `files.list` 合并成一个请求（单请求最多 50 个 parents）。rclone bisync **默认开启** |
| `--checkers 6` | 并发请求数 |
| `--drive-use-trash=false` | 默认 `true`，删除进回收站。改成 false 即永久删除（危险） |
| `--drive-root-folder-id` | 限定操作的根目录 |

`--fast-list` 的实测收益（rclone 官方数据）：

| 目录规模 | 不用 fast-list | 用 fast-list |
|---|---|---|
| 220 目录 / 700 文件 | 38 秒 | 10 秒 |
| 10600 目录 / 39000 文件 | 22 分 05 秒 | **58 秒** |

⚠️ 但 fast-list 与"空目录多"的 Drive 账户存在已知冲突（Google 的 `(A in parents) or (B in parents)` 查询有时会返回空）。rclone 的 bisync 文档对此的当前建议是：**如果你的 Drive 里空目录很多，给所有 bisync 命令加上 `--disable ListR` 关掉 fast-list**。

### 4.6 定时执行（Windows）

跑通之后，用"任务计划程序"每 N 分钟执行一次 bisync 即可。注意工作目录必须是 bisync 的 workdir 所在盘/目录（Windows 下为 `C:\Users\<用户名>\AppData\Local\rclone\bisync`），且**同一时间只能有一个实例**（bisync 用锁文件保证，崩溃后锁可能残留，用 `--max-lock` 设置过期时间）。

### 5.4 推荐的完整参数组合

```
rclone bisync gdrive:bisync-test/ ./local-test ^
  --create-empty-src-dirs ^
  --compare size,modtime,checksum ^
  --slow-hash-sync-only ^
  --resilient ^
  --conflict-resolve newer ^
  --drive-skip-gdocs ^
  --drive-pacer-min-sleep 10ms ^
  --fix-case ^
  -MvP
```

各参数含义：

| 参数 | 作用 |
|---|---|
| `--create-empty-src-dirs` | 同步空目录的创建与删除（Drive 不存空目录，必须显式处理） |
| `--compare size,modtime,checksum` | 默认只比 `size,modtime`；加入 checksum 更准，且**在 Drive 端几乎零成本**（Drive 自带 md5） |
| `--slow-hash-sync-only` | 只在必要时才算本地 hash，避免本地大量小文件反复计算 |
| `--resilient` | 出错后允许下轮自动续跑，而不是直接锁死要求人工 `--resync` |
| `--recover` | 意外中断后自动从上次备份快照恢复（建议与 `--resilient` 同用） |
| `--conflict-resolve newer` | 有明确胜负时自动按新旧裁决（无胜负时仍保留双份） |
| `--backup-dir1/2` | 覆盖/删除前先备份到同一 remote 的备份目录 |
| `--max-delete 50%` | 默认安全阀：一轮要删超过一半文件就中止 |
| `-MvP` | 详细日志 + 可交互确认 + 进度条 |

## 6. 原理剖析：同步算法到底难在哪

### 6.1 三方合并模型

同步的本质不是"两边比一下"，而是**三方比较**。只有基线（上次同步时的状态）才能告诉你"这一侧的变化是新产生的，还是上次就存在"。

```
        基线 (上次同步快照)
              │
     ┌────────┴────────┐
     │                 │
  本地 Path1        云端 Path2
  (当前状态)        (当前状态)
     │                 │
     └────────┬────────┘
              ↓
        三方对比推导
              ↓
  New / Newer / Older / Deleted / Conflict
              ↓
        生成操作计划并执行
```

状态推导规则（简化）：

| 基线 | 本地 | 云端 | 判定 | 动作 |
|---|---|---|---|---|
| 无 | 有 | 无 | New(local) | 上传 |
| 无 | 无 | 有 | New(remote) | 下载 |
| A | A≠B | A | Newer(local) | 上传覆盖 |
| A | A | A≠B | Newer(remote) | 下载覆盖 |
| A | A≠B | A≠B（内容与本地不同） | **Conflict** | 保留双份 / 按策略裁决 |
| A | 无 | A | Deleted(local) | 删除远端 |
| A | A | 无 | Deleted(remote) | 删除本地（**最危险的一类**） |
| A | B | B | 重命名或两端一致 | 视内容哈希而定 |

**为什么必须三方而不是两方**：两方比较无法区分"文件 A 被改了"和"文件 A 从 A 变成了 B"。基线是唯一的信息来源。这也是 `bisync` 强制要求先 `--resync` 建立基线的原因——没有基线，三方合并退化成两方比较，结果不可信。

### 6.2 rclone bisync 的设计要点

- **状态存储**：每次运行后保存 Path1 和 Path2 的 listing 快照，作为下次的基线。workdir 在 Windows 下是 `C:\Users\<用户名>\AppData\Local\rclone\bisync`
- **`--resync` 是逃生门**：任何检测到状态不可信的情况（工作目录被删、上轮非正常中断、基线损坏），bisync 都会拒绝运行并要求先 `--resync`。`--resync` 会重建基线并按 `--resync-mode` 决定谁赢（默认 path1 无条件赢）
- **`--check-sync`（默认开启）**：运行结束后比对两边的 listing 快照是否一致，防止"以为同步了其实没同步"。但它**只检查快照，不检查真实文件**
- **`--resilient` + `--recover`**：把"出错就锁死"改成"下轮自动续跑"。配合 `--max-lock` 处理崩溃残留的锁文件
- **`--max-delete 50%`（默认值）**：一道重要的数据保险。一轮内要删除的文件超过总数的 50% 就中止

源码入口：`fs/sync/bisync/bisync.go`。这是理解三方合并最好的材料。

### 6.3 Drive 的增量方案 vs rclone 的全量方案

**rclone 每次同步都做全量 `files.list`。** 对于文件少的个人账户无所谓，但对于几万文件的账户：

- 全量 list 每次都是 O(文件数) 的 API 调用
- 列目录消耗 100 units/次，是读（5 units）的 20 倍
- 用 `--fast-list` 合并请求能缓解（39000 文件从 22 分钟降到 58 秒），但本质上仍是全量

**Drive 提供了 `changes` feed，这是 rclone 目前没有利用的能力**：

```
首次：changes.getStartPageToken  →  存下 startPageToken
之后：changes.list(pageToken=上次的)  →  只返回"自上次以来变化过的条目"
        返回 nextPageToken → 翻页
        返回 newStartPageToken → 说明已到最新，存下来供下次使用
```

- token **永不过期**，可以安全持久化
- 支持 `includeRemoved` / `restrictToMyDrive` / `spaces=drive`（含共享云端硬盘）
- 每页最多 1000 条
- 还可以用 `changes.watch` 订阅 webhook，收到推送后再去拉 changes——但这需要一个公网 HTTPS 回调地址，个人机器通常没有

**这就是自研能比 rclone 强的地方**：稳态同步的开销从 O(文件数) 降到 O(变化数)。对于"文件多但每天只改几个"的典型场景，节省巨大。

代价是需要额外处理 pageToken 的持久化、以及 token 失效（410 / invalid page token）后如何优雅地重建基线。

## 7. 自研路线评估

### 7.1 什么时候才值得自研

| 值得 | 不值得 |
|---|---|
| 学习目的（本次即是） | 只是想要个能用的同步器 |
| 需要 rclone 没有的定制逻辑（如特殊过滤规则、加密、特定触发时机） | 只是嫌官方客户端不好用 |
| 文件数量极大，需要 `changes` feed 增量省配额 | 文件量在几千以内 |
| 需要把同步能力嵌进已有的 Python 工具链 | 需要立刻可靠的方案 |

### 7.2 成本估计

| 部分 | 难度 | 说明 |
|---|---|---|
| OAuth 认证与 token 管理 | 中 | 坑 1 全部要自己处理 |
| Drive API 封装（CRUD + 限流退避） | 低 | 官方 SDK 现成 |
| 三方合并引擎 | **高** | 真正的难点，rclone 的状态机有数百行 |
| 删除墓碑与重命名检测 | **高** | 边界情况极多 |
| 本地文件监听（watchdog） | 低 | 有成熟库 |
| 断点恢复与状态持久化 | 中 | SQLite 事务设计 |

**保守估计**：一个可用的最小实现需要几天；做到生产级（各种异常恢复、冲突策略、无人值守）需要数周。这与 rclone 已投入的开发量差距很大。

### 7.3 模块草图

```
config.py          OAuth 配置、本地/远端根路径、过滤规则、轮询间隔
auth.py            OAuth2 installed-app 流程、token 持久化与自动续期、失效检测与重新授权
drive_client.py    Drive API 薄封装：list / changes / upload(resumable) / download / update / delete
                   + 429/403 指数退避重试（关键：不重试会直接触发限流）
state_db.py        SQLite 状态库：
                     - file_id ↔ 本地相对路径、size、mtime、md5
                     - 墓碑（已删除记录，用于删除传播）
                     - changes feed 的 pageToken
scanner.py         本地目录扫描（watchdog 事件防抖，或定时轮询）
sync_engine.py     三方合并（基线 vs 本地 vs 远端）→ 生成操作计划 → 执行
                   ★ 本项目的核心
watcher.py         watchdog 事件 → 聚合防抖 → 触发同步
cli.py             init / scan / sync --dry-run / status / reauth
```

需要自己拍板的设计点：

| 设计点 | 备选方案 | 取舍 |
|---|---|---|
| 变更检测 | `changes` feed（增量，省请求）/ 全量 list（简单，同 rclone） | 文件多选前者 |
| 状态存储 | SQLite（结构化、支持事务、便于查询） | 无明显替代 |
| 冲突策略 | 保留双份 + 命名规则（Nextcloud 式）/ 按 mtime 选一 / 按内容相似度合并（合并最复杂） | **本次需求：保留双份** |
| 墓碑保留期 | 永久 / 固定天数 | 永久则状态库只增不减 |
| 重命名检测 | hash + size 匹配 / 不检测（退化为删+建） | 不检测会导致删除-新建传播，触发大删除安全阀 |
| 上传分块 | resumable，256KB~8MB 分片 | Drive 侧上限与 rclone 一致（默认 8MiB） |
| 触发方式 | 定时轮询 / watchdog | Drive 侧无论如何都要轮询（除非有公网地址用 webhook） |

### 7.4 自研必踩的坑汇总

1. OAuth token 7 天失效（见坑 1）—— PUBLISH APP 是必须的
2. `changes` pageToken 失效后的基线重建
3. 429/403 限流的指数退避，**不能漏重试**
4. Google 原生文档无 md5、需 export、有损
5. Drive 不存空目录
6. Drive 大小写不敏感
7. Windows 保留文件名与非法字符
8. 半成品文件（正在被写入）需要防抖，`--max-age` 是简单解法
9. Drive 回收站是重要的安全网，删除时应默认保留
10. 与 Drive 桌面版的互斥

## 8. 选型对比

| 方案 | 上手成本 | 可靠性 | 学习价值 | 移动端 | 增量支持 | 适用场景 |
|---|---|---|---|---|---|---|
| **rclone bisync** | 低（0.5 小时） | 高（久经考验，但需懂规则） | **高**（源码是最佳教材） | ❌ | ❌（全量 list） | **本次推荐**：学习 + 实用两得 |
| **Google Drive 桌面版镜像模式** | 极低（10 分钟） | 最高（官方维护） | 低 | ✅ | ✅（官方实现） | 只想用，不关心原理 |
| **自研 Python 同步器** | 高（数天~数周） | 初期低 | **最高** | ❌ | ✅（changes feed） | 学习 / 有定制需求 |
| **rclone mount** | 低 | 中（VFS 缓存坑多） | 中 | ❌ | — | 想把 Drive 当盘用 |
| **Syncthing** | 低 | 高 | — | ✅ | ✅（P2P） | 想要跨设备同步且不想有云服务商 |
| **自建 Nextcloud** | 很高（要服务器+域名+HTTPS） | 高 | 低 | ✅ | ✅ | 想要完整可控的私有云 |
| **GitHub/OneDrive/Dropbox API 同步** | — | — | — | ✅ | ✅ | 微软系生态用户 |

### 推荐结论

**分两步走，不要跳过第一步：**

**第一步（今天就能做完）**：装 rclone，按第 4 节配好 remote，按第 5 节跑一遍实验。目标是**把坑全部撞一遍**并留下记录文档。这一步同时满足"能用"和"学 API"两个目的。

**第二步（做不做都行）**：读 `fs/sync/bisync/bisync.go`。如果读完觉得"我想要 `changes` feed 的增量版本"，那时的自研是有明确差异化理由的，不是为了重复造轮子。

**如果只是想要一个能用的同步器**——直接用 rclone bisync，或者干脆用 Drive 桌面版的镜像模式（本地保留完整明文副本，官方客户端维护同步逻辑，最省心）。
