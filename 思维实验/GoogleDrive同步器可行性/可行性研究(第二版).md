## 0. 文档说明

### 0.1 与第一版的关系

第一版是一次"泛问"——**Google Drive 能不能通过 API 访问？能不能用它做个人同步器？** 结论是"能"，并给出了 API 能力清单、配额说明、关键限制、rclone 的安装配置与验证实验步骤。

第一版写作时还没有明确的实际场景，因此模型部分是通用的。本版本基于真实约束重新推导：

- 4 台设备（公司台式 + 公司笔记本 + 家里台式 + 家里笔记本）
- 需要同步的是"很常用的文件"，总量 **< 5 GB**
- 当前用租来的云服务器跑 Nextcloud，成本高且慢
- **人工触发同步完全可接受**，希望有图形界面
- 需要保留改动历史，具备单文件恢复能力
- 目标：用一个轻量自研工具替代 Nextcloud

### 0.4 数字来源纪律

**本文档所有具体数字**（免费额度、价格、配额、token 失效天数、上传限制、速率估算）**必须**满足以下之一：

1. **附官方来源链接**（优先官网/官方文档，其次 rclone 官方后端文档）
2. **显式标注"待核实"或"个人观察，非官方依据"**

**为什么立这条规矩**：v2 初稿把 pCloud 的**付费档**（€199.99 的 500 GB 终身版）误写为"免费额度"，用户实际注册只拿到 2 GB才发现。根因是**凭印象写数字、未查证、未标注来源**。技术文档里的一个错误数字足以让使用者做出错误的选型决策。

**自查方式**：读到任何数字时，向上找它附近的脚注或链接。找不到链接且没有"待核实"标记的，视为可疑。

### 0.5 hub 可达性硬前提（第 0 号依赖）

**前提**：4 台设备均在中国内地；每台设备都有**自己的、稳定的代理**访问 Google API。

这条是全文的地基，重要性高于所有技术细节：

| 如果前提被推翻 | 后果 | 应对 |
|---|---|---|
| 某台设备的代理挂了/变慢 | 该设备无法同步，其余设备不受影响 | 失败模式见 8.10；状态可从零重建，见 5.6 |
| 代理长期不可用 | **hub 选型翻转**：OneDrive 上位（微软服务在内地可达性显著好于 Google），其余设计不变（后端差异见 4.5、`backend_caps` 见 8.3） | 本文档 4.4–4.5 的对比表即为翻盘准备 |

**安全性澄清**：代理不构成 token 泄露面。rclone 与 Google 之间全程 HTTPS，refresh_token 与文件内容都不以明文经过代理；代理能看到的只有"连着 googleapis.com"这一事实。真正的风险是**可用性**而非机密性。

**带宽澄清**：同步速度 = min(代理带宽, 本地上行, Drive 端)。单轮耗时分首轮与 delta 轮，见 6.2。自行实测代理带宽的方法同 4.6 F 节（`rclone copy` 一个小文件观察 MB/s）。

## 1. 结论摘要

### 1.1 可行性判定

| 问题 | 结论 |
|---|---|
| Google Drive 能否通过 API 访问？ | **能。** 公开、免费、Tier-1 支持的 REST API |
| 能否用它做多设备文件同步？ | **能。** Drive 本身就是服务器权威模型，天然适合做 hub |
| 能否替代 Nextcloud？ | **能。** 对"4 设备 + <5GB + 人工触发 + 单文件恢复"这个场景，需求远小于 Nextcloud 的完整功能集 |
| 该怎么实现？ | **rclone 作传输层 + 自研同步引擎 + 本地 Web GUI** |
| 现成方案够用吗？ | `rclone bisync` 功能上够，但**没有 GUI、备份粒度不可控、单文件恢复需手工翻目录**，与需求有落差 |

### 1.2 最终推荐方案（一句话）

> **Hub-and-Spoke 模型：4 台设备都只和 Google Drive 对话；每次同步由人在 Web GUI 上点两下（扫描 → 执行）；引擎自研三方比对，rclone 只负责传输；所有覆盖/删除前自动备份，备份可通过 GUI 搜索定位，恢复动作全部人工。**

### 1.3 这个方案的三个关键判断

1. **< 5 GB 意味着可以做全量扫描，不需要增量优化。** 每轮 1-3 分钟，所有状态机复杂度大幅下降。
2. **人工触发消除了同步器最难的 80% 复杂度**——文件监听、防抖、守护进程、崩溃一致状态，全部不需要。
3. **真正剩下的复杂度只有"4 个设备 ↔ 1 个权威"的并发问题**，以及"覆盖前留一份"的保护逻辑。这两个都可以做得很小。

## 2. Drive API 能力与限制

### 2.1 能力对照：同步器需要什么 vs Drive API 有什么

| 同步器需求 | Drive API 对应能力 | 满足度 |
|---|---|---|
| 列目录 / 全量扫描 | `files.list`，支持 `q` 查询、`pageToken`、`fields` 裁剪、`spaces=drive` | ✅ 完整 |
| **增量变更检测** | `changes.getStartPageToken` + `changes.list`，token **永不过期** | ✅ 完整，官方同步方案 |
| 变化推送 | `changes.watch` / `files.watch` | ⚠️ 需公网 HTTPS 回调，个人场景退化为轮询 |
| 上传（断点续传） | resumable upload session（256KB 最小分片） | ✅ 完整 |
| 完整性校验 | `md5Checksum`（部分文件另有 sha1/sha256）；原生文档需 `files.export` | ✅（原生文档除外） |
| 删除 / 回收站 | `files.delete` 默认进回收站（30 天），`trashed` 字段可查 | ✅ 完整 |
| 重命名 | `files.update` 改 `name` | ✅ |
| 移动（换父目录） | My Drive 下可行；共享云端硬盘可原子修改 | ⚠️ My Drive 下需模拟 |
| 版本历史 | `revisions`（30 天或 100 版，不占存储配额） | ✅ 赠送 |
| 权限管理 | `permissions` | ✅ 完整 |
| 共享云端硬盘 | `drives`（原 Team Drives） | ✅ 完整 |

### 2.2 配额（2026-05-01 起改版）

Drive API 现按"配额单位（quota units）"计费：

| 限额类型 | 数值 |
|---|---|
| 每分钟 / 每项目 | 1,000,000 units |
| 每分钟 / 每用户 / 每项目 | 325,000 units |
| 每 24 小时 / 每项目（开始计费阈值） | 400,000,000 units |

单次请求消耗：

| 操作 | units |
|---|---|
| 读（`files.get`） | 5 |
| **列（`files.list`）** | **100** |
| 下载（`files.download`） | 200 |
| 改（`files.update`） | 50 |
| 其他（如 `files.generateIds`） | 5 |

**配额消耗与文件数量成正比，与体积无关。** 这是自研同步器的主要瓶颈，也是增量方案的动机所在——但见第 5.5 节，本场景不需要增量。

其他硬限制：

- Workspace 用户每天在 My Drive 与共享云端硬盘之间只能上传 **750 GB**（复制计入），单文件上限 **5 TB**，单次复制上限 750 GB
- 目前所有标准使用**不额外收费**，官方声明 2026 年内会对超额部分开始计费（提前 90 天通知）
- 每个 OAuth client_id 有独立的每秒事务数限制，**默认 10 transactions/second**（这是建议自建 client_id 的原因之一）

### 2.3 Drive 的"原生文档"是个坑

Google Docs / Sheets / Slides 在 Drive 里不是普通文件：没有原始字节，下载必须走 `files.export` 按格式导出。影响：

- **没有 `md5Checksum`**，校验逻辑必须特判
- 导出是**有损**的（xlsx → csv 会掉格式）
- rclone 用 `--drive-skip-gdocs` 让原生文档在列表里彻底隐身，这是实践推荐做法

**本方案的对策**：只同步普通文件，原生文档一律跳过。问题即消失。

## 3. 关键限制与坑

这一章是第一版内容的保留，是所有坑中最可能让项目失败的 7 条。

### 坑 1：OAuth refresh token 7 天失效 ⚠️ 最容易踩

**现象**：程序跑得好好的，一周后突然全部 API 调用失败，报 `invalid_grant: Token has been expired or revoked`。

**原因**：Google Cloud 项目的 OAuth consent screen 同时满足三个条件时：
1. 用户类型是 **External**
2. 发布状态是 **Testing**
3. 请求的 scope 不在基础集合（`name`/`email`/`profile`）内 —— **Drive 不在豁免范围内**

refresh token **只有 7 天有效期**。实践中"External + Testing" 基本等于"一周失效一次"。

**解法**：把 publishing status 从 `Testing` 切成 **`In production`**。

**关键澄清**（很多教程混淆这两个概念）：

| 轴 | 是什么 | 影响 | 耗时 |
|---|---|---|---|
| **发布状态**（Testing ↔ In production） | 你自己能点的开关 | **refresh token 寿命**、是否需要测试用户白名单 | 即时 |
| **审核验证**（unverified ↔ verified） | Google 人工审查 | 登录警告屏、用户数上限、能否向陌生人开放 restricted scope | 数天到数周 |

**应用可以处于「In production + unverified」状态**。Google 明确豁免了"个人使用（少于 100 用户）"类应用的强制验证。登录时点一下"高级 → 前往 xxx（不安全）"即可。

其他会导致 token 失效（非定时）的情况：用户主动撤销授权、连续 6 个月未使用、修改 scope、超过活跃 token 数上限（约 50）、改密码/安全事件。

### 坑 2：scope 选择

| scope | 能力 | 验证负担 |
|---|---|---|
| `drive` | 访问所有文件（同步器必须用） | restricted scope。公开分发需 CASA 第三方安全评估；单用户自用不受影响 |
| `drive.file` | 只能访问本应用创建的文件 | 轻。但手动上传的文件 rclone 完全看不到，**做通用同步器不可用** |
| `drive.appfolder` | 应用专属隐藏目录 | 轻。但只能看到一个隔离目录 |

本方案用 `drive`，接受坑 1 的全部约束。

### 坑 3：没有服务端 move

Drive API **没有**"移动"的原子操作：

- 改名 = `files.update` 改 `name`（原子，可行）
- 换父目录 = My Drive 下一次 `files.update` 给出新 parents 列表（可行，因为 My Drive 里一个文件只有一个 parent）；**共享云端硬盘**里文件可有多个 parent，模拟移动会经历"短暂存在于两处"的中间态

对本方案的影响：rename 检测（避免"删除+重建"浪费带宽）无法用服务端 move 实现。可选策略：不做 rename 检测（接受少量浪费），或本地做 hash+size 匹配。

### 坑 4：没有文件系统，客户端必须维护目录树映射

Drive **不提供** WebDAV、不提供可被 `rclone mount` 直接使用的 POSIX 语义。同步器必须自己：

- 把本地目录树映射成远端 `parents` 关系
- 处理本地有但远端没有的**空目录**（Drive 不存空目录）
- 处理 Windows 保留名（`CON`/`PRN`/`AUX`/`NUL`/`COM1`...）、非法字符、260 字符路径限制
- 处理**文件名大小写**：Drive 不区分大小写，`README.md` 和 `readme.md` 会撞车

**从"坑"变"策略"**（扫描期检测，实现时照此执行）：

| 情况 | 策略 | 说明 |
|---|---|---|
| 本地空目录 | **不同步**，原样留在本地 | planner 天然是 files-only（`lsjson --files-only` + 本地只收文件）。远端删除永不传来。这是**已知限制**，在 UI"关于"里写明，不做 sentinel 文件之类的补丁 |
| 本地大小写冲突（`README.md` 与 `readme.md` 同目录共存） | **整轮拒绝**并列出冲突项，要求用户改名 | Drive 大小写不敏感，硬传必有一个被静默覆盖。Windows 本地磁盘实际大小写不敏感，此情况多为从 Linux/网盘拷入，少见但要防 |
| Windows 保留名 / 非法字符（`:` `*` `?` 等不可能出现在本地名，但全角变体可能） / 超长路径（>259 字符） | **跳过该项**，在扫描清单标注"skipped-unsupported"，其余文件正常同步 | 不要为了个别文件中断整轮。历史目录用镜像路径，同名风险已被时间戳前缀化解 |

### 坑 5：移动端原生同步做不了

Google 官方 Drive 手机客户端走**私有 API**，不基于公开的 Drive API v3。第三方工具无法注册为手机系统同步服务。

结论：**手机端自动同步是死路**。本方案的定位是"电脑之间同步"，手机用官方客户端看即可。

### 坑 6：与其他客户端互斥

Google Drive 桌面版和自研工具会在同一份数据上并发修改，必然冲突。**4 台设备上都必须关闭 Drive 桌面版**（或至少不挂载同步目录）。工具启动时应检测 `GoogleDriveFS` 进程并拒绝运行。

### 坑 7（好消息）：Drive 的 revisions 是免费保险

Drive 为每次内容变更保存历史版本（30 天或 100 版，先到先算，不占存储配额）。即使工具误删了文件，30 天内可从回收站/版本历史捞回。

**但要注意**：revisions 只覆盖**云端侧**的变化。本地文件被覆盖前的内容，Drive 完全不知道——那必须靠本地备份。见第 7 章。

## 4. rclone 调研

### 4.1 rclone 在本方案中的角色

**重要定位澄清**：本方案中 rclone 不是"同步引擎"，而是**传输层**。它只负责三件事：

| 用途 | 命令 |
|---|---|
| 列目录（拿到结构化清单） | `rclone lsjson` |
| 传输文件 | `rclone copyto` / `rclone move` |
| 删除文件 | `rclone deletefile` |

所有"判定"逻辑（哪些要传、哪些冲突、哪些要备份）都由自研引擎负责。

**为什么不把 rclone 当黑盒**：本方案的核心需求是 GUI 扫描清单、冲突检测、备份策略。`rclone sync --dry-run` 只有人类可读的文本输出，解析它很脆（格式随版本变化、无稳定契约）。用 `lsjson` 拿结构化数据，判定逻辑自持，才能支撑 GUI。

**白拿的好处**：rclone 支持的后端（见 4.4）全部自动可用，换云盘只改配置不改代码。**多网盘并行的架构支持见 4.7；对象存储（S3/B2）的国内可用性专项评估见 4.6。**

### 4.2 安装：前置必须先建 Google Cloud 项目

**2026 年的变化（这是第一版之后才明确的）**：rclone 原本自带一个所有用户共用的 OAuth `client_id`，但官方已公告：

> "The shared client_id is being retired and will stop working during 2026. To avoid interruption you must create and use your own client_id, so creating one is now required rather than merely recommended."

也就是说，**现在配置时 `client_id` 留空会在后续失效，必须自己建**。而建 client_id 就需要 Google Cloud 项目——这一点对"直接用 rclone"和"自研工具"两条路都适用。

#### 建项目的完整步骤

1. 登录 [Google API Console](https://console.developers.google.com/)（任意 Google 账号，不必是要同步的那个 Drive 账号）
2. 选择或新建一个 project
3. **APIs & Services → Library**，搜索 "Drive"，启用 **Google Drive API**
4. 左侧点 **Credentials**（注意不是 "Create credentials"，那会打开向导）
5. 若无 OAuth consent screen，点右上 **CONFIGURE CONSENT SCREEN → Get started**：
   - Application name：`rclone` 即可
   - User support email：自己的邮箱
   - **Audience：选 `External`**（Google Workspace 用户可选 `Internal`，但那样 API 只能被本组织使用）
   - 填联系方式，同意条款，Create
6. 配置 scope（左侧 **Data Access → Add or remove scopes**，或手动粘贴）：

   ```

   ```

   加入表后点 **Update**，再点页面底部 **Save**
7. 左侧 **Audience** → 滚动到底 → **+ Add users**，把自己加为测试用户，保存

若 consent screen 创建报 "The request failed because changes to one of the fields of the resource is not supported"，可从 [Python Quickstart](https://developers.google.com/drive/api/v3/quickstart/python) 页面点 "Enable the Drive API"，会自动建项目并给出 Client ID/Secret。

#### 为什么建议自建 client_id

除了"必须"，还有一个理由：Google 对**每个 client_id** 有独立的每秒事务数限制（默认 10 transactions/second）。4 台设备共用同一项目时，独立 client_id 可以避免互相拖累（本方案 4 台设备可共用一个 client_id，但仍建议自建以便将来区分）。

### 4.4 rclone 支持的网盘，以及"能不能用来同步"

#### 同步需要的能力（分层，不是单一能力）

| 能力 | 为什么重要 | 缺失的后果 |
|---|---|---|
| **可写的 mtime** | 同步的一切判断建立在时间戳上 | **同步不可用**（最重要） |
| **内容 hash** | 区分"同一文件"与"大小相同的两个文件" | 退化为 size+mtime，易误判 |
| 服务端 copy/move | 改名/移动几乎零成本 | 退化为下载+上传，rename 检测失效 |
| 增量变更 feed | 只取变化项而非全量扫描 | 慢，耗配额（**最稀有**） |

rclone 官方有 **Tier 分级**，可直接当"能不能用于同步"的筛选器：

| Tier | 含义 |
|---|---|
| **Tier 1** | Core，生产级核心 |
| Tier 2 | Stable，稳定，有小缺口 |
| Tier 3 | Supported，能用但有已知问题 |
| Tier 4 | Experimental，谨慎使用 |
| Tier 5 | Deprecated，不再维护 |

#### Tier 1 + 有 hash + mtime 可写（放心用）

| 后端 | Hash | mtime | 备注 |
|---|---|---|---|
| **Google Drive** | md5, sha1, sha256 | R/W | **唯一有增量 changes feed 的** |
| **OneDrive** | quickxor | R/W | |
| **Dropbox** | dropbox hash | R/W | |
| **Box** | sha1 | R/W | |
| **pCloud** | sha1, sha256 | R/W | |
| **Yandex** | md5 | R/W | |
| **B2** | sha1 | R/W | |
| **S3** | md5 | R/W | 含各家兼容 S3 |
| **WebDAV** | sha1 | R/W | 见下方中文网盘 |
| **Filen** | blake3 | R/W | 加密云盘 |

**Tier 1 但无 hash**（能用，只靠 size+mtime）：Storj、Shade、PikPak（有 md5）

**Tier 1 但完整性只靠 mtime**（同步风险较高）：FTP、SMB

**不建议用于同步**：Mega（Tier 2，无 hash，mtime 只读）、Seafile / Sugarsync / Zoho（Tier 3）

#### 中文网盘：百度 / 阿里 / 夸克

**rclone 没有原生后端**。标准做法是套一层 **OpenList**（AList 的后继）：

```
夸克网盘 ─┐
百度网盘 ─┤
阿里云盘 ─┼→ OpenList ─WebDAV→ rclone ─→ 工具
天翼云盘 ─┤
123pan  ─┘
```

OpenList 支持的网盘种类很多（阿里云盘、百度、夸克、天翼、123pan、和彩云、迅雷、PikPak 等），统一暴露成 WebDAV。

**代价**：多一跳代理，WebDAV 层能力有折扣——OpenList 的 WebDAV 对部分存储**不支持复制操作**（GoogleDrive、123pan、FTP、SFTP、PikPak、S3 等），会让 rclone 的服务端 copy 优化和 rename 检测失效；另外 mtime 可靠性不如原生后端。**能用，但比原生后端差一档。**

#### 三个必须专门处理的差异

**① hash 算法各不相同——本地必须算同样的算法**

这是多网盘支持最容易做错的地方。planner 用 hash 判断"内容是否相同"，如果本地算 md5 而远端报 quickxor，**每一个文件都会被判定为"两边都改了"→ 全量冲突**。

| 后端 | 必须本地计算的算法 |
|---|---|
| Google Drive / S3 / B2 / Azure Blob | md5 |
| OneDrive | **QuickXorHash**（Microsoft 私有变体，不是标准 sha1） |
| Dropbox | **DropboxHash**（私有格式） |
| pCloud | sha1 或 sha256 |
| Box / WebDAV | sha1 |

**推荐做法：本地 hash 也交给 rclone 算**，与远端同源，算法天然对齐，不需要自己实现 QuickXorHash / DropboxHash。已核实 rclone 官方 overview 表：**local 后端 Hash = ALL**（即 rclone 实现的所有算法都支持，含 quickxor / dropbox hash），推荐做法的可行性有官方依据。

但"一条命令全算"与 8.4 的"懒计算"是两套策略，此处**定稿为二选一**：

| 方案 | 命令 | 耗时 | 适用 |
|---|---|---|---|
| **甲（默认）** | 本地扫描**不带** `--hash`（只拿 size+mtime）；仅对"疑似变更"文件批量 `rclone hashsum md5 <file1> <file2> ...` | 常规轮约 0.5–2 秒（90%+ 文件 size+mtime 未变，零 hash 开销） | 日常同步 |
| 乙 | `rclone lsjson -R --files-only --hash --hash-type md5 .\local\` 一次全算 | 5 GB 约 10–30 秒 | 首轮建库、或你不在乎每次多等半分钟 |

方案甲的真懒计算成立的原因：`rclone hashsum` 支持一次传入多个路径，只算需要算的文件。远端侧不变——`lsjson --hash` 拿到的远端 hash 是网盘**已存储**的值，对 Drive/B2/S3 零成本，对 OneDrive/Dropbox 是服务端计算好直接返回，都不增加成本。

**为什么默认甲**：本工具是人工触发、每次同步都看清单，delta 轮里"没动过的文件"占绝大多数；为它们付 10–30 秒 hash 是纯浪费。若将来文件数上万且 delta 也变小，切乙无任何改造成本（同一条 rclone）。

**② OneDrive 的 mtime 只有秒精度，文件名限制比 Drive 更严**

- 秒精度对同步够用（planner 的容差本就是 2 秒），但**同一秒内改两次会漏检**，可接受
- OneDrive 会把 `" * : < > ? \ |` 这些字符**替换成全角等价字符**（`?` → `？`）。后果：本地文件 `报告:最终.md` 传到 OneDrive 变成 `报告：最终.md`，下次扫描发现名字对不上 → **永远判定为"已删除+新增"，无限循环重传**

对策：本地扫描阶段就用同样的规则归一化文件名再比对；或在 ignore 规则里排除含这些字符的文件。

**③ OneDrive 的版本历史占存储配额，且改一次 mtime 就多一个版本**

- OneDrive 每次内容变更都创建新版本，**计入用户配额**（Drive 不计）
- rclone 上传后再设 mtime 会**再创建一个版本** → 单次同步占 2 份空间
- rclone 默认**关闭** `--onedrive-upload-cutoff`（分片上传）正是为了规避这个问题。**用 OneDrive 建议显式设置 `--onedrive-upload-cutoff 10Mi`**，让大文件走分片上传以避免多版本

**④ Box 免费版的两个硬伤：250 MB 单文件上限 + 仅 1 个版本历史**

- [官方 pricing](https://www.box.com/pricing/individual)：Individual（免费）= 10 GB 存储，**单文件上传上限 250 MB**，**版本历史仅 1 个版本**
- 250 MB 会挡住大文件（本方案若同步含视频/大压缩包则直接不可用）
- 仅 1 个版本意味着"覆盖前的内容"在云端完全不存在，第 7.3 节的"三道保险"退化为两道（本地备份 + 回收站）

**⑤ Yandex 的封锁风险与上传限制**

- [官方说明](https://360.yandex.com/premium-plans/)：免费额度用尽后访问受限，**若不处理，44 天后 Yandex Disk 完全封锁**
- [官方 Disk 页](https://360.yandex.com/disk/)：**100 GB 单文件上传上限和更高月上传限额仅对 2025-11-13 后激活 Pro 计划的用户开放**，免费版无此权益
- ⚠️ 文档此前写的"有地区访问问题"是**个人观察，未找到官方依据**，不应作为选型理由。若在国内实测访问明显异常，可自行补记

#### 各网盘的定位建议

| 网盘 | 适合做 hub 吗 | 说明 |
|---|---|---|
| **Google Drive** | ✅ 最推荐 | 唯一有完整增量 feed；版本历史不占配额；15 GB 免费够 5 GB 场景；**但内地可达性依赖稳定代理，见 0.5** |
| **OneDrive** | ✅ 可用；**0.5 前提不成立时的默认翻转目标** | 微软生态内最省心、内地无代理依赖；注意 90 天 token 失效、文件名全角替换、版本占配额 |
| **Dropbox** | ✅ 可用 | 同步质量好，但 2 GB 免费额度偏小 |
| **pCloud** | ⚠️ 备选（双写目标） | 免费 7–10 GB，有版本历史与回收站；但**服务器仅瑞士/美国，无亚洲节点**，与 4.6 节 B2 同一硬伤 |
| Box | ❌ 不推荐 | 免费版**单文件 250 MB 上限 + 仅 1 个版本历史**，与本方案需求冲突 |
| Yandex | ❌ 不推荐 | 免费版无大文件上传上限；额度用尽 44 天封锁；国内访问情况需自行实测 |
| **S3 / B2** | ⚠️ 技术最优但国内不推荐 | 技术上最好（大小写敏感、hash 可靠、mtime 精确），但**无免费额度、无回收站无版本历史**，且**无亚洲节点**——详见 4.6 |
| **Syncthing** | ✅ 另一条路 | 纯 P2P，无云服务商。但要设备常在线 |
| 中文网盘(OpenList) | ⚠️ 兜底方案 | 额度大/便宜。但多一跳代理、无 hash 保证、无版本历史 |

**一个反直觉的建议**：如果纯粹从"同步质量"看，**S3/B2 技术上优于 Google Drive**——它们大小写敏感（避免了 `README.md`/`readme.md` 撞车）、hash 可靠、mtime 精确。Drive 的原生文档、无 md5、需 special-case 的坑，S3 都没有。代价是要花钱（对象存储按量很便宜，5 GB 一个月几分钱）和自己承担"没有回收站"的风险。**但这一优势在中国内地会被跨境链路抵消**，详见 4.6。

#### pCloud 专项说明

用户实测注册仅得 2 GB，与部分资料流传的"500 GB 免费"不符，特此澄清。

##### 免费额度的真相

**pCloud 从未有过 500 GB 免费档位。** 500 GB 是**终身买断付费版**（€199.99 一次性或 €49.99/年，[官方 pricing](https://www.pcloud.com/cloud-storage-pricing-plans)）。混淆源于两项不同的活动/规则：

| 途径 | 获得额度 |
|---|---|
| 注册即得 | 2 GB |
| 完成新手教程（每步 +1 GB）：验证邮箱 / 上传一个文件 / 安装登录桌面端 / 安装登录手机 App / 开启自动上传 | +5 GB → **7 GB** |
| 邀请朋友（每成功邀请 1 GB，需对方注册并验证邮箱），最多 3 位 | +3 GB → **10 GB（封顶）** |

依据：[官方 Plan Details](https://help.pcloud.com/article/plan-details)、[官方 Referral Program](https://help.pcloud.com/article/referral-program)。免费版另有 **Shared Link Traffic 50 GB/月**、上传流量为存储空间 2 倍/30 天两项限制。

##### 数据区域：无亚洲节点（此前遗漏）

[pCloud 数据区域](https://www.pcloud.com/data-regions)只有 **Europe（瑞士）与 USA**，**没有亚洲节点**。这与 4.6 节 Backblaze B2 是**同一等级别的跨境硬伤**——换掉 Nextcloud 的动机若是"慢"，pCloud 未必解决。**这一条在 v2 初稿中被完全遗漏。**

##### 商业模式争议（社区观点，非事实）

Reddit 有讨论（2026 年，标题《The Lifetime Trap》）质疑其"终身付费"模式：公司失去挽留付费用户的动机，服务质量或下滑；且提到 Google 在 2026 年将基础档免费提升以竞争，pCloud 对老用户无升级通道。**这是用户观点，不是官方声明或已证实的质量问题**，但结合"瑞士公司 + 跨境链路 + 无亚洲节点 + 商业模式争议"四条，作为长期同步后端需谨慎评估。

##### 定位修正

原表述"✅ 可用，**500 GB 免费**是最大优势"**已作废**。修正为：**⚠️ 备选/双写目标**——免费 7–10 GB 与回收站、版本历史齐备，适合作为 4.7 节所述"双写同一份到两个网盘"的第二目标，但**不宜作为唯一主力 hub**（无亚洲节点）。

### 4.6 对象存储（S3 / B2）：注册与国内可用性专项评估

4.5 曾指出 S3/B2 在**技术上**是最适合做同步 hub 的后端。这一节回答另一个问题：**在中国内地，它能不能用、值不值得用。**

#### 结论先行

> **能注册，但麻烦，且跨境链路是硬伤。对本方案（4 设备 / <5 GB / 人工触发）的场景不划算**——技术优势兑现不了多少，却要付出绑卡、跨境延迟、失去回收站三重代价。

#### A. Backblaze B2：注册流程

官方流程：

1. 邮箱注册 → **必须用注册时的同一个浏览器**打开验证链接（15 分钟过期）
2. 选择数据区域 → **创建后不可更改**
3. 登录控制台 → 创建 Bucket（**桶名全局唯一**，撞名需反复重试）
4. 生成 Application Key（rclone 使用的就是这对 KeyID / ApplicationKey）
5. 用 rclone 配置 S3 后端填入 endpoint、access key、secret

#### B. 四个坎

##### 坎 1：绑卡绕不过（但可控制风险）

| 项 | 情况 |
|---|---|
| 免费额度 | **10 GB** 存储，超过即计费 |
| Public 桶 | 需绑卡并扣 1 美元（Private 桶不需要） |
| 支持的支付方式 | **仅主流信用卡/借记卡（Visa / Mastercard / Amex）+ 银行转账（ACH）** |
| 不支持 | **PayPal、支付宝、微信**（未接入） |
| 风控 | CVV 校验 + 地址匹配 + **发卡行地区白名单** 三重验证 |
| 额外材料 | 部分新兴市场用户可能需上传身份证明才能完成首充（来自第三方博客，可信度一般） |

**国内发行的信用卡能否通过地区白名单，官方文档没有明确说明，只能实测。**

> **风险控制建议**：5 GB 数据远在10 GB 免费额度内，正常同步**永不产生费用**。但若 Access Key 泄露被写入垃圾数据，费用立刻产生。对策：
> - Application Key **只授权一个 bucket**（不要用全局 master key）
> - 权限收窄为"只读 + 只写"，不给删除/列桶权限
> - 定期轮换密钥
> - 在 Backblaze 控制台开启**消费告警**（余额低于阈值邮件提醒）

##### 坎 2：没有亚洲区域，且区域不可改

Backblaze 现有数据中心：

| 区域 | 数据中心 |
|---|---|
| US West（默认） | Sacramento + Stockton + Phoenix（美国） |
| US East | Reston, Virginia（美国） |
| EU Central | Amsterdam（荷兰） |
| CA East | Toronto（加拿大） |

**没有香港、新加坡，没有任何中国大陆节点。** 且一个账号只能属于一个区域，注册后不可更改；想要多区域必须开多个账号。

对国内链路的后果（经验值，需实测）：

| 指标 | 估算 |
|---|---|
| 单线程 RTT | 150–250 ms（连美国西部） |
| 同步 5 GB（10 MB/s 带宽） | 约 10 分钟，**但跨境丢包时更慢且不稳定** |
| 晚高峰 | 电信/联通/移动到美西的路由质量差异很大，可能极差 |

**这是本节最重要的结论**：你换掉 Nextcloud 的动机是"慢"，而跨境对象存储**未必更快，甚至更慢且不可控**。

##### 坎 3：S3 兼容 ≠ 保留 Google Drive 的那些便利

| | B2 | Google Drive |
|---|---|---|
| 回收站 | ❌ **删除即永久删除** | ✅ 30 天 |
| 版本历史 | ❌（需自建规则） | ✅ 30天/100版，不占配额 |
| 网页版浏览 | ⚠️ 仅简易文件列表 | ✅ 完整 |
| 大小写敏感 | ✅ 敏感 | ❌ 不敏感 |
| 真实目录语义 | ✅ 有 | ⚠️ 不存空目录 |

**第一行是重点**：第 7 章设计的"覆盖前自动备份 + 快速定位"在 Drive 上是**三道保险**（本地备份 + Drive 回收站 + Drive revisions，见 7.8），在 B2 上会**退化为唯一一道**。

##### 坎 4：不是所有操作都免费（但同步场景恰好在免费额度内）

| 项目 | 价格 | 你的 5 GB 场景 |
|---|---|---|
| 存储 | **$6.95 / TB / 月** | ≈ $0.035/月（约 2.5 毛） |
| 出口流量 | 每月免费额度 = **平均存储量的 3 倍**，超出 $0.01/GB | 存 5 GB → 每月免费下载 15 GB，**同步几乎永不超** |
| A/B/C 类事务 | 免费 | — |
| D 类事务 | $0.004 / 万次 | 可忽略 |

**结论：对象存储确实是"几乎零成本"。** 同步是"存一次、偶尔取一次"的模式，流量比远小于存储的 3 倍。

#### C. AWS S3：比 B2 更麻烦，不推荐个人用

| 问题 | 说明 |
|---|---|
| 绑卡 | 必须，且会预扣 $1 验证 |
| **中国区需单独账号** | 开通 aws.cn 需要**企业营业执照 + 实名认证**，个人账号无法开通 |
| 用境外账号存国内数据 | 慢，且**数据出境的合规性存疑** |
| 存储价 | $23 / TB / 月（5 GB ≈ $0.115/月，约 8 毛），是 B2 的 3 倍多 |
| 出口 | 每月前 100 GB 免费，之后 $0.09/GB |
| 免费层 | 新用户 5 GB / 12 个月，**过期即删数据** |

AWS 的优势（生态、Glacier 归档、区域复制、合规认证、CASA 评估体系）**在本场景一项都用不上**。

#### D. 技术优势确实是真的（但不适用于本场景）

这是本节需要平衡的一侧。4.5 的评价不是营销话术：

| 维度 | B2/S3 | Google Drive |
|---|---|---|
| 大小写敏感 | ✅ `README.md` 与 `readme.md` 是两个文件 | ❌ 撞车 |
| hash 算法 | ✅ 标准 md5 / sha1 | ⚠️ 原生文档无 hash |
| mtime | ✅ 秒级标准 RFC3339 | ✅ 毫秒精度 |
| 原生文档坑 | ✅ 不存在 | ⚠️ 需特判（见 2.3） |
| 空目录 | ✅ 真实目录 | ⚠️ 不存 |

**这些优势兑现的前提**：同步内容全是文档 / 代码 / 文本，不涉及 Office 原生文档。如果满足，B2 在数据模型层面确实干净得多。

#### E. 最终选型建议

**本方案（4 设备 / <5 GB / 人工触发 / 需要单文件恢复）：不选 B2/S3。**

理由按重要性排序：

1. **跨境链路是硬伤且不可可控**——换掉 Nextcloud 的动机是"慢"，跨境对象存储未必更快
2. **失去回收站与版本历史**——第 7 章的三道保险退化为一道
3. **需绑境外信用卡**，注册与支付均存在风控不确定性（国内卡能否过白名单未知）
4. **技术优势兑现有限**——5 GB 文档类文件，Drive 的原生文档坑本来也碰不到

**但架构上留了口子**：第 8.3 节的 `backend_caps.py` 把后端差异编码成查表，换后端**只改配置不改代码**。若将来网络条件变化（如公司有稳定国际专线），把 `remote` 从 `gdrive:work` 改成 `b2:work` 并在 `backend_caps` 里加一条 `b2` 条目即可。

#### F. 若仍要试，最小验证路径

建议先花 30 分钟验证，不通就放弃：

```powershell
# 1. 注册建桶 + 生成 key（只授权一个桶）
# 2. 配置 rclone
rclone config
#   Storage> s3
#   provider> Other
#   access_key_id       → 你的 KeyID
#   secret_access_key   → 你的 ApplicationKey
#   endpoint            → https://s3.us-west-004.backblazeb2.com
#     （region 对应地址，见 rclone docs）

# 3. 实测上行速度（关键一步）
rclone copy .\5MB-test.bin b2:test --progress
#    观察 MB/s 和是否有卡顿

# 4. 实测列举延迟（关键一步）
Measure-Command { rclone lsjson b2:test } | Select-Object TotalMilliseconds
```

**判定标准**：单线程上传 ≥ 5 MB/s 且列举延迟 < 500 ms 才值得继续。达不到就放弃，回到 Drive。

### 4.7 多网盘并行：不同文件夹用不同的 hub

**结论：完全可以，而且本方案的架构天然支持。**

#### 为什么架构上已经支持

planner / backup / executor 三个模块**没有任何 Drive 特有的逻辑**：

| 模块 | 是否绑定 Drive |
|---|---|
| `planner.py` | ❌ 只认 `Entry`（relpath/size/mtime/md5） |
| `backup.py` | ❌ 只认本地路径 |
| `executor.py` | ❌ 只调 rclone_wrapper |
| `rclone_wrapper.py` | ❌ remote 就是一个字符串 `name:path` |

**"远端"在整个引擎里只是一个字符串。** 换网盘 = 改配置，不改代码。

#### 但有五处必须改

**① 配置从单对变成列表（profile 列表）**

```jsonc
// config.shared.json —— 可放 U 盘，4 台机器共用
{
  "profiles": [
    {
      "name": "工作文档",              // 本地显示名
      "remote": "gdrive:work",         // hub A：Google Drive
      "local_dir_hint": "work",        // 仅提示，本机覆盖
      "ignore": ["*.tmp", "~$*", ".git/**"]
    },
    {
      "name": "照片",
      "remote": "onedrive:photos",     // hub B：OneDrive
      "local_dir_hint": "photos",
      "ignore": ["*.xmp", "Thumbs.db"]
    },
    {
      "name": "项目归档",
      "remote": "b2:archive",          // hub C：Backblaze B2
      "local_dir_hint": "archive",
      "ignore": []
    }
  ],
  "backup_keep_versions": 5,
  "backup_keep_days": 30
}

// config.local.json —— 每台机器一份
{
  "device_name": "公司台式",
  "profiles": {
    "工作文档": { "local_root": "D:\\work" },
    "照片":     { "local_root": "D:\\Photos" },
    "项目归档": { "local_root": "D:\\Archive" }
  }
}
```

**② `index.db` 的主键必须加上 profile 名**

这是最容易漏的一处。多个 profile 共用一个 `index.db` 时，`notes/todo.md` 这个 relpath 在不同 profile 下是完全不同的文件：

```sql
-- 错误（会串数据）
CREATE TABLE baseline (relpath TEXT PRIMARY KEY, ...);

-- 正确
CREATE TABLE baseline (
    profile   TEXT NOT NULL,      -- 新增
    relpath   TEXT NOT NULL,
    size INTEGER, mtime TEXT, md5 TEXT, remote_id TEXT, synced_at TEXT,
    PRIMARY KEY (profile, relpath)     -- 复合主键
);

CREATE TABLE backup (
    id INTEGER PRIMARY KEY,
    profile     TEXT NOT NULL,    -- 新增
    relpath TEXT NOT NULL,
    version_path TEXT NOT NULL,
    size INTEGER, md5 TEXT, created_at TEXT, reason TEXT, device TEXT
);
```

`backup` 表同样要加 `profile` 列，否则定位页搜索 `todo.md` 会返回其他 profile 的备份。

**③ 备份目录按 profile 分层**

```
.sync/
  index.db
  history/
    工作文档/
      notes/20261013-153000__todo.md
    照片/
      20261013-160000__IMG_001.jpg
```

**④ 远端 hash 算法按 profile 记录**

因为 4.5 讲的①——每个 profile 的本地 hash 算法不同：

```jsonc
{
  "name": "工作文档", "remote": "gdrive:work",
  "hash_types": ["md5"]              // ← 新增字段
}
{
  "name": "照片", "remote": "onedrive:photos",
  "hash_types": ["quickxor"]
}
```

**⑤ UI 从"单 profile"变成"下拉选择"**

扫描页顶部加 profile 选择器，一次只扫描一个 profile（保持"一次同步一件事"的清晰度）。定位页可跨 profile 搜索（结果加一列显示来源 profile）。

#### 多网盘并行的三个陷阱

**陷阱 1：多个 remote 的 token 各自独立失效**

| 后端 | 失效规则 |
|---|---|
| Google Drive | 停在 Testing 状态则 **7 天**；In production + 6 个月不动 |
| OneDrive | **90 天不运行 rclone 即失效**，需 `rclone config reconnect onedrive:` |
| Dropbox 等 | 相对宽松 |

4 台设备 × 3 个 profile = 12 个授权要维护。**U 盘上要带一份完整的 `rclone.conf`**（含 3 个 remote 的 token）。

**建议**：工具加一个"token 健康检查"按钮，依次对每个 profile 跑一次轻量 `lsjson`，失败的标红提示需重新授权。

**陷阱 2：跨网盘不能同步**

如果一个文件要从"工作文档"(Drive) 移到"照片"(OneDrive)，工具**不做这个操作**。要么手动下载再上传，要么两个 profile 用同一个 remote。

**陷阱 3：分散在多个网盘 ≠ 备份冗余**

把文件夹拆到 Drive 和 OneDrive，**不构成备份策略**。Drive 账号被封时只有 OneDrive 那部分数据安全；而且每个网盘都只有你的一份数据，没有第二份。

**真要冗余，正确做法是双写**：同一份数据同时同步到两个 remote（配两个 profile，指向同一个 local_root，不同 remote）。这才是 3-2-1 备份的思路。但这会让同步时间和存储翻倍——对 5GB 数据来说完全可行。

#### 什么时候值得用多网盘

| 场景 | 建议 |
|---|---|
| 单一网盘够用（< 5 GB） | **不要多网盘**。多一套配置、多一套 token、多一类故障 |
| 单个网盘有大小写/哈希缺陷 | 换网盘，而不是并用 |
| 不同数据类型要不同特性（照片要容量、文档要版本历史） | ✅ 值得。但注意 pCloud 免费只有 7–10 GB（见上文 pCloud 专项），**"500 GB"是付费档不是免费额度**，放大照片要么付费要么另选 |
| 想要真正的容灾 | ✅ 值得，但要**双写同一份**，不是拆分 |

**本方案的模块设计天然支持 profile 列表，但建议 v1 只实现单 profile**，把多 profile 作为 v2 增量——因为它涉及 schema 变更（复合主键），晚做比早做改动小。

### 4.8 `lsjson`：本方案扫描远端的核心命令

```powershell
rclone lsjson -R --files-only --hash --no-mimetype gdrive:work/
```

返回稳定的结构化 JSON 数组（可整体解析，也可逐行解析）：

```json
{
  "Path": "notes/todo.md",
  "Name": "todo.md",
  "Size": 2048,
  "ModTime": "2026-10-13T09:15:57.034+01:00",
  "MimeType": "text/markdown",
  "ID": "1XyfxxxxxxxxxxxxxxxxxxxxxxxxxKHCh",
  "IsDir": false,
  "Hashes": { "MD5": "b1946ac92492d2347c6235b4d2611184" }
}
```

要点：
- `Path` 是**相对远端根目录**的路径，直接可作为两侧比对的 key
- `ModTime` 是 RFC3339 格式，精度取决于后端（Drive 是毫秒，即 3 位小数）
- `Hashes` 需显式加 `--hash`；可用 `--hash-type MD5` 限制只取一种
- `--no-mimetype` 可省一次请求（同步不需要 MIME）

### 4.9 便携性与 venv 的陷阱

#### rclone 本身是完全便携的

rclone 是单一静态可执行文件，无依赖。官方文档明确支持完全便携模式，且配置文件查找**优先级第 1 位就是 `rclone.conf`（与 rclone.exe 同目录）**：

```
E:\
  rclone.exe
  rclone.conf     ← 含 refresh_token
```

完整可控路径还有 `--config` / `--cache-dir` / `--temp-dir` / `--bisync-workdir`。

**Windows 上的唯一例外**：`rclone mount`（挂载成虚拟盘）需要装 **WinFsp 驱动**，不是纯便携。但 `lsjson` / `copyto` / `move` / `deletefile` 全都不需要。本方案不用 mount。

#### ⚠️ venv 不能跨机器拷贝

这是本方案在分发上的关键技术陷阱。Windows venv 内部有两处**绝对路径烧死**：

| 文件 | 问题 |
|---|---|
| `venv\pyvenv.cfg` | `home = C:\Users\X\AppData\Local\Programs\Python\Python314`，换机器路径不对 → `python.exe` 启动即失败 |
| `venv\Scripts\pip.exe` | Windows exe launcher 把解释器绝对路径写进了二进制 → 必然失效 |

所以"拷贝 venv 到 U 盘在另一台机器运行"**跑不起来**，除非那台机器的 Python 装在完全相同的路径。

**修法（本方案采用）**：用 `pip install --target` 而不是 venv。

```bat
@echo off
REM 开发期：用真 venv（venv\Scripts\activate）
REM 发布期：把依赖导出到一个可移植的 libs 目录，随工具一起放 U 盘
set PYTHONPATH=%~dp0libs
python -m app
```

| 方案 | 可移植性 | 代价 |
|---|---|---|
| **甲：`--target libs` + PYTHONPATH** | ✅ 完全可移植，只要求目标机有 Python | 需一次导出步骤 |
| 乙：PyInstaller `--onefile` | ✅ 最彻底，连 Python 都不用 | 每次改代码要重新打包 |

**采用甲**。理由：requirements 只有 4 个纯 Python 包（flask / werkzeug / jinja2 及其依赖），`--target` 方式完全可靠；且保留了开发期的 venv 体验。导出命令：

```powershell
py -m pip install -r requirements.txt --target .\libs
```

#### 凭据随 U 盘走的安全考量

`rclone.conf` 里的 `refresh_token` = 账号完整访问权。U 盘丢了 = 账号丢了。

本方案的定位是"个人自用 + U 盘随身"，风险可接受，但要明确知道这一点。若要收敛风险：把 `rclone.conf` 放在 VeraCrypt / 7zip AES 加密容器里，或拆成"每台机器各自授权"（各机器独立 token，U 盘只带工具本体）。

## 5. 同步模型演进

本章记录从"两两同步"的直觉到最终模型的推导过程，包括一次被修正的判断和一个被否决的脑洞。

### 5.1 起点：人工触发式同步

对比两类软件的复杂度来源：

| 自动同步（Nextcloud 类）的负担 | 手工触发（GoodSync 类）是否消失 |
|---|---|
| 文件监听（inotify / FSEvents / ReadDirectoryChangesW）+ 事件防抖 | ✅ 消失 |
| 处理"正在写入的半成品文件"（编辑器保存过程） | ✅ 消失 —— 点按钮时文件已写完 |
| 常驻守护进程：崩溃重启、休眠唤醒、网线抖动 | ✅ 消失 —— 进程生命周期由人控制 |
| 增量状态必须崩溃一致（断电不能损坏状态库） | ✅ 消失 —— 状态随时可从零重建 |
| 静默删除：程序自己决定删掉你三个月没注意的文件 | ✅ 消失 —— 你看得见 |

**手工模式的真正杀手锏**：自动模式必须用算法解决"这个文件是删了还是新建"的歧义；手工模式可以直接**问人**。

```
以下文件在本地存在、云端不存在，是否从云端删除？
  [x] report.pdf
  [x] draft.docx
```

单用户场景下，几乎所有让三方合并变难的情况，都能被这一句话解决。

### 5.2 第一次推导：顺序单向同步

既然是手工触发，方向就是已知的，**基线（上次同步快照）就不必要了**：

```powershell
# 第一步：拉。先看清楚要下什么
rclone sync gdrive:work/ D:\work --dry-run
rclone sync gdrive:work/ D:\work -MvP --max-delete 20%

# 第二步：推。确认没问题再上
rclone sync D:\work gdrive:work --dry-run
rclone sync D:\work gdrive:work -MvP --max-delete 20%
```

**先拉后推，绝不同时。** 效果：

- ✅ 不需要基线（方向已知，无需三方比较）
- ✅ 不需要状态库（无状态 = 无崩溃一致性问题）
- ✅ 不需要墓碑（方向明确）
- ✅ 依然是"先看 diff 再执行"的安全模型

代价：本地删了的东西再拉会回来；两边都改过会被覆盖。

**这个方案对单设备、双设备是足够的。但 4 台设备时，它有一个致命问题。**

### 5.3 纠偏：Drive 本身就是"状态板"

第一版曾提出"多设备需要一个共享状态板，让各端通报自己的同步状态"（用 Google Sheet 或邮箱）。这个脑洞的方向部分正确，但结论错了——**Drive 已经内置了，不需要另造**。

| Nextcloud 的机制 | Drive API 的对应物 |
|---|---|
| 服务端 change journal（每次改动的流水） | **`changes.list` feed**（按 pageToken 增量拉，永不过期） |
| per-client sync token | `changes.getStartPageToken` 的 pageToken |
| 文件版本历史 | `revisions` |
| 全局唯一文件标识 | Drive `fileId` |

**Drive 的 changes feed 就是权威的、按时间排序的、不需要互斥的日志。** 第一版设想的 `_sync/clients/<uuid>/` 那套状态板在 Drive 上是多余的。

#### 为什么"共享状态板"这个思路本身有致命缺陷

一块大家都能写的共享板，**本身就是一个同步问题**——你在用同步问题解决同步问题，而且是在一致性模型更弱的地基上。

| 载体 | 为什么不行 |
|---|---|
| **Google Sheet** | 行没有原子 compare-and-swap。"读-判断-写"三步中间有 TOCTOU 窗口，两端同时写同一行必然丢更新。要修就得在 Sheet 上自己实现锁协议——等于重新发明一个会丢数据的数据库 |
| **邮箱** | fire-and-forget：没有原子读改写、没有顺序保证、IMAP 线程排序是灾难、投递延迟秒到分钟、Gmail 有存储和线程数上限。**只能做"报警通知人"，不能进协议** |

而且其中有一类信号（"我正在编辑这个文件"、"我马上要批量删除"）确实**无法从文件元数据推导出来**，需要额外通道。所以正确的结论是：

> **共享"可观测性/协调"信号是有价值的，但载体必须是"私有写 + 公共读"的文件命名空间（Drive 的 changes feed + revisions 已覆盖大半），绝不能是 Sheet 或邮箱。而"一致性裁决"（谁覆盖谁）必须由文件元数据本身决定，任何状态板都不能参与。**

### 5.4 最终模型：Hub-and-Spoke，不是网状

```
        [公司台式] ──┐                    ┌── [家里台式]
        [公司笔记本] ─┼→ Google Drive →───┼── [家里笔记本]
                       (权威 / 仲裁者)
```

"两两同步"与"Hub-and-Spoke"的区别是本质的：

| | 网状（真两两直连） | Hub-and-Spoke |
|---|---|---|
| 4 台设备的关系数 | 6 对 | 4 个 spoke |
| 全局时间序 | ❌ 无 | ✅ 有（changes feed 是排序的） |
| 判断谁更新 | ❌ 难 | ✅ Drive 的 modifiedTime 说了算 |
| 冲突重复检测 | 每对各查一遍 | 一次统一判定 |
| 增删改历史 | ❌ 无 | ✅ revisions |
| 断网后恢复 | ❌ 难 | ✅ 重新拉即可 |

**结论：不要做真正的两两直连。所有路径都经过 Drive，多一跳换来的确定性和日志值这个价。** 反正家和公司都能上网，不存在"物理直连"的必要。

#### 每台设备只需维护的状态

小到出人意料：

```
1. pageToken（或一个扫描游标）        ← 你在 changes 日志里的位置
2. 每个文件的元数据基线:              ← 这就是三方合并的"基线"
   fileId | 相对路径 | size | modifiedTime | md5
```

没有服务端组件，没有跨设备通信。**注意：这是每台设备各自的状态，不共享**（见 5.6）。

### 5.5 真正会丢数据的地方只有一处

**拉取时用云端版本覆盖了本地一个"本地已经改动过"的文件。**

其他操作要么可逆（上传就是上传了），要么有 Drive 回收站兜底。只有这一处会静默丢数据。

检测方法（用基线）：

```
文件 F
  本地现在:      md5 = AAA     ← 本地有未同步的修改
  上次从 Drive 见: md5 = BBB     ← 基线
  Drive 现在:     md5 = CCC     ← 云端也变了
                                   ↓
                          AAA ≠ BBB 且 CCC ≠ BBB  →  真冲突
```

**每次同步前的第一步必须是冲突检查。** 有冲突就停下人工处理，没有冲突才继续。完整判定表见 8.4。

#### 为什么本场景不需要增量 feed

Drive 的 `changes` feed 相对全量扫描的优势是"只取变化项"。但本场景 `< 5 GB`，即使文件数上万，一次全量 `lsjson` 也就几十秒的传输量，且 Drive 端列目录免费（额度充足）。

**全量扫描的最大好处是状态可以从零重建**——没有 pageToken 失效、没有增量状态损坏、没有"漏了一条变更"这类恢复难题。对个人工具来说，无状态的鲁棒性远比省流量重要。

结论：**全量扫描，不做增量。** rclone bisync 也正是这么做的。

### 5.6 状态为什么不能跨设备共享

反直觉但重要：**每台设备的基线必须各自独立**。

```
公司台式跑同步 → 基线记录的是 (公司台式本地目录 ↔ Drive)
家里台式读同一份基线 → 拿公司台式的基线去判断自己的文件 → 完全混乱
```

如果用 U 盘把 `.sync/index.db` 也带走，多台设备会互相污染基线。**结论：配置（凭据）可以跟随 U 盘走，状态库必须每台机器本地独立。**

同理，rclone bisync 的 workdir（含基线快照）也**绝对不能跨机共享**。

**代理中断同样不破坏一致性**（0.5）：未传的文件改进项只是"晚点到"，下轮重扫即补上；没有"传了一半"的中间态需要修补——这正是全量扫描 + 可重建状态的又一红利。

### 5.7 冲突解决闭环

planner 按 8.4 判定表发现"冲突"（L ≠ B 且 R ≠ B）只是**暂停**，不是解决。解决了冲突必须恢复"已同步"状态，否则冲突项会每轮复现。这是本设计最薄弱的环节，必须显式设计。

**三个裁决动作**（GUI 在冲突行提供三按钮，安全阀 1，见 8.6）：

| 动作 | 含义 | 备份 | 基线更新 |
|---|---|---|---|
| **取云端**（强制拉取） | 云端版本是对的，本地存档即可 | 本地当前内容 → history（`pull_overwrite_conflict`） | 更新为远端态。生效后该文件回到"已同步" |
| **取本地**（强制推送） | 本地版本是对的，覆盖云端 | 远端当前版本下载 → history（`push_overwrite_conflict`） | 更新为本地态 |
| **保留双份** | 两边都要。本地文件重命名为 `x.conflict-<YYYYmmdd-HHMMSS>` | 无 | 改名后的本地文件按"本地新增"走正常推送，云端原文件不动，二者成为两个独立文件各自同步 |

**一个必须写进用户提示的陷阱**：

> **不要用"删掉本地文件"来表达"接受云端版本"。**
> 用户删掉冲突文件的本地副本后，下一轮扫描会命中判定表 row 8（本地已删 → 删远端），**恰好把用户想保留的云端版本也删掉**。虽然 row 8 有删除前备份兜底，但这与用户意图完全相反。"接受云端"的唯一正确入口是 **取云端** 按钮。

**为什么不让 planner 自动选边**：单用户场景下，四个设备都是"我"，冲突的双方大概率有一个是我不要的——但"哪个不要"只有我知道。自动选边（如 mtime 新的赢）迟早覆盖掉错的一份。三按钮的人工裁决与 5.1 的"问人"哲学一致。

## 6. 实际场景与工作流

### 6.1 场景定义

| 维度 | 情况 |
|---|---|
| 设备数 | 4 台：公司台式、公司笔记本、家里台式、家里笔记本 |
| 同步内容 | "很常用的文件"，总量 **< 5 GB** |
| 触发方式 | **人工触发**，到岗/下班时各同步一次 |
| 网络前提 | 4 台设备均在中国内地，各自需有稳定代理访问 Google API（0.5，第 0 号硬依赖） |
| 当前方案 | 租云服务器跑 Nextcloud（成本高、慢） |
| 目标方案 | Google Drive 作中心点 + 轻量自研工具 |
| 额外需求 | 改动历史保留，具备单文件恢复能力 |
| 界面 | 图形界面（扫描 → 查看清单 → 点同步） |

### 6.2 日常流程

```
【到公司】
  公司台式:   扫描 → 核对清单 → 执行
  公司笔记本: 扫描 → 核对清单 → 执行

【工作日】

【下班前】                              ← 关键节点
  公司台式:   扫描 → 核对清单 → 执行
  公司笔记本: 扫描 → 核对清单 → 执行

【回家】
  家里台式:   扫描 → 核对清单 → 执行    ← 此时拉到了公司的所有改动
  家里笔记本: 扫描 → 核对清单 → 执行
```

**耗时估算必须分首轮与常规轮**：

| 轮次 | 场景 | 耗时 |
|---|---|---|
| 常规轮 | 两次同步之间只有少量变更（日常形态） | 本地扫描 + 远端 lsjson + delta 传输 ≈ **1–3 分钟** |
| 首轮 | 新设备接入、新 profile、基线重建（本地↔Drive 有一次全量搬运） | 全量 5 GB 传输。按 0.5 的带宽公式估算：代理 3 Mbps ≈ 3.7 小时，10 Mbps ≈ 1.2 小时。**一次性支出，不是每轮成本** |

带宽假设（代理出口速率）必须用 4.6 F 的同款方法实测校准：`rclone copy` 一个 5 MB 小文件到 `gdrive:test --progress`，观察稳定 MB/s。

### 6.3 唯一的行为风险

**在两个同步节点之间，某个设备改了文件但没有同步。**

后果分析：

| 后果 | 严重性 |
|---|---|
| 该设备上的改动暂时没上云 | 轻微——数据没丢，只是"晚点到" |
| 回家后其他设备拉不到这个改动 | 轻微——同上，下次该设备一同步就补上 |
| 如果此时又在这台设备删除了文件 | **数据丢失**——因为云端从来没有过这个文件 |

第三种是唯一的真实风险。缓解手段（按成本排序）：

1. **习惯**：把"扫描→执行"绑定到一个明显的日常动作上（开机后 / 关机前）
2. **界面提示**：工具检测到"上次同步时间距今超过 N 小时且检测到本地改动"时，顶部显示醒目提示条
3. **手机热点兜底**：下班前发现忘了同步，开手机热点花 1 分钟补上（< 5 GB 完全可行）

不需要复杂的机制。工具只需在第 2 点上做个提示即可。

### 6.4 为什么 4 台设备不该用 rclone bisync

`rclone bisync` 只支持 **2 个位置**。4 台设备 + 1 个云盘 = 5 个位置，bisync 的三方模型不适用。

即使强行让 4 台设备各自与 Drive 做 bisync：bisync 官方仅支持**两个**路径，多设备共用同一 remote 属**未支持场景**——两端各自持有与 Drive 的基线、互不知情，A 推上去的内容 B 可能当"云端新增"拉回，一端的误删更会经 Drive 传播到全部设备。不是模型结构上坏了，而是删除传播与冲突判定在多端下不可控。

**多设备要用服务器权威模型**（changes feed + 各自基线），这正是第 5.4 节的模型，也是本方案自研引擎的原因之一。

### 6.5 设备身份与配置

每台设备需要：

| 项 | 说明 | 是否可共享（U 盘） |
|---|---|---|
| 设备名 | 如"公司台式"，用于日志和 UI 显示 | ✅ 各设备默认值不同 |
| 本地同步根目录 | 如 `D:\work` | ❌ 各设备不同 |
| 远端路径 | 如 `gdrive:work` | ✅ 相同 |
| 忽略规则 | 如 `*.tmp`、`~$*`、`.git/` | ✅ 相同 |
| `rclone.conf` | 凭据 | ✅ 可共享（见 4.9 安全考量） |
| `.sync/index.db` | 基线 + 备份索引 | ❌ **绝对不能共享** |

**配置分离建议**：共享部分（远端路径、忽略规则）放一个 `config.shared.json`，可放 U 盘；本机部分（设备名、本地路径）放 `config.local.json`，每台机器一份。

## 7. 备份与恢复设计

### 7.1 需求澄清

原始需求是"有撤回能力"。经过讨论，确定为：

| 需求 | 决定 |
|---|---|
| 备份粒度 | **按文件**（不是按轮次）——单文件恢复更实用 |
| 备份时机 | 覆盖/删除**之前**自动执行，无需人工触发 |
| 恢复方式 | **人工**。工具只提供"快速定位备份"，不做一键恢复 |
| 轮转 | 可配置份数 + 时间双条件 |

### 7.2 为什么不用"按轮次快照"

第一版曾推荐"按轮次整体快照"（每次同步建一个时间戳目录，可整体回滚）。改用按文件粒度的理由：

| 问题 | 按轮次 | 按文件 |
|---|---|---|
| 拿不到"我要恢复这个文件的旧版本" | ❌ 得先知道是哪一轮 | ✅ 直接按文件名搜 |
| 热文件历史被摧毁 | ❌ 一个每天改 10 次的文件，快照里全是今天 10 分钟内的 | ✅ 按版本数轮转，可调 |
| 跨设备推理 | ❌ 4 台设备各有 N 轮，快照数量爆炸 | ✅ 只需搜本机 |
| 用户实际需求 | "把 notes.md 恢复到昨天那个版本" | ✅ 匹配 |

**实际需求是"按文件恢复"，不是"回到某个时间点"。** 这是本方案与第一版结论的翻转点。

### 7.3 两个方向保护的不对称性

一个能省一半工作的观察：

| 同步方向 | 被破坏的是 | 已有保护 | 需要本地备份？ |
|---|---|---|---|
| 拉取 drive→local | **本地文件** | 无——Drive 完全不知道本地曾有过什么 | **必须** |
| 推送 local→drive | **云端文件** | Drive revisions（30天/100版）+ 回收站 | 不必须 |

所以**本地备份的核心价值是保护"拉取覆盖本地"**——尤其是那些从没同步过的本地文件（云端从来没有过它们的旧版本）。

**但本方案仍然两个方向都备份**，理由：

1. 代码是同一个"覆盖前先存"的钩子，不增加分支复杂度
2. < 5 GB 数据量下备份成本可忽略
3. Drive revisions 当第二道保险，不当唯一依赖（30 天/100 版上限，且用户手动清空回收站就没了）

**两条删除路径的备份语义**（对应 8.4 判定表 row 6 / row 8，容易搞反，特此定义）：

| 判定 | 动作 | 备份对象 | 做法 |
|---|---|---|---|
| row 6：云端已删 | 删本地 | 即将消失的**本地**文件 | 拷进 history（本地有副本，零网络成本） |
| row 8：本地已删 | 删远端 | 即将消失的**远端**文件 | **先下载再删**——本地已无副本，不下载等于把内容仅存在于云端的最后一份删掉。Drive 回收站 30 天兜底，工具仍默认下载 |

### 7.4 备份存储布局

```
.sync/
  index.db                          ← SQLite，见 7.5
  history/
    notes/
      20261013-153000__todo.md      ← 镜像原目录，时间戳前缀，保留原扩展名
      20261012-091500__todo.md
    项目A/
      20261013-161500__方案.md
```

设计要点：

| 要点 | 理由 |
|---|---|
| **镜像原目录结构** | 人可以直接在资源管理器里浏览、复制、粘贴——符合"人工恢复"的需求 |
| **时间戳前缀 `YYYYmmdd-HHmmss__`** | 按文件名排序即按时间排序；一眼看出版本先后 |
| **保留原扩展名** | 复制出来能直接用（`.md` 而不是 `.md.bak`） |
| **不做内容寻址（按 md5 分桶）** | 只有文件被覆盖时才备份，而被覆盖意味着内容已变，去重几乎不命中——白白引入 GC 和孤儿块处理 |

### 7.5 index.db 的两张表

**关键：基线表和备份索引表必须分开，它们是两个不同的东西。**

| 表 | 用途 | 生命周期 |
|---|---|---|
| `baseline` | "上次同步时两边是什么样"，用于**变更检测** | 与文件一一对应，文件删除后才移除 |
| `backup` | 被覆盖内容的副本清单，用于**定位备份** | 每次备份追加一条，按轮转规则清理 |

```sql
-- 表 1：基线 —— 三方合并的"第三方"
-- 若支持多 profile（见 4.7），主键须改为 (profile, relpath) 复合主键
CREATE TABLE baseline (
    relpath      TEXT PRIMARY KEY,   -- 相对同步根目录的路径，两侧共用同一 key
    size         INTEGER,
    mtime        TEXT,               -- RFC3339
    md5          TEXT,
    remote_id    TEXT,               -- 网盘内文件 ID（Drive=fileId, OneDrive=item id）
    synced_at    TEXT
);

-- 表 2：备份索引 —— 定位用（多 profile 时同样需加 profile 列）
CREATE TABLE backup (
    id           INTEGER PRIMARY KEY,
    relpath      TEXT,               -- 原路径
    version_path TEXT,               -- history 下的实际文件路径
    size         INTEGER,
    md5          TEXT,
    created_at   TEXT,
    reason       TEXT,               -- pull_overwrite / push_overwrite
                                       -- / delete_local / delete_remote
    device       TEXT                -- 哪台设备产生的备份
);
```

`reason` 记录是哪个操作导致的备份——排查"这个文件怎么变成这样的"时非常有用。`device` 字段在多设备场景下能标明备份来自哪台机器。

**关于 hash 列名**：`md5` 是 Google Drive / S3 情况下的叫法。换用其他网盘时（见 4.5），本地要算的是 quickxor（OneDrive）、dropbox hash（Dropbox）等对应算法——建议列名保持 `md5` 不变，实际存储"该 profile 远端所使用的 hash"，由配置中的 `hash_types` 字段决定。

### 7.6 轮转规则

| 规则 | 建议值 | 理由 |
|---|---|---|
| 按版本数保留 | 最近 5 版 | 覆盖"回到刚才"到"回到本周" |
| 按时间保留 | 30 天内全留 | 覆盖"我上周改坏了什么" |
| 触发时机 | 每次同步**开始前**检查 | 不要等磁盘满了才处理 |

< 5 GB 数据、每文件 5 版、平均文件 100 KB → 备份总量最坏情况（1 万文件 × 5 版）约 5 GB。建议给备份目录单独设一个容量上限告警。

### 7.7 快速定位功能（唯一的"恢复"功能）

按用户需求，**不做一键恢复，只做定位**。GUI 提供：

```
┌──────────────────────────────────────────────────┐
│ 搜索备份:  [ todo.md                    ] [搜索]  │
├──────────────────────────────────────────────────┤
│ 原路径                    备份时间   原因    操作 │
│ notes/todo.md          10-13 15:30  拉取覆盖 [定位] │
│ notes/todo.md          10-12 09:15  拉取覆盖 [定位] │
│ 项目A/方案.md            10-11 20:03  推送覆盖 [定位] │
└──────────────────────────────────────────────────┘
                         点击 [定位] →
              在资源管理器中选中该文件
```

实现要点：

| 要点 | 说明 |
|---|---|
| 搜索范围 | `relpath` 的模糊匹配（支持路径片段和文件名片段） |
| 结果排序 | 按时间倒序，最新在前 |
| "定位"动作 | Windows 上调用 `explorer /select,"<绝对路径>"`，直接打开资源管理器并选中该文件 |
| 只读展示 | 同时显示该版本的 md5 和大小，方便和手头文件对比 |

**不做**：预览内容、双栏 diff、一键覆盖回原位。用户的需求就是"知道去哪找"，然后自己去复制粘贴。

### 7.8 恢复的兜底：Drive 回收站与 revisions

作为第三道保险：

- **Drive 回收站**：任何通过 rclone 的删除都是 `files.delete`，默认进回收站，保留 30 天。误删可从 Drive 网页版恢复
- **Drive revisions**：误覆盖可从网页版"版本历史"恢复

本地备份（history）和 Drive 机制覆盖的是**不同的东西**：前者保护本地内容，后者保护云端内容。三者叠加，用户在任何一层出错都有退路。

## 8. 工具设计方案

### 8.1 核心工作流

严格对应 GoodSync 的使用习惯，且更简单（因为没有"规则"概念）：

```
启动工具
   ↓
[扫描]  →  本地扫描 + 远端 lsjson + 与基线比对
   ↓
展示清单（分类：上传/下载/删除/冲突）
   ↓
   ├── 发现冲突 → "执行同步"禁用；逐项三按钮裁决（取云端/取本地/保留双份，见 5.7），
   │             或勾选"跳过冲突项，同步其余"
   ↓
[执行同步]  →  逐项：备份（如需）→ re-stat 校验（见 8.4 TOCTOU）→ 执行 → 按文件粒度更新基线
   ↓
显示结果摘要 + 日志
```

**全程无自动化、无定时任务、无后台常驻。** 这是本方案最大的简化。

### 8.2 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | Python 3 | 本机已有 3.14.6；与仓库现有项目一致 |
| Web 框架 | **Flask** | 依赖最少（flask + werkzeug + jinja2 + 标记安全库），同步代码是阻塞式，与引擎天然匹配，无需处理异步 |
| 前端 | Jinja2 模板 + 原生 JS | 不引入构建工具，单文件即用 |
| 远端访问 | rclone 子进程 | 认证、限流退避、分片上传全部白拿 |
| 状态存储 | SQLite（标准库 `sqlite3`） | 无依赖，支持事务，便于查询 |
| 分发 | U 盘 + `pip --target libs` + 批处理 | 见 4.9 |

### 8.3 分层架构

```
┌──────────────────────────────────────────────────────┐
│  Web UI (Flask) — http://127.0.0.1:8765              │
│  扫描页 / 备份定位页 / 日志页                            │
├──────────────────────────────────────────────────────┤
│  planner.py      三方比对 → 同步计划（含冲突标记）      │  ← 核心
├──────────────────────────────────────────────────────┤
│  scanner.py    本地 os.scandir + 远端 lsjson → Entry  │
│  baseline.py   SQLite 基线                              │
│  backup.py     覆盖前备份、history 索引、轮转            │
│  executor.py  执行 + 安全阀 + 日志                      │
├──────────────────────────────────────────────────────┤
│  backend_caps.py   后端能力表：hash算法/mtime/大小写/     │  ← 多网盘适配
│                    版本历史/回收站/token失效规则          │
├──────────────────────────────────────────────────────┤
│  rclone_wrapper.py  lsjson / copyto / move / deletefile │
└──────────────────────────────────────────────────────┘
        ↓                      ↓
   本地文件系统          Google Drive / OneDrive / Dropbox
                        / pCloud / S3 / 中文网盘(OpenList) …
```

**模块职责**：

| 模块 | 职责 | 不做什么 |
|---|---|---|
| `rclone_wrapper.py` | 调用 rclone 子进程、解析 JSON 输出、分类错误码 | 不做任何判定 |
| `backend_caps.py` | 按 remote 名查表：该网盘的 hash 算法、mtime 精度、大小写敏感性、版本历史/回收站能力、token 失效规则 | 不执行命令 |
| `scanner.py` | 本地 `os.scandir` + stat；远端解析 `lsjson`；用 `backend_caps` 决定本地算哪种 hash；统一为 `Entry` 结构；提供 `verify_entry_unchanged()`（TOCTOU 用，见 8.4） | 不比较 |
| `baseline.py` | SQLite 读写基线表 | 不知道文件为什么变 |
| `planner.py` | **三方比对，生成 Plan** | 不执行 |
| `backup.py` | 备份执行、history 索引、轮转清理 | 不管判定 |
| `executor.py` | 按 Plan 执行、调 backup、安全阀校验、写日志 | 不重新判定 |

**关键原则**：`planner.py` 是纯函数——输入（本地 Entry 列表 + 远端 Entry 列表 + 基线列表），输出（Plan 列表），无副作用。这让它可以被独立测试。

**长任务模式**：扫描（1–3 分钟）与执行都是分钟级阻塞操作，Flask 路线必须放**后台线程**，前端轮询进度端点（`GET /api/task/<id>`），全程禁用"重复启动"按钮。这与"无守护进程"不矛盾——线程生命周期仍由这一次点击决定，进程退出即终止。

**关于 `backend_caps.py`**：这是多网盘支持的核心抽象。把 4.5 表格里的差异编码成一张查表，引擎在运行时按 remote 名查：

```python
BACKEND_CAPS = {
    "gdrive":   BackendCaps(hash_types=["md5"],  mtime="ms",
                           case_sensitive=False, has_versions=True,
                           versions_cost_quota=False, has_trash=True),
    "onedrive": BackendCaps(hash_types=["quickxor"], mtime="s",
                           case_sensitive=False, has_versions=True,
                           versions_cost_quota=True,  has_trash=True,
                           token_expiry_days=90, filename_normalize=True),
    "dropbox":  BackendCaps(hash_types=["dropbox"], mtime="s",
                           case_sensitive=False, has_versions=True,
                           versions_cost_quota=False, has_trash=True),
    "pcloud":   BackendCaps(hash_types=["sha1"], mtime="s",
                           case_sensitive=False, has_versions=True, has_trash=True),
    "s3":       BackendCaps(hash_types=["md5"],  mtime="s",
                           case_sensitive=True,  has_versions=False,
                           versions_cost_quota=True,  has_trash=False),
}
```

这样 planner 里的逻辑**完全不用针对具体网盘写分支**——它只问 "这两个 hash 能不能直接比"、"这个网盘大小写敏感吗"。

### 8.4 planner 判定表（核心逻辑）

设 `B` = 基线（上次同步时两边的状态），`L` = 本地当前，`R` = 远端当前。

| # | L | R | 条件 | 判定 | 动作 | 是否备份 |
|---|---|---|---|---|---|---|
| 1 | 有 | 有 | `md5(L) == md5(R)` | 已同步 | 无 | — |
| 2 | 有 | 有 | 不同，`L == B` 且 `R ≠ B` | 云端改了 | 拉取 | ✅ |
| 3 | 有 | 有 | 不同，`R == B` 且 `L ≠ B` | 本地改了 | 推送 | ✅ |
| 4 | 有 | 有 | 不同，`L ≠ B` 且 `R ≠ B` | **冲突** | **停止，列出** | — |
| 5 | 有 | 无 | `B` 无此文件 | 本地新增 | 推送 | — |
| 6 | 有 | 无 | `B` 有此文件 | 云端已删 | 删本地 | ✅ |
| 7 | 无 | 有 | `B` 无此文件 | 云端新增 | 拉取 | — |
| 8 | 无 | 有 | `B` 有此文件 | 本地已删 | 删远端 | ✅ |

**"是否备份"两列的两个易错点**：

- row 2/3 的备份 = 覆盖前把**被覆盖方**的当前内容存进 history（拉取覆盖就存本地，推送覆盖就存远端）
- row 8 的备份 = **删远端前先把远端版本下载进 history**——此时本地文件已不在，不下载等于裸删（删除动作执行时本地无副本可存）。Drive 回收站（30 天）是云侧第二道，但工具默认下载（5 GB 场景流量可忽略），与 7.3 口径一致

**"等于"的判定规则**（避免不必要地算 md5）：

```
相等 ⟺ md5 都存在且相同
    ⟺ 否则 size 相同 且 mtime 相同（容差 2 秒，跨系统时钟/精度差异）
```

md5 的计算策略（已定稿，见 4.5 "①"）：
- `lsjson --hash` 已经给了远端 hash，零成本
- **本地默认走方案甲（懒算）**：本地扫描不带 `--hash`（只拿 size+mtime），仅对"疑似变更"文件批量 `rclone hashsum md5 <files...>`
- 方案乙（`lsjson --hash` 全算，5 GB 约 10–30 秒）保留给首轮建库或你不在乎每次多等半分钟的情形；`hash_types` 配置字段决定算法名

**执行顺序**：

```
1. 冲突检查      → 有冲突则"执行同步"禁用；逐项三按钮裁决（5.7）或勾选跳过
2. 拉取项 (2,7)  → 云端 → 本地
3. 推送项 (3,5)  → 本地 → 云端
4. 删除项 (6,8)  → 最后执行，且单独确认
5. 更新基线      → 按文件粒度提交：单项成功即写，失败项留给下轮
```

**先拉后推**，且本轮内标记已同步项——避免刚拉下来的文件又被推回去（`lsjson` 有缓存延迟，刚推完立刻扫可能拿不到最新状态）。

**为什么删除放最后**：删除是不可逆操作最重的一类。若前面有失败，删除应该被推迟到确认无误后再做。

**为什么按文件粒度更新基线**：整轮一个事务的话，任何一项失败都会导致整轮回滚重做——人工触发场景下，500 个文件里 1 个失败重跑全轮不可接受。按文件提交 = 断点续传。

#### TOCTOU：扫描之后、执行之前，本地文件可能又变了

扫描是"只读规划"，执行是"稍后落实"，中间隔着人工看清单的时间（几分钟）。这期间编辑器自动保存、另一个程序写盘，都可能让本地文件面目全非。若不处理，传上去的是新内容、基线记的是扫描时旧 hash，下一轮必然误报冲突。

**对策**：每个推送项执行前，executor 调 `scanner.verify_entry_unchanged(entry)`：

```
(size, mtime) 与扫描时一致            → 放行
不一致                                → 重算 hash：内容确已变 → 该项标"计划过期"，跳过并列入结果摘要
                                                          → 内容没变（只是 touch）→ 放行
```

跳过不是失败：该项在结果里列出，下轮重扫自然带上新内容。**上传本身也有兜底**：rclone 上传期间检测到源文件变化会报 "source file is being updated" 并中止该项（`--local-no-check-updated` 是关闭该检查的选项，本工具**不要**开）。

### 8.5 关键数据结构

```python
# 统一的文件条目（本地和远端都归一化成这个）
@dataclass
class Entry:
    relpath: str        # 相对同步根目录的路径，两侧共用同一 key
    size: int
    mtime: datetime     # 统一转成 UTC 存
    md5: str | None     # 本地懒计算
    remote_id: str | None   # 仅远端有

@dataclass
class PlanItem:
    action: Literal["upload", "download", "delete_local", "delete_remote"]
    entry: Entry
    reason: str         # 判定依据，如 "云端改了"
    need_backup: bool

@dataclass
class Plan:
    items: list[PlanItem]
    conflicts: list[Conflict]   # 冲突项单独收集，不进 items
    stats: dict                 # {"upload": 12, "download": 3, ...}
```

### 8.6 安全阀（六道，缺一不可）

| # | 闸门 | 行为 |
|---|---|---|
| 1 | **冲突检测与裁决** | planner 发现冲突 → "执行同步"禁用；每个冲突项提供三按钮（取云端/取本地/保留双份，见 5.7），裁决动作同样走备份钩子；勾选"跳过冲突项"可放行其余文件 |
| 2 | **覆盖前备份** | 所有 `need_backup` 项**先备份，备份失败则中止该项**并报错 |
| 3 | **删除阈值** | 本轮删除数/占比超阈值（默认 20% 或 50 个）→ 中止并要求显式确认 |
| 4 | **Drive 桌面版检测** | 检测到 `GoogleDriveFS` 进程 → 拒绝启动，提示先退出 |
| 5 | **并发锁** | 单实例运行，用 PID 文件锁，防止两窗口同时操作 |
| 6 | **凭据不外泄** | token 只在 `rclone.conf`；不写入 SQLite、不写日志、不返回给前端 |

**第 6 条的具体做法**：日志和 API 响应中，凡是要打印配置的地方，只打印 remote 名称（`gdrive`），不打印整个 config 内容。

### 8.8 配置文件

```jsonc
// config.shared.json（v1：单 profile；多 profile 列表形态是 v2 增量，见 4.7）
// 可放 U 盘，4 台机器共用
{
  "profile": {
    "name": "工作文档",               // 本地显示名
    "remote": "gdrive:work",          // hub：Google Drive（内地需稳定代理，见 0.5）
    "hash_types": ["md5"],            // 本地需计算的 hash 算法（默认方案甲，见 4.5）
    "ignore": ["*.tmp", "~$*", ".git/**", "node_modules/**", ".DS_Store"]
  },
  "backup_keep_versions": 5,
  "backup_keep_days": 30,
  "delete_threshold_ratio": 0.2,
  "delete_threshold_count": 50

// config.local.json（每台机器一份）
{

**为什么分两个文件**：共享部分（远端路径、忽略规则、轮转策略）统一，避免 4 台机器配置漂移；本机部分（本地路径、设备名）必须独立。

**`rclone.conf` 里可以预先配多个 remote**（`gdrive:`、`onedrive:` 等），v1 只用其中一个，v2 多 profile 时按 profile 的 `remote` 字段引用。参见 4.5 各自的认证坑。

    rclone_wrapper.py             ← rclone 子进程封装
    scanner.py                    ← 本地 + 远端扫描
    baseline.py                   ← SQLite 基线
    planner.py                    ← 三方比对（核心，纯函数）
    backup.py                     ← 备份 + 轮转
    executor.py                   ← 执行 + 安全阀 + 日志
    locate.py                     ← 备份定位（explorer /select）
  web\
    app.py                        ← Flask 路由
    templates\
      scan.html
      locate.html
      logs.html
    static\style.css
  libs\                           ← pip install --target 导出的依赖
  rclone.exe
  rclone.conf                     ← 含多个 remote 的凭据（见 4.9 安全考量）
  requirements.txt
```

### 8.10 错误处理

| 情况 | 处理 |
|---|---|
| rclone 返回 401/403 | token 失效（多半是坑 1 的 7 天问题）→ 提示重新授权，给出命令 |
| rclone 返回 429 | 指数退避重试（rclone 内部已做，工具层只需等待并显示） |
| rclone 返回 404 | 文件已被删除 → 刷新远端清单 |
| **代理连接失败 / 超时**（proxy connect failed 等，注意与 401/403 区分） | **链路问题不是 token 问题**。跑 8.7 的"网络体检"确认；未完成项全标失败、**基线不更新**，代理恢复后重扫即续 |
| 大文件上传中代理断 | rclone 断点续传自动恢复；分片作废该项失败重来，不影响其他项 |
| 本地文件被占用 | 复制失败 → 该项标记失败，继续下一项，最后汇总报告 |
| 磁盘满 | 备份写入失败 → 中止（安全阀 2 生效） |
| 网络中断 | 已完成的项按文件粒度保留基线更新，未完成的标记为失败，下次重扫 |

**原则：单项失败不中断整轮，但删除类操作若有任何前置失败则跳过该项。**

## 10. 选型对比与最终建议

### 10.1 各方案对比

| 方案 | 上手成本 | 可靠性 | GUI | 单文件恢复 | 学习价值 | 移动端 |
|---|---|---|---|---|---|---|
| **rclone bisync** | 低（0.5h） | 高 | ❌ | 手工翻目录 | 高（源码是教材） | ❌ |
| **Google Drive 桌面版镜像模式** | 极低（10min） | 最高 | ✅ 官方 | revisions（云端侧）；本地侧需另配 restic 快照 | 低 | ✅ |
| **自研薄壳（推荐）** | 中（数天） | 中（自己兜底） | ✅ 定制 | ✅ 定位功能 | **最高** | ❌ |
| rclone mount | 低 | 中（VFS 缓存坑多） | 无 | ❌ | 中 | ❌ |
| Syncthing | 低 | 高 | ✅ | ❌ | — | ✅ |
| 继续用 Nextcloud | — | 高 | ✅ | ✅ | 低 | ✅ |

**一条"零开发路线"**（上表第一二行的组合）：Drive 桌面版镜像模式负责同步，本机 restic 定时快照负责"单文件恢复"（`restic snapshots` 找到版本、`restic restore latest --include <路径>` 或 `mount` 后浏览复制）。维护≈0，代价是恢复粒度是快照而非"改动即备份"。**如果自研动机只是"替换 Nextcloud 的功能"，先评估这条**；本工具的价值在扫描清单 GUI、按文件粒度备份定位、冲突逐项人工这三件现有工具给不了的事。

### 10.1.1 hub 网盘怎么选

| 网盘 | 同步质量 | 免费额度 | 版本历史 | 认证坑 | 结论 |
|---|---|---|---|---|---|
| **Google Drive** | 好 | 15 GB | ✅ 不占配额 | Testing 态 7 天 | **默认推荐** |
| **OneDrive** | 好 | 5 GB | ⚠️ 占配额 | **90 天不动即失效** | 微软生态内选它 |
| **pCloud** | 好 | **500 GB** | ✅ | 较少 | 额度敏感选它 |
| **Dropbox** | 好 | 2 GB | ✅ | 较少 | 额度偏小 |
| **S3 / B2** | **最好** | 几乎无 | 需自开 | 密钥管理 | 能接受付费 + 无回收站则选它 |
| Box | 一般 | 10 GB | ✅ | 需自建 app | 不推荐 |
| Yandex | 一般 | 5 GB | ✅ | 地区访问 | 不推荐 |
| 中文网盘(OpenList) | 较差 | 大 | ❌ | 各异 | 兜底方案 |

**关键判断**：同步**质量**最好的是 S3/B2（大小写敏感、hash 可靠、mtime 精确、无原生文档的坑），但它们**没有回收站也没有免费额度**——误删即永久丢失。若不放心，本地备份（见第 7 章）就是必须项而非可选项。

若追求**省心 + 免费**，Google Drive 是综合最优；有增量 feed、版本历史不占配额、15 GB 够用。

### 10.2 为什么最终推荐自研薄壳

不是因为现成方案不够用——`rclone bisync` 功能上完全够。推荐自研的理由是**需求错位**：

| 需求 | bisync | 自研薄壳 |
|---|---|---|
| 扫描清单 GUI | ❌ 只能看文本输出 | ✅ 分类表格 |
| 冲突人工处理 | ❌ 只能靠参数预设策略 | ✅ 逐项处理 |
| 备份粒度按文件 | ❌ `--backup-dir` 是按轮次 | ✅ 按文件版本 |
| 快速定位备份 | ❌ 无 | ✅ 搜索 + 资源管理器定位 |
| 冲突时保留双份 | ✅ 有 | ✅ 有 |

**bisync 的备份是按轮次的**（`--backup-dir <时间戳目录>`），要恢复单个文件的旧版本，必须先想清楚是哪一轮、再去翻对应目录。自研按文件粒度则可以直接搜。

反过来说，**如果不需要 GUI 和按文件备份，直接用 `rclone bisync` + 一个批处理脚本是更省事的选择**。这个判断留给实际使用者。

### 10.3 什么时候应该放弃自研

诚实地说，以下情况应该直接用现成方案：

- 只是想有个能用的同步，不需要 GUI → `rclone bisync`
- 想要最稳、零维护 → Drive 桌面版镜像模式
- 需要手机端同步 → 官方客户端（自研做不到）
- 文件量超过 50 GB → 考虑 Nextcloud 或其他方案，5 GB 假设不再成立
- **只是想要"多个网盘并用"** → 先问为什么：多一套 token、多一类故障。如果动机是"怕单点故障"，正解是**双写同一份到两个网盘**（见 4.7），而不是把不同文件夹拆到不同网盘

**两条现实的对照路线**（都为"零自研"而设）：

1. **零开发路线：Drive 桌面版镜像 + 本地 restic 快照**（见 10.1 末）。10 分钟部署、维护≈0，满足"4 设备同步 + 单文件恢复"，缺的是扫描清单 GUI / 按文件备份定位 / 冲突逐项人工。
2. **"国内 VPS + Nextcloud"**：官方桌面+手机端 + Web GUI + 完整版本历史，功能上确实覆盖本方案全部需求。代价是钱（99 元/年档只有两条真实路径，见附录 C）、带宽（3–5 Mbps，首轮单设备 5 GB 约 3–4 小时，delta 轮分钟级）、备案（**用户实测：旧备案已失效，需重新走首次备案 3–22 个工作日**，附录 C）、以及一份自运维负担（证书、升级、备份、被扫）。它是另一条路线，不是本方案的简化版——本方案不为它改设计，仅存档参考。

## 附录 C：国内轻量服务器对照（Nextcloud 场景）

> 用途：§10.3“国内 VPS + Nextcloud”对照路线的选型参考。数字按 0.4 纪律标注来源；**凡标“待核实”的，下单前以控制台实时报价为准**。
> 核查时间：2026-10-14。

### C.1 两个先说清楚的事实

**带宽**（“不另外加钱只有 1 Mbps”的印象已过时，2026 年轻量入门档实测如下）：

| 厂商 | 入门档带宽 | 月流量 |
|---|---|---|
| 阿里云轻量 | **全系 200M 峰值**（[官网](https://www.aliyun.com/product/swas)） | **不限月流量** |
| 腾讯云轻量 | 3M / 4M 固定（[官网](https://cloud.tencent.com/product/lighthouse)） | 200–300 GB/月 |
| 京东云轻量 | 3M / 5M 固定（[官网](https://www.jdcloud.com/cn/products/light-virtual-machines)） | 200–500 GB/月 |
| UCloud 奔流型 | 200M 峰值（[官方说明](https://www.ucloud.cn/yun/articles/2604)） | 不限流量 |
| 天翼云 | 仍有 1M 档（秒杀款） | — |

换算：3 Mbps ≈ 375 KB/s → **单设备首轮同步 5 GB ≈ 3.7 小时**；4 Mbps ≈ 2.8 小时。之后 delta 轮分钟级。4 设备各 5 GB 的初期全量 ≈ 20 GB 出流量，200 GB/月套餐够用。**结论：首轮一次性慢，日常可用**；比 Google Drive + 代理的差别主要是“速率上限确定、不随代理波动”。

**备案**（三元组 + 一个会失效的第四个事实）：

备案不是域名的永久属性，而是 **主体（证件）+ 域名 + 接入商（含关联服务器与账号）** 的动态登记——[阿里云备案首页](https://beian.aliyun.com/)原话："非阿里云注册域名可以在阿里云提交 ICP 备案申请，备案主要与服务器提供商相关"。更坑的是**记录本身会失效**：接入的服务器释放、长期无有效接入，备案可能被清理，"曾经备过案"说没就没。

**本案例全程实录（2026-10，用户实测）**：mcgods.top 早年备过案 → 新购阿里云 ECS + Nextcloud + 域名访问 → **立即被阿里云未备案拦截页拦下** → 诊断发现**域名上已无备案记录**（旧接入失效/未维护被清理）→ 结论：不是接入备案，是**重新走首次备案**。

**三条路径（按验证结果选）**：

| 路径 | 前提 | 动作与时长 |
|---|---|---|
| **A. 零等待** | 买前 30 秒验证三件事全过：①备案控制台能查到该域名；②状态正常（非过期/注销/空壳主体）；③备案账号 = 服务器账号 | 直接解析即用，无任何备案操作 |
| **B. 重新备案（本用户情形）** | 域名无在册记录或记录失效 | **首次备案**：订单填资料 → 阿里云 App 人脸核验 + 身份证 → 初审 1–2 个工作日（含电话核验）→ 工信部短信核验（24h 内）→ 管局审核 1–20 个工作日 → **总计 3–22 个工作日**。硬门槛：服务器需**包年包月 > 3 个月且有公网带宽**，否则拿不到备案服务码（[阿里云服务器要求](https://help.aliyun.com/zh/icp-filing/basic-icp-service/support/server-check-faq)） |
| **C. 灰度过渡** | 审核期间想立即用 | Nextcloud 客户端直连 `http://IP:非标端口`：`config.php` 的 `trusted_domains` 加服务器 IP，Web 服务监听 80/443 之外的端口。不碰域名不触发拦截，社区自用实践可行，属灰色地带 |

**两个补充事实**：

- 工信部系统（beian.miit.gov.cn）**查不到接入商**（[腾讯云官方文档](https://cloud.tencent.com/document/product/243/103520)明说）；想知道备案当年接入在哪，只能登录当年提交备案的控制台查
- 子域名免备的前提是主域名**当前**有有效备案（[阿里云 FAQ](https://help.aliyun.com/zh/icp-filing/basic-icp-service/product-overview/faq-about-icp-filing-applications-in-different-scenarios)）；主域名记录没了，`nc.mcgods.top` 照样被拦。GA 公安备案绑主体不绑服务器，换机无需重做

### C.3 口碑与操作建议

- 个人自用口碑：阿里/腾讯的备案流程、文档、Nextcloud 教程最成熟，网络到家宽/公司网的质量最好；UCloud 价格诚实但轻量续费规则花样多；芯飞云等小厂便宜但**不建议放个人数据**（跑路风险即数据风险）

### C.4 与主方案的关系

这条路线满足“4 设备同步 + 单文件恢复 + 手机端”的功能全集，但它**不改变主方案结论**：自研工具的价值在扫描清单 GUI、按文件粒度备份定位、冲突逐项人工，以及学习目的。若走 VPS，本文档第 5–8 章仍可复用其备份/恢复设计思想（history 目录 + rclone hashsum），只是“hub”从 Google Drive 换成这台 VPS 的 Nextcloud。
