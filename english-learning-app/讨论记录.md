## 2026-09-20 · v0.3.7 第四场景（小学·问路与地图）主题与"大地图牌"构图决策

- **背景**：v0.3.6 按学段过滤后，小学档只有 scene02 一个场景，"随机"退化为固定；用户要求新增小学场景，主题定为教材里的问路/地图课文（人教版六上 Unit 1 How can I get there?），并要求能支撑 3 个 level 的出题。用户随后提出关键约束：**平板答题时图片只占半屏，元素塞太多会小到认不出**。
- **讨论过的方案**：
  1. 主题锚点：a) 自创生活场景 / b) **锚定教材课文**（问路句型 `Go straight and turn left at the...` 学生课内学过，评测不因"没学过"卡壳）。
  2. 构图：a) 纯街道场景、细节靠建筑招牌堆（原方案：两条路线+闭馆牌+时钟+纸地图老人等 7 类元素）/ b) **前景大 TOWN MAP 地图牌占画面约一半**，路线/地点/营业时间等大字号写进地图，街道退为背景氛围（≤5 个大元素）；日期类陷阱（周一闭馆）改由题目文字给出，图上只留可找到的证据。
  3. 半屏验证方法：按 CSS 实际约束（`.app` 720px、图片 max-height 420px → 3:2 图最终约 630×420）在 533×356 压力下截图验证，全部标签逐字可读后才定稿。
  4. 级别档位：a) 对齐 scene03 三档 / b) **对齐 scene02 加 L4 角色扮演**（问路天然适合扮演，10-12 演小导游出效果）——用户同意。
- **用户决策**：1b + 2b + 3 验证通过即定稿 + 4b；出题思路（L1 指认/L2 图上路线推理/L3 观点迁移/L4 扮演，16 题 grounded×9/open×7）经用户审阅题目清单后确认。
- **理由**：半屏可读性是出题纪律的硬约束——**凡 L1/L2 考的元素必须在缩小后肉眼可辨**，否则学生答不出会被误判为英语问题；评分走 scoringDescription 不受图小影响，但学生眼睛受得了才算数。大地图牌同时解决"细节多"与"看得清"的矛盾，且贴合教材"看图问路"原型。
- **产出**：`Demo/Scene04_image.jfif`（1536×1024 JPEG）+ `Scene04_questions.txt` + `public/scenes/scene04/` 三件套，index.json 登记 primary；小学档 2 场景，10-12 随机恢复多样性。

## 2026-09-20 · v0.3.6 场景按年龄学段过滤

- **背景**：demo 已有小学（scene02）/初中（scene01）/高中（scene03）三个场景，开始页也已让用户选年龄，但年龄目前只影响评分 audience 提示词，`resolveSceneId()` 仍跨全部场景随机——选"16-18"可能抽到小学生日会场景，难度错位损害 demo 说服力。各场景 `meta.json` 其实早已带 `gradeLevel` 字段，分类数据现成。
- **讨论过的方案**：
  1. 是否按年龄过滤场景：a) 保持全池随机 / b) **选了哪个年龄就只在同学段场景内随机**。
  2. 过滤后该学段无场景怎么办（当前每学段只有 1 个场景，属过渡状态）：a) 回退全池随机保体验 / b) **直接报错**进 Error 屏提示换选。
  3. 学段信息放哪：a) 逐场景拉 `meta.json` 比对 / b) **在 `index.json` 注册表登记 `gradeLevel`**（id 列表升级为对象列表），一次请求完成过滤。
- **用户决策**：1b + 2b + 3b。用户确认当前是 demo 阶段每学段仅 1 个场景，后续会在各学段继续加场景，"随机"会随之恢复多样性；无匹配时报错比静默跨学段出题更符合演示预期。
- **理由**：难度错位是体验硬伤，报错是显性、可解释的失败，而跨学段回退会把"场景不足"这一数据问题悄悄变成体验问题；`?scene=` URL 覆盖保持不受学段限制，方便老师/调试强制指定任意场景。

## 2026-09-20 · v0.3.4 开始页"只留四要素"重设计 + 动效降级策略修正

- **背景**：v0.3.3 开始页交付后用户反馈四点：① 元素太多、界面拥挤；② 设计的动画在本机 Windows 关闭系统视觉特效时完全不播放；③ 质疑场景预告条放首页是否合适；④ 明确必备元素只有 Title / 年龄选择 / 题型选择 / 开始按钮，其余皆为视觉装饰。
- **讨论过的方案**：
  1. 拥挤源处理：a) 保留全部元素只缩小间距 / b) **删除三步玩法卡行与双语组标题冗余、改单列居中窄容器**。
  2. 动画失效根因与策略：先定位为 Windows「显示动画效果」关闭 → 浏览器上报 `prefers-reduced-motion: reduce` → v0.3.3 的 `animation: none !important` 一刀切。可选：a) 直接删掉该媒体查询（无视系统全量播放）/ b) **只停位移类，保留淡入与光晕/流光**（尊重无障碍意图但页面不死静）/ c) 加页面内动画开关。
  3. 场景预告条：a) 保留并美化 / b) **移出首页**（首页拥挤主因之一；且场景是开始后才随机/指定确定，预览会造成"看到的不是要聊的"预期落差）/ c) 挪到答题页做切换入口。
  4. 是否整页重做：用户给出四要素约束后确认 **整页重做**（分段年龄控件、瘦题型卡、发光 CTA、四角环境芯片）。
- **用户决策**：2b（只停位移类）+ 3b（移出首页）+ 4 整页重做，装饰元素仅服务视觉、不承载信息。
- **理由**：四要素之外无信息价值，删比缩更有效；无障碍降级不该让页面变成静态图，位移停掉、淡入与光晕保留是兼顾点；场景预览与"开始后才知道聊哪个场景"逻辑冲突。若日后要无视系统设置全量播放，删除 `App.css` 中 `@media (prefers-reduced-motion: reduce)` 块即可。

## 2026-09-18 · v0.3.3 开始页重设计

- **背景**：v0.3.2 虽“活泼化”，但开始页本质还是早期功能验证时搭的临时页，设计度不足。用户要求参考同类英语学习 App（Duolingo/Elsa/Drops 等）重设计为现代、活泼、有设计感的页面。
- **讨论过的方案**（四个关键岔路口，均给推荐项）：
  1. 风格：活泼卡通（多色大色块）/ 柔和渐变+玻璃拟态 / **精致蓝系（保留现有蓝青 tokens 只升级精致度）**。
  2. 场景预告：在开始页展示真实对话场景缩略图 / 纯装饰抽象图。
  3. 动效：丰富（入场+悬停+吉祥物浮动）/ 微妙 / 无。
  4. 依赖：纯 CSS + 内联 SVG（零安装）/ 引入动画库（framer-motion）。
- **用户决策**：精致蓝系 + 场景预告条 + 丰富动效 + 纯 CSS/内联 SVG。
- **理由**：精致蓝系改动风险最小且与问题页视觉统一（不破坏“开始页与问题页共用 tokens”约束）；场景缩略图让学生一眼知道今天聊什么；丰富动效提升活泼度但靠纯 CSS 实现避免增体积；失败静默隐藏预告条且不动选场逻辑，保证纯展示层改造。

## 2026-09-17 · v0.3.2 启动页活泼化

- **背景**：启动页太工程素（学生教学用太平淡）；选项大卡片怪；年龄小字说明多余；配色与问题页不一致。
- **讨论过的方案**：AI 给出 Hero 三选一（卡通渐变/场景图预览/极简标题）、选项三选一（小胶囊/紧凑列表/缩小卡片）、Logo 三选一（emoji/简单SVG/暂不做）、额外想法多选（三步玩法/题数预告/鼓励语/都不加）。
- **用户决策**：
  1. Hero 用卡通渐变（渐变横幅+大Title+副标题，与问题页蓝系一致）。
  2. 选项用小胶囊 pills（年龄只给选项不给说明；小字说明只在题型下保留）。
  3. Logo 用简单 SVG 定制（对话气泡+笑脸，零外部资源）。
  4. 额外只加三步玩法说明（Look/Say/Score），题数预告与鼓励语暂不做。
- **理由**：学生端要活泼但不能增依赖增体积；配色复用问题页 tokens 最省且统一；年龄小字对选型无帮助只留题型处；三步玩法让学生一眼懂流程。

- **用户决策**：
  1. 命名用纯英文 option（内部 `grounded/open`），下方小字英文解释区别（Picture-only / Beyond-picture too）。
  2. 初分类暂定（scene01 grounded×7 + open×6；scene02 grounded×8 + open×8），判定标准沉淀为 `docs/问题分类提示词模板.md` 供新场景复用。

## 2026-09-15 · v0.2.7 STT 连续录音（停顿不断开 + 追加续录）

- **背景（用户实测反馈）**：学生回答复杂问题（L2-L4 长答案）时说话中间要想一会儿，但 STT 停顿 ~1 秒就自动结束录音；再次点录音，新识别结果**直接覆盖**已录文本。简单题尚可一气呵成，复杂题几乎无法完成。
- **根因**：`asrService.ts` 写死 `continuous=false`（Web Speech API 无静音容忍参数可调），且 `onResult` 每次整体替换文本框。
- **讨论过的方案**：AI 提议"continuous + 实时上屏 + 未停止时自动重启续录"，就两个体验点征求意见。
- **用户决策**：
  1. 按停止后再录音 → **追加**（英文空格连接）+ 提供"🗑 清空重说"按钮（不选"无按钮纯追加"：孩子说砸了需要一键重来；不选"保持覆盖"：正是要修的痛点）
  2. 录音过程**实时上屏**（不选"结束才出文本"：孩子有"被听到"的确定感）
- **附带说明**：Safari/iPad 对 continuous/interim 支持不全（只出最终文本），但自动重启机制同样生效，退化为"停顿后自动续录"；自动重启连续失败 5 次才真正报错（有成功识别即重置计数），避免死循环。
