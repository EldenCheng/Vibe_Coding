# 讨论记录

> 记录关键决策的来龙去脉（背景 / 备选方案 / 最终决定 / 理由），最新决策在顶部。

## 2026-09-20 操作组织：automations/ 一文件一操作，编号 + 名称双标识

**背景**：v0.1 把入口脚本直接放在根目录。用户预判以后会加很多不同的自动化操作，根目录会失控，
希望有一个统一入口，既能指定单个操作，也能指定一个范围批量执行。

**备选方案**：
1. 根目录继续堆脚本，靠 `main.py` 里的 if/elif 分发——加一个操作改一次入口，容易漏。
2. `automations/` 一文件一操作，注册表用 `pkgutil` 自动发现，入口只认注册结果。
3. 每个操作一个子目录（`automations/screenshot/`），便于放附属文件，但当前没这需求。

**决定**：方案 2，目录名用 `automations/`。操作同时有编号（`1`）和名称（`screenshot`），
两者都能在命令行里指定。

**理由**：新增操作只往目录里丢一个文件，不碰入口代码；名称给人读，编号方便批量指定范围。
方案 3 等真出现"操作要带资源文件"时再升级，现在多一层目录只是噪音。

## 2026-09-20 编号写死在操作文件里，且永不复用（配编号台账）

**背景**：编号要能写进 `1-10` 这种范围表达式，就必须稳定。

**备选方案**：
1. 编号写死在每个操作文件的 `number = 2`，启动时校验唯一。
2. 按文件名排序自动编号——省事，但插入或重命名文件会让一串编号漂移。

**决定**：方案 1，并额外用 `config/number_ledger.json` 记录"历史上出现过的 编号 → 名称"。
删掉某个操作不回收编号；把已登记的编号改派给别的操作名会直接报错拒绝启动。

**理由**：自动编号在"昨天 3 号是截图、今天变成别的"这种场景下会静默改变用户命令的含义。
台账让编号成为一次性分配的资产；注册时自动写入，不需要手工记账。

## 2026-09-20 批量执行：默认跑完再汇总，乱序列表按书写顺序执行

**背景**：`run 1-10` 中间某步失败时怎么办；`[5, 2, 8]` 按什么顺序跑。

**备选方案**：失败策略——遇错即停 / 跑完再汇总 / 每个操作自声明是否关键。
执行顺序——按书写顺序 / 一律归并成编号升序。

**决定**：默认跑完整串再输出汇总，另给 `--fail-fast` 供想早停的人显式选择；
顺序严格按解析结果，区间和 `all` 是编号升序，显式列表就是你写的顺序。

**理由**：巡检式的自动化各步往往互相独立，中途停掉反而丢信息；而"能表达先后依赖"
（先 `connect` 再 `screenshot`）正是列表写法的价值，重排会把它抹掉。
自声明关键性会让每个操作多一个概念，当前无真实需求，不做。
列表里写重复项就真的执行那么多次（`[2, 2]` 截两张），这是有意的连拍能力。

## 2026-09-20 操作参数走 config/params.json，不进命令行

**背景**：截图操作有"截完打开""复用现有连接"这类个性化开关。一次 `run 1-10` 时这些参数归谁？

**备选方案**：
1. 参数平铺在命令行，启动时校验不同操作不能重名参数。
2. 参数全进 `config/params.json`，每个操作读自己那一段。
3. 取消操作级参数，只留无参操作。

**决定**：方案 2。命令行只保留 `-d/--device`、`-c/--config`、`--fail-fast` 三个全局参数。
原 `--open` 迁成 `screenshot` 段的 `open_after`，`--no-connect` 反向迁成 `reconnect`，另加 `show_info`。

**理由**：用户提出——参数都塞命令行入口，多项操作一起执行时没法传。
配置文件方案让参数归属天然明确（一段一操作），以后要按设备区分参数也有位置挂。
配套约定：操作用 `ctx.param()` 取值，写了不认识的键会在运行时提示，避免拼错后静默失效。

## 2026-09-20 调度骨架独立成 framework/，adb_kit/ 保持纯能力层

**备选方案**：注册表和调度也放进 `adb_kit/`（少一个目录），或新开 `framework/`。

**决定**：新开 `framework/`。依赖方向固定为 `automations/` → `framework/` + `adb_kit/` → 标准库。

**理由**：`adb_kit` 不该知道"操作"是什么，`framework` 也不该知道 adb 是什么；
以后若有不走 adb 的自动化（抓网页、读文件），同一套注册与调度可以直接复用。

## 2026-09-20 旧入口彻底删除，不留薄壳

**背景**：v0.1 的 `connect.py` / `screenshot.py` 已经能用，是否保留成转发壳。

**决定**：删除。`一键截图.bat` 改成调用 `py main.py run screenshot`。

**理由**：项目才一天，没有历史习惯和外部快捷方式要迁就；留两套入口只会让"该改哪个文件"变模糊。

## 2026-09-20 首个功能范围：设备信息 + 连接 + 截图

**背景**：项目起步，需要一个能通过 adb 控制局域网电视盒子的自动化工具集，但具体自动化场景尚未确定。

**备选方案**：
1. 先搭完整骨架（配置 + adb 封装 + 按键/启动 App/截图全套能力）。
2. 骨架之外再加一个可配置的场景步骤引擎。
3. 只做最小可用：设备信息文件 + 连接 + 截图 + 一键 bat。

**决定**：采用方案 3。

**理由**：用户明确指定第一步内容。在没有真实盒子连通过之前，过度封装的 adb 抽象可能与实际设备行为不符；先跑通"连得上、截得到"，再按真实需求扩展。

> v0.2 变更：跑通之后确实按预期扩展成了操作集合，方案 1/2 里的一部分（骨架、封装层）在重构中补上了。

## 2026-09-20 adb 来源：系统全局安装

**背景**：本机 PATH 中没有 adb。

**备选方案**：项目内置 `tools/platform-tools`（不污染系统环境）/ 系统全局安装。

**决定**：系统全局安装，脚本调用命令名 `adb`。

**理由**：用户选择。同时在 `config/devices.json` 保留 `adb_path` 字段作为退路，adb 未进 PATH 时可填绝对路径，无需改代码。

## 2026-09-20 形态：Python 脚本集，配置文件用 JSON

**背景**：仓库内其它项目均为独立 Python 脚本 + 配置文件，无统一构建系统。

**决定**：沿用同一风格。设备信息用 `config/devices.json`（而非 `config.py`），入口脚本放根目录，可复用能力收进 `adb_kit/` 包。

> v0.2 变更：入口脚本不再堆在根目录，改为 `main.py` 单入口 + `automations/` 操作目录；`adb_kit/` 定位收窄为纯 adb 能力层。

**理由**：JSON 是纯数据，用户改设备信息时不需要理解 Python 语法，也不会因语法错误导致脚本崩溃；`adb_path`、输出目录等杂项也一并放进同一个 JSON，配置入口唯一。

## 2026-09-20 无真机情况下如何验证：selftest.py 用假 adb 跑离线自检

**背景**：本机尚未安装 adb，也无法在开发期连到真实盒子，但截图链路有一堆容易写错的地方（PNG 二进制、exec-out 兼容、命名）。仓库其它项目都没有测试，这是第一个例外。

**备选方案**：
1. 等装好 adb、连上真机再手动验证。
2. 写单元测试（pytest），需要额外依赖。
3. 写一个零依赖的 `selftest.py`，monkeypatch 掉 `subprocess` 调用点，用假 adb 应答覆盖各分支。

**决定**：方案 3。

**理由**：零依赖、`py selftest.py` 一条命令跑完，符合本仓库"无统一构建/测试系统"的现状。它验证的是封装逻辑的分支正确性，不替代真机连通性验证——后者仍需在盒子上跑 `connect.py`。它也已经抓到两个真实 bug：`_repair_png` 的 CRLF 还原分支原本是死代码，LF 结尾的 `.bat` 无法被 cmd 解析。

## 2026-09-20 截图命名：日期_时间，多设备时加设备名前缀

**背景**：用户要求文件名为"日期\_时间"，存放到 `screen_shot/`。

**决定**：单设备时用 `2026-09-20_163012.png`；当配置了多台设备时自动加设备名前缀。

**理由**：纯"日期\_时间"在多设备场景下同秒截图会互相覆盖。前缀只在真的有多台设备时才出现，单设备完全遵守用户原始要求。
