# 统一下载管理器 项目设计文档

> 版本：v0.1.0（设计稿）
> 关联需求：`Design/需求提示词.txt`
> 设计目标平台：后端可运行于 **Windows** 与 **macOS**；典型用法是 **Mac 上跑后端**，Windows 浏览器通过局域网访问控制
> 前端/后端语言：后端 Python（≥3.9），前端原生 HTML/CSS/JS

---

## 1. 项目概述

把已有的独立下载器（e-download、fetech_xs、m3u-get-down，**v0.5.0 起新增 http-download**）用一个 Web 管理器统一起来：
在浏览器里选择下载器 → 填参数 → 配置 → 提交任务 → 看实时输出 → 在下载列表里查进度、校验、重下失败项。

**核心原则：不重写下载逻辑。** 管理器只做「参数拼装 + 进程托管 + 输出转发 + 状态读取 + 界面」，
真正的下载工作仍然由各下载器以子进程方式完成。这样各下载器保持独立可单独使用，管理器坏掉也不影响它们。

## 2. 需求与设计决策记录

| 编号 | 事项 | 结论 | 决策来源 |
| --- | --- | --- | --- |
| D1 | 后端 Web 框架 | ~~Flask + waitress~~ → **纯标准库 `http.server`（ThreadingHTTPServer + 有界线程池）** | 用户最初选 Flask + waitress；实现阶段实测本机 pip 无法访问 PyPI，且三个下载器都只用标准库。改用标准库后依赖为零、长期运行的版本风险最小。详见 §20 变更记录 |
| D2 | 前端形态 | 原生 HTML/CSS/JS 单页，无构建工具链（由标准库服务器托管静态文件） | 用户确认 |
| D3 | 配置存储 | **直接读写各下载器自己的 `config.json`**，不另存副本 | 用户确认 |
| D4 | 视频下载器四种方式的深度支持 | **混合分阶段**：一期用 subprocess（get 直链 / batch / sniff 列候选）；二期再考虑给 m3u-get-down 加 HTTP API + 候选推送 | 用户确认 |
| D5 | 访问保护 | **URL 令牌 + localStorage 永久有效**，支持局域网访问 | 用户确认 |
| D6 | 并发约束 | 每种下载器同时只允许 1 个任务；三种下载器之间可并行 | 用户原始需求 |
| D7 | 服务端口 | **8765**（高位端口，免 sudo、不占系统端口） | 用户确认 |
| D8 | 防休眠 | 做，默认开启（macOS 用 `caffeinate`，Windows 用 `SetThreadExecutionState`） | 用户确认 |
| D9 | fetech_xs 输出目录不一致 | 给下载器加 `output_dir` 配置项 + `--output-dir` 参数，**默认指向各自项目下的 `Download/`**（与现存数据位置一致，不搬数据） | 用户确认 |
| D10 | 首期附加功能 | 磁盘剩余空间 + 实时速度汇总；任务完成通知 | 用户确认；产物打包下载、任务历史记录**本期不做** |
| D11 | 服务重启时的遗留进程 | **强制回收**，状态标记 `interrupted`，界面提供「续跑」 | 用户确认 |
| D12 | 运行方式 | 前台运行，带终端窗口（不做开机自启服务） | 用户确认 |
| D13 | 部署结构 | 四个目录**平级**放在同一父目录下（Mac 上建议把 `m3u-get-down` 的 `&` 去掉） | 用户确认 |
| D14 | 第四个下载器：通用 HTTP 直链 | 新增平级项目 `http-download`（仅依赖 requests），支持断点续传/多线程分块/限速/SHA256・MD5 校验/代理/重名处理；产物为**平铺文件** + `.progress` sidecar；前端零改动（数据驱动自动出标签页） | 用户确认 (2026-10-08) |

## 3. 现有下载器接口分析（适配层设计依据）

> 本章全部结论都来自对现有代码的逐行核对，是适配层的唯一事实来源。
> **注意：各下载器都倾向「退出码 0」表示"进程正常跑完"，部分失败（甚至全部失败）仍可能返回 0。
> 因此任务状态判定一律以进度文件为准，绝不以退出码判定成功。**

### 3.1 共性

| 维度 | 共性 |
| --- | --- |
| 参数解析 | 三个都是**手写解析**（fetech_xs/e-download）或 argparse（m3u）。e-download / fetech_xs **没有 `--help`**，未知参数会被静默当位置参数或忽略 |
| 配置文件 | 都读**脚本自身目录**下的 `config.json`（基于 `__file__`，与 cwd 无关） |
| 进度文件 | 都在输出目录下写 `progress.json`（m3u 是 `progress.json` + `批量进度.json`） |
| 日志 | 全部 `print` 到 **stdout**；无 logging、无 stderr 输出、无 `--verbose` |
| 编码 | e-download 用 `sys.stdout.reconfigure(utf-8)` 自保；fetech_xs **不自保**，靠 `PYTHONIOENCODING=utf-8`；m3u 未处理 |
| 缓冲 | 都用 print 无 flush，必须用 `python -u` 或 `PYTHONUNBUFFERED=1` 才能看到实时输出 |
| 进度条 | m3u 用 `\r` 单行刷新；另两个无 `\r` |

### 3.2 e-download

| 项 | 内容 |
| --- | --- |
| 入口 | `py download_gallery.py [--range SPEC] [--rd] [--check] <画廊URL>` |
| 新增参数 | **`--output-dir DIR`（本项目新增，默认=脚本目录，保持原行为）** |
| 配置 | `config.json`：`proxy`、`use_mpv`、`request_delay.{min,max}`、`retry.{max_attempts,backoff_base,backoff_multiplier}`、`timeout_page`、`timeout_image`、`headers`、`cookies` |
| 输出目录 | `<output-dir>/<画廊目录名>/`，目录名规则 `[分类][语言]主标题[副标题]`，超长截断；**旧命名兼容**：若旧规则目录已存在则沿用 |
| 现状 | 根目录 2 个画廊 + `Download/` 下 22 个画廊（历史版本遗留）→ **两处都要扫** |
| 进度文件 | `<画廊目录>/progress.json`：`downloaded[int]`、`failed[int]`、`status`、`gallery_url`、`gid`、`token`、`title`、`subtitle`、`total` |
| check/rd | `--check` 扫 `images/` 下 `^(\d+)_` 文件名重建进度（**需联网**，因为要先抓画廊页定位目录与 total）；`--rd` 重试 `failed` |
| 退出码 | 有失败页仍返回 0；参数错误/URL 非法返回 1 |

### 3.3 fetech_xs

| 项 | 内容 |
| --- | --- |
| 入口 | `py download_novel.py [--rd\|--check] <book_id\|章节列表URL>`；EPUB 是**独立第二步**：`py build_epub.py <书名>` |
| 新增参数 | **`--output-dir DIR`（本项目新增，默认=脚本目录，保持原行为）**；`build_epub.py` 同步支持，且需能从指定目录定位书籍 |
| 配置 | `config.json`：`output_dir`、`proxy`、`request_delay.{min,max}`、`retry.{max_attempts,backoff_base,backoff_multiplier}`、`headers` |
| 输出目录 | `<output-dir>/<书名>/` |
| 现状 | 根目录**没有**书；5 本书全在 `Download/` 下 → 必须用 `--output-dir` 指到实际位置，否则会从头重复下载 |
| 进度文件 | `<书名>/progress.json`：`book_name`、`author`、`chapters_url`、`chapter_titles{}`、`downloaded[int]`、`failed[int]`、`last_index`、`status`、`total` |
| check/rd | `--check` 扫 `chapters/*.html` 的 `^(\d+)_` 重建；`--rd` 重试 `failed` |
| 特殊风险 | 单章网络超时**无 try 包裹**，会直接让整个进程崩溃 → 管理器需做「崩溃后自动重启续跑」 |
| 退出码 | 部分章节失败仍返回 0 |
| 依赖 | requirements 里有 `ebooklib`，**本机当前未安装**，EPUB 生成会直接 `ModuleNotFoundError` |

### 3.4 m3u-get-down

| 项 | 内容 |
| --- | --- |
| 入口 | `py -m m3u_down {get\|sniff\|play\|batch} <URL> [参数]`，工作目录须为 `m3u-get-down/` |
| 配置 | `config.json`：`concurrency`、`proxy`、`retry_times`、`retry_backoff`、`timeout`、`output_dir`、`download_interval`、`ffmpeg_path`、`insecure`（**导入时加载**，改配置需新起进程） |
| output_dir | 相对 **cwd** 解析（不是脚本目录）→ 管理器必须显式传 `-o` 绝对路径或固定 cwd |
| 进度文件 | 单集：`<out>/progress.json`（切片级）；批量：`<番剧目录>/批量进度.json`：`episodes{URL:{label,status,file}}`；另有 `简介.md` 状态表 |
| check/rd | **没有** `--check`/`--rd`；靠「重跑同一命令」自动跳过已完成集、续传未完成切片 |
| 输出 | 单集 `-o` 未指定时：get→`downloads/<stem>/`（**不扁平**）、sniff→`downloads/<标题>/`、play→`downloads/play_时间戳/`；batch→`downloads/<番剧名>/`，含 `_work/` 中间目录 |
| 退出码 | 0 成功；2 DRM 或 argparse 用法错误；130 中断；1 其它异常。**batch 单集失败被吞，仍返回 0** |
| 硬依赖 | `ffmpeg` 必需；**`playwright` 是顶层 import**——连 `get` 都必须装 playwright，否则 import 就失败 |

#### 四种下载方式的可行性（关键结论）

| 需求叫法 | 子命令 | 终端交互 | 浏览器 | 能否无人值守 |
| --- | --- | --- | --- | --- |
| 直接下载 | `get <m3u8直链>` | 无 | 不需要 | ✅ **完全可自动化** |
| 批量下载 | `batch <列表页> --yes --episodes N` | 可跳过（`--yes`） | 有头，**每集一次** | ⚠️ 可自动跑，但依赖页面自动出流 |
| 嗅探 | `sniff <播放页>` | `--auto N` 可跳过 | **有头**（`headless=False` 硬编码） | ❌ 需页面里点播放 |
| 通过缓存下载 | `play <播放页>` | 无 | **有头** | ❌ 需视频真的播放完整段 |

网页前端**点不到**那个浏览器窗口里的播放按钮，也看不到候选列表 —— 这是四种方式无法全部无损接入的根本原因（决策 D4）。

### 3.5 http-download（v0.5.0 新增，决策 D14）

| 项 | 内容 |
| --- | --- |
| 定位 | 通用 **HTTP(S) 单文件直链**下载（GitHub release、软件站直链等），不抓页面不嗅探 |
| 入口 | `py -u http_download.py [选项] <URL>`；选项：`--output-dir/--proxy/--filename/--sha256/--concurrency/--speed-limit/--overwrite/--header/--max-attempts` |
| 配置 | `config.json`：`output_dir`、`proxy`（留空=读系统代理，**不遮罩**）、`headers`（Authorization/Cookie 遮罩）、`concurrency`、`min_split_mb`、`speed_limit_kb`、`timeout`、`retry.{max_attempts,backoff_base,backoff_multiplier}`、`overwrite(rename/overwrite/skip)`、`auto_verify` |
| 产物形态 | **平铺文件**在 `Download/` 下；工作文件：断点 `<名>.part`、分块 `<名>.part.seg<i>`、坏数据 `<名>.corrupt`、校验 `<名>.sha256` |
| 进度文件 | `Download/.progress/<名>.<url摘要8>.json`：`status(downloading/complete/failed)`、`bytes_done/bytes_total`、`actual_sha256`、`error/note` |
| stdout 锚点 | `文件保存到: <绝对路径>`（成功）、`进度文件: <绝对路径>`（sidecar 位置）—— 适配器定位与判定的第一依据 |
| 退出码 | 0=成功；1=失败（含校验失败）。判定仍以 sidecar 为准，退出码只作失败依据 |
| 列表动作 | 仅「续传/重下」= 重跑同一 URL（下载器自动利用 `.part`/段文件续传）；无分片级失败概念 |

## 5. 适配层设计

### 5.1 统一抽象

```python
@dataclass
class LaunchPlan:
    """一次任务启动所需的全部信息"""
    argv: list[str]          # 完整命令行（含解释器与 -u）
    cwd: str                 # 工作目录（下载器项目目录）
    kind: str                # 'download' | 'check' | 'retry' | 'build_epub'
    hint: dict               # 用于完成判定的线索：输出目录、进度文件路径等

class Adapter(Protocol):
    type_id: str                              # 'ebook' | 'ehentai' | 'video'
    display_name: str
    project_dir: str                          # 下载器项目目录
    def probe(self) -> ProbeResult: ...        # 探测依赖是否满足（python/pip 包/ffmpeg/playwright）
    def config_schema(self) -> dict: ...       # 配置表单结构（字段类型、默认值、敏感标记、说明）
    def read_config(self) -> dict: ...         # 读 config.json（敏感字段标记为已设置但不回传明文）
    def write_config(self, patch: dict) -> dict: ...
    def build_launch(self, form: dict) -> LaunchPlan: ...      # 下载
    def build_check(self, target: dict) -> LaunchPlan: ...     # 校验
    def build_retry(self, target: dict) -> LaunchPlan: ...     # 重下失败项
    def build_extra(self, action: str, target: dict) -> LaunchPlan: ...  # 如 build_epub
    def scan_downloads(self) -> list[DownloadItem]: ...        # 扫描输出目录（点刷新才调用）
    def progress_of(self, item: DownloadItem) -> ProgressInfo: ...
    def finalize(self, task) -> TaskOutcome: ...               # 完成判定（读进度文件）
```

### 5.2 三个适配器的关键实现点

#### e_download.py

- 项目目录：`../e-download`；解释器：项目 python；
- 下载：`py -u download_gallery.py [--range SPEC] [--output-dir DIR] <URL>`
- 扫描：同时扫 `DIR/` 与 `DIR/Download/` 两个位置（历史遗留），判定「画廊目录」= 含 `progress.json` 的目录
- 完成判定：`status == complete` 且 `failed == []` 且 `len(downloaded) == total`；否则 `in_progress`；
  `failed` 非空 → `partial_failed`
- 校验：`--check`；重下：`--rd`（可带 `--range`）
- 配置敏感项：`cookies.*`、`headers.*`

#### fetch_xs.py

- 项目目录：`../fetech_xs`
- 输出目录必须由管理器指定为**实际位置**（默认 `../fetech_xs/Download`），否则会重复下载
- 下载：`py -u download_novel.py [--rd|--check] --output-dir DIR <book_id|URL>`
- EPUB：`py -u build_epub.py --output-dir DIR <书名>`
- 扫描：扫 `DIR/` 下的书目录（含 `progress.json` 或 `chapters/`）
- 完成判定：`status == complete` 且 `failed == []`；另核对 `chapters/` 实际文件数 == `total`（progress 可能滞后）
- **崩溃看护**：进程非正常退出（退出码非 0 且非人为停止）且进度文件显示有 `failed` → 任务标记 `crashed`，
  界面上提供"续跑"按钮（等价于重跑同一命令）；**不做自动无限重启**，避免对站点造成压力
- `ebooklib` 缺失时，EPUB 按钮置灰并提示安装命令

#### m3u_down.py

- 项目目录：`../m3u-get-down`；cwd 必须是它（`output_dir` 相对 cwd 解析）
- 一期支持的形态：
  - `get <m3u8直链>`，可选 `--referer/--user-agent/--cookie/--quality/--variant-index/-o`
  - `batch <列表页>` + `--yes` + `--episodes` + `--line` + `--pick` + `--interval` + `-o`
  - `sniff <播放页> --no-download --auto N --max-wait S`（仅列候选，用于拿直链）
- **`--line` 与 `--pick` 的区别（极易混淆，UI 已分开两个输入框）**：
  - **`--line`（选线路）**：仅**内嵌播放器站点**（mvffm 等，页面 JS 直接含“线路×剧集”直链）
    有效，指定**主线路**（序号或名称，如 `22` 或 `FLV 22 推薦31`），其余线路作为 `alts` 自动 failover；默认第 1 条。
  - **`--pick`（选候选）**：仅**非内嵌站点**（需开浏览器嗅探）有效，指定**每集自动取第 N 个捕获到的 m3u8 候选**
    （占位页面可能捕获到广告 / 不同清晰度 / 音轨等多个流），默认 1。**它不选线路**。
- `-o` 一律由管理器传**绝对路径**，并默认指向 `m3u-get-down/downloads`
- 完成判定：batch 读 `批量进度.json`，统计 `done`/`failed`/总数；单集读 `progress.json` 的切片完成度 + 成品文件是否存在
- 校验/重下：复用「重跑同一命令」（`--rd` 不支持）→ 按钮文案为"续跑/补下失败集"
- UI 对 `sniff`/`play` 明示：**需要 Mac 本机屏幕前操作**（会弹出浏览器窗口），远端只能看日志

#### http_download.py（v0.5.0 新增，决策 D14）

- 项目目录：`../http-download`；入口：`py -u http_download.py [选项] <URL>`
- **产物是文件不是目录**：`Download/` 平铺；下载列表「点刷新」列出普通文件
- 状态来源（两路）：stdout 锚点行 + `Download/.progress/` 下的 sidecar
  （`bytes_done/bytes_total/status/actual_sha256/error`）；定位失败时按 URL 反查 sidecar 兜底
- 完成判定：sidecar `status == complete` → completed；`failed` → failed（带错误原因）；
  进程退出码非 0 一律 failed；锚点与 sidecar 都找不到 → completed(未核实)
- `DownloadItem` 为**文件条目**（`base.py` 已支持单文件取 `st_size`），进度用 MB（1 位小数）渲染进度条，
  小文件/失败时给 summary 文本
- 配置敏感项：仅 `headers.Authorization`、`headers.Cookie`；`proxy` 沿用「不遮罩」约定

### 5.3 章节/分片级进度与「重下失败项」

每种下载器都从自己的进度文件读出失败项的**可读标识**，供下载列表展示与重下：

| 下载器 | 失败项标识 | 展示 |
| --- | --- | --- |
| e-download | 页码 int | `第 24, 25, 88 页` |
| fetech_xs | 章节索引 int | 用 `chapter_titles` 映射成 `第5章 …`，无标题时显示索引 |
| m3u batch | 剧集 URL + label | `第03集、第07集` |
| http 直链 | 无（失败即整个文件） | 显示错误原因；「续传/重下」重跑同一 URL 自动续传 |

重下按钮 = 对应该下载器的 `--rd`（或 m3u 的续跑），后端把原任务的 URL/输出目录一并带上。

## 6. 任务状态机与完成判定

```
  queued ──► running ──┬──► completed        退出码 0 且进度文件显示全部完成
                       ├──► partial_failed   退出码 0 但进度文件有 failed 项
                       ├──► failed           退出码非 0 且非人为停止
                       ├──► crashed          解释器异常退出（如 fetech_xs 单章超时崩溃）
                       ├──► stopped          用户点停止（SIGTERM / taskkill /T /F）
                       └──► interrupted      服务重启时发现的遗留 PID，已强制回收
```

**判定优先级**（严格按此顺序）：

1. 人为停止/服务重启回收 → `stopped` / `interrupted`（不看退出码）
2. 退出码 != 0 → `failed`；若 stderr/日志里出现 `Traceback` 且进度文件有 failed → `crashed`
3. 退出码 == 0 → 读进度文件：
   - 全部完成且无失败 → `completed`
   - 有失败项 → `partial_failed`
   - 进度文件缺失 → `completed_with_warning`（完成但无从核实）

> 为什么不能只看退出码：e-download 与 fetech_xs 即使大量失败也返回 0；m3u 的 batch 单集失败被吞掉同样返回 0。

## 7. 配置文件管理（决策 D3）

- 管理器**直接读写**各下载器自己目录下的 `config.json`，任务运行时读到的就是这一份，天然一致。
- 写入策略：**只覆盖 UI 提交的字段**，保留文件中其它未知字段（避免抹掉 `_readme` 之类）；
  dict 类字段做**合并更新**而不是整体替换（与下载器自身的浅层合并语义一致）。
- 写前校验类型（int/float/bool/str/dict）；不合法直接拒绝并返回原因，不写坏文件。
- 写前备份：`config.json.bak.<时间戳>`，UI 提供"恢复上一份备份"。
- **敏感字段遮罩**（重要）：`cookies.*`、`headers.Authorization` 等，
  GET 只返回 `{"__set__": true}`，前端显示为「已设置」的密码框；提交时留空表示不修改。
  （e-download 现在的 `config.json` 里有明文的 e-hentai `ipb_member_id` / `ipb_pass_hash`，必须按此处理。）
  **`proxy` 不在其列**（见 §20.10）：代理按各工具的惯例是普通配置，遮罩它会让
  「已设置时留空=不修改」，导致 UI 上无法清空代理。
- 每个配置项都要有中文说明与默认值，UI 折叠面板里逐项渲染。

## 8. 实时输出与日志

- 子进程启动方式：`[python, "-u", ...]` + 环境变量 `PYTHONIOENCODING=utf-8`、`PYTHONUNBUFFERED=1`、`PYTHONIOENCODING` 兜底。
  （fetech_xs 会打印 `✓`/`✗`，在 GBK 控制台下会 UnicodeEncodeError，这是它文档要求设 `PYTHONIOENCODING` 的原因。）
- 读取：两个线程分别读 stdout/stderr，用 `errors="replace"` 解码，**永不因编码问题崩溃**；每行标注来源（`out`/`err`）。
- **读管道必须用 `read1()` 而不是 `read(n)`**（血的教训，见 §20.11）：`Popen` 默认给的
  `BufferedReader.read(n)` 会阻塞到凑满 n 字节或 EOF，会让「每秒一行」的下载器输出
  攒成 4KB 才喷一次，页面上表现为「文件在下载但输出区一直没动静」。
- `\r` 处理：收到的数据按 `\r` 与 `\n` 都切分；`\r` 结尾的片段作为"覆盖当前行"的事件推送给前端，
  前端用同一个 DOM 行原地替换 → 进度条正常刷新，而不是刷满屏。
- 存储：内存环形缓冲（每任务默认保留最后 2000 行）+ 同时追加写 `data/logs/<任务ID>.log`（完整不截断）。
- 分发：SSE（`text/event-stream`），事件类型：`log`、`progress`、`status`、`notice`、`heartbeat`。
  每个任务一个频道；输出区可切换"跟随最新/暂停跟随/清屏/下载日志"。
- 注意 m3u 的 `get/sniff/play` 在**自己目录**下也写 `progress.json`，后处理会删掉它；若用 `--keep` 则保留。

## 12. 安全设计（决策 D5）

- 监听 `0.0.0.0:8765`，局域网内任何设备都能打开 → **必须有令牌**。
- 令牌：管理器 `config.json` 中 `access_token`（首次启动自动生成 32 位随机串并打印到控制台）。
- 校验：`X-Auth-Token` 头，或 `Authorization: Bearer`，或 `?token=`（用于首次进入）；
  比较用 `secrets.compare_digest` 防时序攻击。静态资源与 `/api/health` 免鉴权（否则引导页无法加载）。
- 前端把令牌存 `localStorage`，**永不过期**（符合需求 8），并在页脚显示"退出/清除令牌"。
- 额外防线：
  - `server.host` 可改为 `127.0.0.1` 完全禁止外部访问；
  - `server.allowed_cidrs` 可选网络白名单，非白名单来源直接 403；
  - 记录每次任务创建的对端 IP 到日志，便于审计。
- 不做用户管理（决策来自需求 8），但令牌可随时在配置里更换。

## 13. 长期稳定运行设计

需求里明确"下载时间长、服务长期不关不重启"，据此设计：

1. **进程树回收**：Playwright 浏览器、ffmpeg 都是子进程。停止任务时必须杀整棵树
   （Windows：`taskkill /PID <pid> /T /F`；macOS：`os.killpg` + `SIGTERM` 后超时 `SIGKILL`）。
   统一用 `psutil` 实现，避免平台分支逻辑散落。
2. **子进程组**：POSIX 下 `start_new_session=True` 建立新进程组；Windows 下 `CREATE_NEW_PROCESS_GROUP`。
3. **服务重启后的遗留进程**：启动时读 `data/tasks.json`，对标记为 `running` 的任务：
   若 PID 仍存活，**强制回收**（因为我们已失去它的输出管道，无法再管理），状态改 `interrupted`；
   界面上给"续跑"按钮 —— 三个下载器都支持重跑续传，不会白下。此行为在启动日志与 UI 中明确提示。
4. **内存可控**：日志内存缓冲有上限（环形），完整内容落盘；SSE 客户端断开要正确清理订阅，
   避免长期运行后订阅者泄漏（用 Flask 的生成器 + `try/finally` 取消注册）。
5. **任务记录**：`data/tasks.json` 原子写（写临时文件 + `os.replace`），限制保留最近 N 条。
6. **日志文件轮转**：单任务日志超过 `log.max_mb` 后截断保留尾部；`data/logs/` 超过 `log.keep_days` 的清理。
7. **不使用 Flask 开发服务器**：生产用 waitress（决策 D1）；`debug=False`，禁用重载器。
8. **防休眠**（决策 D8）：启动时按配置开启，`caffeinate -i -w <pid>`（macOS）/ Windows `SetThreadExecutionState`；
   任务全部结束且 `sleep_guard.when == "idle"` 时释放。平台不支持则只记日志不报错。
9. **异常兜底**：后台线程统一包 `try/except` 并写管理器日志，绝不让一个任务的异常拖垮服务。
10. **启动自检**：`/api/sysinfo` 暴露 `ffmpeg`、`playwright`、`ebooklib`、各 python 可执行文件是否可用，
    缺失时在对应标签页给出明确安装提示，而不是等任务跑失败。

## 14. 跨平台（Windows / macOS）要点

| 事项 | Windows | macOS |
| --- | --- | --- |
| 启动脚本 | `start_server.bat`（经 `pick_python.py` 选解释器，用 PowerShell 调 `SetThreadExecutionState`） | `start_server.command`（`python3`，`chmod +x`，`caffeinate`） |
| Python 探测顺序 | 配置 `python_exe` →（free-threading 时）同版本 GIL 构建 → 管理器同环境 → `py`/`python`；`pick_python.py` 与 `backend/config.py` 单一来源 | 配置 `python_exe` → `python3` |
| 编码 | 全程 `utf-8` + `errors="replace"`，避免 cp936 崩 | 默认 utf-8 |
| 进程树终止 | `taskkill /T /F` | `killpg(SIGTERM)` → 超时 `SIGKILL` |
| 防休眠 | `SetThreadExecutionState(ES_CONTINUOUS\|ES_SYSTEM_REQUIRED)` | `caffeinate -i` |
| 路径 | 用 `pathlib`；配置里的路径在 UI 里按当前平台展示 | 同 |
| 文件名合法性 | 下载器自身已处理；管理器展示时只读不改名 | 同 |
| 端口占用提示 | 启动时检测 8765 被占则明确报错并提示改配置 | 同 |

> 管理器只在 Mac 上跑、Windows 只开浏览器，所以「下载器项目目录」的路径是 Mac 上的路径，
> 由管理器的 `config.json` 配置，UI 上不做路径输入（避免跨平台路径混用）。

## 18. 已知边界与风险

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 嗅探/播放器模式无法远端交互 | 会弹出 Mac 本机浏览器窗口，需要人点播放 | UI 明确提示；一期只支持"列候选拿直链"和 batch 自动选候选 |
| batch 选错候选 | `--pick` 默认 1，网页端无法看候选列表 | UI 暴露 `--pick`，并把 `简介.md` 的线路信息展示出来 |
| 内嵌站点选错线路 | `--line` 决定主线路，选错会下到别的源 | UI 暴露 `--line`（序号或名称），其余线路自动 failover |
| 退出码不可信 | 三个下载器都可能"部分失败但返回 0" | 一律以进度文件判定 |
| fetech_xs 单章超时崩溃 | 无 try 包裹 | 状态记为 `crashed`，提供续跑 |
| `ebooklib` 未安装 | EPUB 生成必失败 | 自检 + 按钮置灰 + 安装提示 |
| 一个下载器同时只能一个任务 | 三个都写同一份 `progress.json`，并发会互相覆盖 | 每类型串行队列 |
| 服务重启遗留子进程 | 输出管道已断，无法继续管理 | 启动时强制回收 + 状态 `interrupted` + 续跑按钮 |
| 端口/网络 | macOS 防火墙可能拦截 8765 | 启动脚本给出提示与排查步骤 |
| 磁盘空间 | 电子书与视频可能占几十 GB | 磁盘剩余展示 + 低阈值提醒 |
| 下载站点反爬 | 三个下载器都有延迟与重试策略 | **不修改**其延迟与重试逻辑（遵循仓库规范） |

## 20. 实现期变更记录（与原设计的差异）

实现过程中发现的问题与相应调整，均已落进代码：

### 20.1 后端框架：Flask + waitress → 纯标准库

- **原因**：本机环境中 pip 无法访问 PyPI（SSL 拦截），装不上 flask/waitress/psutil；
  且三个下载器本来就只用标准库。
- **决定**：改用 `http.server` + `ThreadingHTTPServer` + 有界线程池（`backend/httpd.py` 自写极简框架：
  路径参数路由、JSON、静态文件、SSE、统一错误）。
- **额外收益**：管理器依赖为零，长期运行的版本风险与升级维护成本都最小 ——
  这与「服务长期不重启」的需求方向一致。
- **代价**：路由/鉴权要自己写（约 250 行），已在 `tests/api_test.py` 里覆盖。

### 20.2 Windows 进程终止：taskkill → Win32 API

- **原因**：实测部分受限环境下 `taskkill /T /F` 会被拒绝（`Access denied`），
  导致「停止任务」失效、可能留下孤儿浏览器/ffmpeg 进程。
- **决定**：Windows 下改用 `CreateToolhelp32Snapshot` 枚举进程树 + `TerminateProcess` 逐个终止，
  **先叶子后根**（顺序很关键：父进程先死会让子进程被系统重新挂到别的父进程，从而找不到）；
  `taskkill` 仅作兜底。POSIX 仍用 `killpg`。
- **验证**：`tests/killtree_test.py`（父子进程一起收掉）、`tests/recovery_test.py`（重启后回收遗留进程）。

### 20.3 产物目录定位：预期目录名 → 三级策略

- **原因**：重跑一个**已存在**的产物（如已下载完的书再执行一次 `--check`）不会产生新目录，
  最初只用「目录快照差集」会定位失败，导致状态被误判成「无法核实」。
- **决定**：`detect_target_dir` 改为三级：① 日志中的明确路径 → ② 目录快照差集（新产物）
  → ③ **按身份反查已有产物**（画廊按 `gid`、电子书按 `book_id` 匹配进度文件）。
- **验证**：实测对已下载完的《玩具》(book_id=35346) 重跑，正确识别为「全部完成，共 17 章」。

### 20.4 敏感字段遮罩：只遮叶子 → 遮整棵子树 + 覆盖未声明字段

- **原因**：最初只把已声明字段里的值换成标记，未在 schema 中声明的敏感字段会经 `extra` 原样回传，
  等于泄漏登录态。
- **决定**：遮罩整棵子树（连键名都不回传，因为「配了哪些键」本身也是信息），
  并对 `extra` 递归剔除敏感键。
- **验证**：`tests/api_test.py` 断言真实 cookie 值不出现在任何回传取值中。

### 20.5 下载器改动范围：只加参数 → 加 `output_dir` 配置项

- **原因**：用户要求把输出目录做成配置项，默认指向各自项目下的 `Download/`。
- **决定**：e-download 与 fetech_xs 新增 `output_dir` 配置项 + `--output-dir` 参数；
  m3u 本来就有 `output_dir`，但**修正了它的相对路径基准**（原来相对 cwd，改相对项目根目录）。
- **默认值变更的兼容处理**：现有数据不搬动。e-download 的适配器会同时扫描
  项目根目录与 `Download/` 两处（历史遗留），fetech_xs 默认值与现存 5 本书的位置对齐，
  所以原有效果可直接续传。

### 20.6 其它实现细节

- 三个下载器读 config.json 时不再丢弃未知字段（原来只保留已知键，会把管理器写入的配置抹掉）。
- 日志读取强制 `errors="replace"`：本机默认 `py` 是 3.14t free-threading 版，
  跑含 lxml 的脚本会往 stderr 打 `RuntimeWarning`，不能让编码问题把日志线程打挂。
- `tests/` 下的脚本不使用系统临时目录（部分受限环境禁止写），改用项目内 `data/` 临时子目录。

### 20.7 视频下载器项目目录改名（`m3u-get&down` → `m3u-get-down`）

- **原因**：`&` 在 shell 里是「后台执行」符号，`cd`、启动脚本、定时任务里都要额外转义，
  是持续的踩坑源。应用户要求本次一并改名。
- **影响分析结论：对代码零影响**。依据：
  - 包名是 `m3u_down`，与目录名无关；
  - 项目根目录由 `Path(__file__).resolve().parent.parent` 推导（`m3u_down/config.py`），自动跟随；
  - `config.json` 也按 `__file__` 定位，不依赖目录名；
  - 全仓库检索确认**没有任何代码把目录名当字符串或路径使用**，只有文档与外部配置引用它。
- **需要同步修改的地方**（均已改）：
  1. `download-manager/config.json` 的 `projects.video.dir`（唯一真正的路径引用）；
  2. `download-manager/backend/config.py` 的内置默认值；
  3. `AGENTS.md`（顺带补上原先缺失的 `m3u-get-down/` 与 `download-manager/` 两个项目条目）；
  4. 两份项目文档的标题与正文引用、`download-manager` 的三份文档、启动脚本提示文案。
  - **有意不改**：`Design/需求提示词.txt`（用户原始需求原文，属历史记录）。
- **实测验证**：`tests/verify_rename.py` 逐一核对目录存在性、旧目录已消失、内置默认值与
  `config.json`、适配器解析出的项目目录与输出根目录、服务接口返回值、生成的命令行与 cwd
  全部指向新名且不含旧名；并单独验证了从新目录、以及从仓库根目录（cwd 不同）启动时
  `PROJECT_ROOT` / `OUTPUT_DIR` 都正确。

### 20.8 启动脚本的两类坑（用户实测反馈后修复）

**（1）`start_server.bat` 编码导致批处理语法被破坏**

- **现象**：在 PowerShell / cmd 里运行启动脚本，报一串
  `'...' is not recognized as an internal or external command`（中文版：
  `不是内部或外部命令`）；服务仍可能起来，但输出里夹着一堆解析错误。
- **根因**：文件保存为 **UTF-8**，而 `cmd.exe` 解析 .bat 时用的是**本地 OEM 代码页**
  （中文 Windows 为 **GBK/cp936**；实测本机 `chcp` = **936**，**并非 65001**——
  早期文档里“实测 65001”的结论是错的）。UTF-8 中文被按 GBK 解成乱码字节，
  某些序列会把 `rem` 行撕成命令。实测 `chcp 65001`（放首行）与「UTF-8 带 BOM」
  **都不能**解决（BOM 反而让 `@echo off` 这行本身报错）。
- **修复与加固（v0.2.0 修正）**：
  1. 文件仍存为 **UTF-8 无 BOM + CRLF**（与仓库其它文件一致，编辑器 / Git 正常）；
  2. **所有 `rem` 注释一律纯 ASCII（英文）**——注释不显示，用英文零成本；
  3. **中文只出现在 `echo` 行**，流程控制一律 `goto` 标签、不用括号块。
     这样即使将来编码被改错，最多是文字乱码，**不会再破坏语法**；
  4. 备注：若希望**双击后在原生 cmd 窗口**里中文完全正常，可把 .bat 存成 GBK，
     但那样在 UTF-8 编辑器 / Git 里会显示为乱码，故仍以 UTF-8 为准。
- **验证**：`cmd /c start_server.bat --port 8799` 实测解析错误 **0 条**、
  服务用 GIL 构建启动成功、`--port` 参数正确透传。

**（2）PowerShell 里 `start` 不是启动脚本**

- **现象**：用户按直觉敲 `start`，得到 `cmdlet Start-Process 位于命令管道位置 1，请提供以下参数的值: FilePath:`。
- **根因**：`start` 是 PowerShell 内置 `Start-Process` 的**别名**，优先级高于当前目录下的文件；
  PowerShell 也不像 `cmd.exe` 那样按 PATHEXT 补全 `.bat` 扩展名。
- **修复**：文档补齐启动方式；`使用指南.md` 新增整节「三、怎么启动服务」，
  给出三种方式（双击 / `.\start_server.bat` / `py -3 -X utf8 server.py`）、可用参数，
  并专门解释了上面这个别名陷阱。**这是文档缺口而非代码 bug**，但属于「照着文档做不出来」，
  性质上等同于缺陷，已按此对待。

**（3）顺带修掉的依赖自检不一致**

`start_server.command` 原来只检查 `requests/bs4/lxml/playwright`，与适配器自检（已补
`pycryptodome`/`pysocks`）不一致，漏掉的正是会「让命令完全起不来」的 `pycryptodome`。
现已把顶层依赖清单抽成 `m3u_down` 适配器的 `top_level_modules` 单一来源，
`start_server.command` 与之对齐（并额外提示可选依赖 `ebooklib`），避免两处逻辑各自漂移。

### 20.9 启动脚本改名 `start.bat` → `start_server.bat`

用户把两平台的启动脚本改名为 `start_server.bat` / `start_server.command`
（避免 `start` 这个太通用的名字，也避开 PowerShell 内置别名带来的混淆）。
管理器的代码**不依赖脚本文件名**（`server.py` 才是真正入口），
本次只做引用同步：`使用指南.md`、`AGENTS.md`、本文档、脚本内自述提示、
以及 `m3u_down` 适配器里「依赖清单被启动脚本复用」的注释。

### 20.10 代理语义修正：`proxy` 移出敏感字段 + fetech_xs 增补代理

用户对配置界面上那句「留空=不使用显式代理（系统代理仍生效）」提出质疑，核查后确认
**说明文字写错了**，而且背后还有一个功能性缺陷。

- **实测事实（用户直觉的反例）**：控制台子进程**确实**能拿到系统代理，因为
  Python 的 `urllib.request.getproxies()` 在没有代理环境变量时会回落到读操作系统设置
  （Windows 是 `HKCU\...\Internet Settings` 注册表，macOS 是 `scutil --proxy`）。
  实测本机环境变量为空，但 `getproxies()` 仍返回注册表里的 `http://127.0.0.1:10808`。
  三个下载器都用裸 `requests.Session()`（没有一处设 `trust_env=False`），
  只在显式配置时才 `session.proxies = {...}` —— 所以「不设显式代理」≠「直连」，
  而是「回落到系统代理」。原文字里其实是对的，但极易被理解成"直连"。
- **真正的缺陷**：`proxy` 被声明为敏感字段，于是 `apply_patch` 里
  「敏感字段留空 = 不修改」直接生效，前端也把输入框换成 password 且留空不提交。
  结果：**一旦设过代理，UI 上就再也没有办法把它清空**（只能手改 `config.json` 或恢复备份）。
  说明文字「留空=不使用显式代理」与实际行为直接矛盾。
- **决定（用户拍板）**：`proxy` **不再作为敏感字段**（`e_download`、`m3u_down`
  的 `sensitive_paths` 移除 `proxy`；`fetch_xs` 本来就没有）。
  **代价已确认并记录**：若代理 URL 里带 `user:pass@`，它会以明文出现在页面与 API 响应里
  （页面走局域网 HTTP，无 TLS）。用户认为这与各下载工具的惯例一致，可接受。
  改完之后：明文显示、**留空并保存 = 真的清空**（测试已断言）。
- **说明文字重写**：三个适配器统一改成「留空并保存=清空该设置；清空不等于直连，
  requests 会转而读取操作系统代理」，m3u 额外说明嗅探用的浏览器是否走系统代理
  由 Chromium 自己决定（Playwright 只在你显式给了 `proxy` 时才覆盖，且默认不读
  `HTTP_PROXY` 环境变量），并注明 socks5 需要 `pysocks`。
- **fetech_xs 增补代理（用户要求）**：原来它连字段都没有，只能被动吃系统代理。
  场景是「Mac 上的下载器要走 Windows 上装的代理」，必须能显式指定局域网地址。
  - `download_novel.py`：`load_config()` 默认值加 `proxy: ""`，
    `create_session()` 非空时设置 `session.proxies`（与 e-download 同款写法）；
  - `config.json` 加 `"proxy": ""`；
  - 管理器 `FetchXsAdapter.config_schema_data` 加「代理」字段，
    help 里写明跨机要填局域网地址、且代理软件需允许局域网连接（Allow LAN）。
  - 未加 `--proxy` 命令行参数：e-download 也只有配置项，保持一致；管理器本来就是写配置文件。
    需要的话可以后续补。
- **顺带修正**：`m3u-get-down/config.json` 的 `_readme` 原文写「留空=不启用」，
  同样不准确，已与 `m3u_down/config.py` 的 `_DEFAULTS` 一并改为
  「留空=不设显式代理, 此时 requests 仍会读取系统代理」（代码行为未变）。
- **验证**：`tests/smoke.py` 新增两条断言（代理明文回传且 `is_sensitive=False`；
  留空提交后 `proxy` 被真正清空），`tests/api_test.py` 新增一条（真实配置里代理非敏感）。
  五套测试全绿。

### 20.11 输出区收不到下载器输出：`BufferedReader.read(n)` 的阻塞陷阱

用户实测报告：E-Hentai 画廊在正常下载（`Download/` 里图片在增长），
但页面输出区**只有 4 行管理器自己的 `[sys]` 提示**，下载器输出一行都没有。

- **排查路径**（关键是先分清"没采到"还是"没推出去"）：
  1. 看磁盘日志 `data/logs/<task>.log` —— **内容是完整的**，说明采集与落盘都正常；
  2. 直接连 SSE 端点 `/api/tasks/<id>/events` 抓事件 —— **能流式收到**；
  3. 于是对比两类行的时间戳，问题立刻现形：4 行 `[sys]` 的 `ts` 是任务启动那一刻，
     而之后 **127 行 `out` 的 `ts` 全挤在同一个毫秒批次**（相隔 5 分 46 秒）。
- **根因**：`RunningProcess._pump` 用 `stream.read(4096)`。`Popen` 默认 `bufsize=-1`
  给的是 `BufferedReader`，其 `read(n)` 的语义是「**读满 n 字节或到 EOF 才返回**」。
  下载器每 1~2 秒打印一行（几十字节），攒满 4KB 需要好几分钟 —— 于是输出以
  「几分钟一次、一次几百行」的形式出现，看起来就像完全没输出。
  管理器自己的 `[sys]` 行是直接 `bus.append()` 的，不走管道，所以它照常即时显示，
  进一步加深了"输出区是好的、只是下载器不说话"的错觉。
- **实测对照**（子进程每秒一行、共 6 行）：

  | 读法 | 收到时间 / 字节 |
  | --- | --- |
  | `read(4096)` | `[(6.03, 48)]` —— 等于等到进程退出 |
  | `read1(4096)` | `[(0.03,4), (1.03,4), (2.03,4), ...]` —— 逐行即时 |

- **修复**：`reader = getattr(stream, "read1", None) or stream.read`，用 `read1(4096)`。
  它「有多少返回多少」，被切断的半行由 `LineAssembler` 负责拼接
  （该组件的设计本来就考虑了跨块截断，所以这个改动是安全的）。
- **回归测试**：新增 `tests/stream_test.py`，三条关键断言 ——
  第一行 1.5 秒内到达、至少 4 行在进程**仍运行时**收到、各行到达时间被拉开。
  修好前的实现会让这三条全部失败（0 行在运行期间到达、跨度 ≈ 0）。
- **教训**：`subprocess` 管道 + `read(n)` 是个经典陷阱，
  任何"实时日志"功能都必须用 `read1` / `readline` / 非阻塞读；
  单元测试若不真的"慢慢输出"就抓不到它（这也是之前 5 套测试全绿却仍有此 bug 的原因：
  它们的子进程要么秒退、要么输出量大到立刻填满 4KB）。

### 20.12 两个实例同时监听一个端口，把任务记录覆盖没了

在修复 §20.11 需要重启服务时，发现**端口上挂着两个 LISTENING 的实例**，
并已造成实际数据丢失：一个正在下载的任务记录从 `data/tasks.json` 里消失，
界面上连「续跑」按钮都没有。

- **现象（`netstat` 实证）**：
  `TCP 0.0.0.0:8765 LISTENING 29280` 与 `... LISTENING 28172` 同时存在。
- **根因一：端口占用检查在 Windows 上是失效的。**
  原来的 `check_port()` 是
  `socket.setsockopt(SOL_SOCKET, SO_REUSEADDR, 1); socket.bind(...)`。
  **Windows 的 `SO_REUSEADDR` 语义与 Unix 不同**：它允许绑定一个
  **已被别人主动监听**的端口（接近 Unix 的 `SO_REUSEPORT`，而非 Unix 的
  "只避开 TIME_WAIT"）。于是探测永远成功 → 第二个实例照常启动。
  叠加 Python `HTTPServer.allow_reuse_address = 1` 的默认值，
  **真正的监听套接字**也带上了这个选项 → 两个实例都绑成功、都对外服务。
- **根因二：状态文件是"各写各的"。**
  每个实例维护自己的内存任务表，`_save_state()` 只写自己知道的那份
  （`task_manager.py`），两个实例共享同一份 `data/tasks.json` →
  后启动者一存盘就把对方的记录抹掉。这正是任务记录消失的原因。
  注意这只靠"端口冲突"是防不住的：用户完全可能用 `--port 9000` 手动再起一个。
- **修复（用户拍板选 A+B）**：
  1. **端口检查改成两步**：先做**连接探测**（`connect_ex` 能连上就是有人在监听，
     不受 `SO_REUSEADDR` 语义影响），再用**独占方式**试绑一次——
     Windows 不设 `SO_REUSEADDR` 并尽量加 `SO_EXCLUSIVEADDRUSE`；
     POSIX 保留 `SO_REUSEADDR`（那里的它不会抢占活跃监听，且能避开 TIME_WAIT 误报）。
  2. **监听套接字禁止复用**：`_ThreadedHTTPServer.allow_reuse_address = (os.name != "nt")`，
     并在 Windows 上通过覆写 `server_bind()` 设置 `SO_EXCLUSIVEADDRUSE`。
  3. **新增单实例锁 `backend/instance_lock.py`**：`data/server.lock` 记录
     `{pid, host, port, started_at, python}`。启动时若记录的 PID 仍存活 → **拒绝启动**
     并打印占用者信息；PID 已消失 → 视为陈旧锁自动接管；`--force` 跳过检查
     **且不写锁**（测试脚本用，避免误伤真实实例的锁）。
  4. **版本号单一来源**：`config.VERSION`，banner 与 `/api/health` 都读它
     （此前 banner 与 `app.py` 各自写死 `0.1.0`，而变更日志已经到 v0.1.4）。
  5. **抑制客户端断开时的 traceback**：浏览器关闭输出页签会在读请求行阶段
     触发 `ConnectionResetError`，原来会在控制台喷 20 行栈，现按正常现象吞掉。
  6. **`recovery_test.py` 加代码级保护**：它读真实 `tasks.json` 并**另起一个服务实例**，
     那个实例启动时会把所有 `running` 任务当遗留进程强制回收——
     等于会杀掉用户正在跑的下载。现在检测到运行中/排队任务就直接拒绝执行（返回码 2），
     并且它启动的服务带 `--force`。
- **验证**：新增 `tests/instance_test.py`（端口探测必须判定被监听端口为占用；
  有存活实例时拒绝启动并说明占用者；陈旧锁可接管；`--force` 放行且不覆盖已有锁；
  释放后清理锁文件）。并实测"第二个实例启动被拒"：
  `[错误] 无法监听 0.0.0.0:8765 —— 127.0.0.1:8765 上已经有服务在监听`（退出码 1）。
  7 套测试全绿。（另：`Get-NetTCPConnection` 在本沙箱下会静默返回空，
  排查端口占用请用 `netstat -ano`。）

## 21. v0.2.0 设计（任务队列增强 + 目录联动 + 界面重构）

> 触发：用户实测使用后的改进反馈。目标：把「功能做出来了」变成「顺手好用」。
> 四项诉求对应下面 21.1~21.4，界面重构部分参考 qBittorrent / Free Download Manager
> 这类成熟下载器的信息层级（左侧类别、中间传输列表、底部状态/日志、配置退居弹窗）。

### 21.1 任务队列增强与「上一个任务的进程必定关掉」

**现状与缺陷**（读代码核对）：

- 每类型 FIFO 队列**已经存在**（`TaskManager.queues` + `_pump`），但 `_pump` 有并发竞态：
  `create_task` 与 `_on_exit` 可能同时进入 `_pump`，两者都在锁外看到「没有运行中的进程」，
  于是各自弹出一个任务并启动 → **同类型同时跑两个**，正是队列要防的事。
- 任务自然退出后，若下载器留下了孤儿子进程（Playwright 浏览器、ffmpeg），
  没人回收。用户担心「一晚上后台开了上百个控制台进程」就是这一类。

**设计**：

1. **每类型一把 `_pump_lock`**，把「检查空位 → 出队 → 启动」串行化。
   `_start` 改为返回是否成功，失败时由 `_pump` 在持锁状态下继续尝试下一个，
   不再由 `_start` 递归回调 `_pump`（避免锁重入 / 队列卡死）。
2. **子孙进程跟踪与回收**（`runner.RunningProcess`）：
   - Windows 上起一个轻量看护线程，每 2 秒记录一次当前进程的全部子孙 PID
     （`CreateToolhelp32Snapshot` 快照，已有实现）；
   - 无论进程正常退出还是异常崩溃，`_wait` 在收干输出后调用 `reap_children()`：
     Windows 逐个 `TerminateProcess` 仍存活的后代；POSIX 对进程组 `killpg(SIGKILL)`。
   - 回收数量写入任务日志（`[清理] 已回收 N 个残留子进程`）。
   - 这样「开始下一个任务之前，上一个任务的控制台/浏览器/ffmpeg 一定已经关闭」。
3. **队列可视化**：排队中的任务在列表里显示「排队中 · 第 N 位」，行内操作由「停止」
   改为「取消排队」（后端本来就支持：对 queued 任务调用 stop 即出队并标记 stopped）。

> 说明：后端子进程用管道而非新控制台窗口启动（没有 `CREATE_NEW_CONSOLE`），
> 用户看到的「控制台进程」指的是下载器 Python 进程本身。上面的回收按整棵进程树处理，
> 覆盖下载器派生出来的所有子孙。

### 21.2 在文件管理器中打开目录（跨平台）

- 新增接口 `POST /api/system/open {path, select}`：
  - **平台分支**：Windows `explorer`（`select=true` 时用 `explorer /select,<path>` 定位到文件/文件夹）；
    macOS `open`；Linux `xdg-open`。均以子进程后台方式启动，不阻塞请求。
    > v0.4.3 修正：Windows 的 `/select,` 实现有坑（会跑去「文档」），已重写，见 §26.3。
  - **安全校验**：路径必须存在，且解析后位于**某个下载器的扫描根/输出根之内**
    （这些根来自管理器配置，是可信目录），否则拒绝。避免令牌持有者拿它当任意命令执行器。
  - 返回 `{ok, path, opener}`；不可用时返回 400 并说明原因。
- 新增 `platform.can_open_files`（后端是否支持打开文件管理器，供前端决定按钮是否出现）。
- **前端显示条件**：只有当「前端浏览器所在 OS」与「后端所在 OS」一致时才显示按钮
  —— 因为打开的是**后端机器**的文件管理器。若 Mac 后端 + Windows 浏览器，
  打开 Finder 对用户没有意义，此时按钮隐藏并在提示里说明。
- 入口：工具栏「📂 打开下载目录」（打开当前下载器输出根）+ 产物行「📂 打开」。

### 21.3 界面重构（参考 qBittorrent / FDM 的信息层级）

**问题清单**（用户反馈）：

1. 配置这类低频操作占了页面空间，而任务列表这类高频内容被挤到下面（轻重不分）；
2. 三个标签页会随页面上滚，翻到下面就找不到；
3. 输出区是浮动窗，一打开就把参数输入、任务显示遮住；而判断「任务有没有成功开始」
   又必须打开输出，形成来回折腾；
4. 任务队列区、扫描产物区都太长。

- **粘性头部**：顶栏 + 标签栏固定（`position: sticky`），不随内容滚动。
- **两栏工作区**（窄屏自动堆叠）：
  - 左列（主视觉）：**任务与队列**卡片（限高、可展开）+ **已下载的产物**卡片

- **配置改为弹窗**：不再常驻占位。顶栏「⚙ 配置」与右栏按钮都打开同一个模态框，
  内容仍是既有的配置表单（保存 / 重新读取 / 恢复备份不变）。
- **底部输出坞（Dock）**：固定在底部、**不遮挡内容**（内容按坞的高度留出下边距）。
  两档高度：默认「小」（约 6 行）→点「展开」变「大」（约 55vh）。

- **限高 + 展开**：任务表、产物表默认只显示约 6 行，点「展开」切换到高区域。
- 保留三标签页与全部既有功能（参数表单、校验、重下、生成 EPUB、失败明细、通知、磁盘/速度）。

#### 21.4.1 解释器选择：free-threading 构建会让 Playwright 崩溃（实测发现）

装完依赖后做 UI 验证时发现视频下载器仍不可用，定位到一个更隐蔽的环境问题：

- 本机默认 `py` = **Python 3.14t（free-threading，无 GIL）**，而本机**还装有一个同版本号的
  普通（GIL）构建** `...\pythoncore-3.14-64\python.exe`。
- **Playwright 的同步 API 在 free-threading 构建上会段错误**：
  `sync_playwright().start()` 直接崩溃（实测，`-X gil=1` 与 `PYTHON_GIL=1` 都无法规避）；
  异步 API（`async_playwright`）在该构建上正常。
- m3u-get-down 的 `sniffer.py` / `player_capture.py` / `batch.py` **全部使用同步 API**，
  因此嗅探/批量/播放在该解释器下必然崩溃（`get` 直链下载不使用 Playwright）。
- 两个环境的依赖分布也不同：3.14t 有 playwright/pycryptodome/pysocks 但**没有 ebooklib**；
  普通 3.14 有 ebooklib 但原来没有前三个。现已把三个包也装进普通 3.14，
  使**普通 3.14 成为完整环境**（requests/bs4/lxml/ebooklib/playwright/pycryptodome/pysocks 齐全）。
- **处理（`backend/config.py` 的 `resolve_python`）**：当管理器自身跑在 free-threading 构建上、
  且本机存在同版本号的 GIL 构建时，**自动改用 GIL 构建**运行下载器，并在来源说明里写明原因
  （sysinfo 会显示这行说明）。这样三个下载器都不会碰到 Playwright 崩溃，且 ebooklib 也齐了。
  显式配置 `python.python_exe` 时仍以配置为准（不会被覆盖）。
- 实测：以 `py`（3.14t）启动管理器后，`/api/sysinfo` 返回的 worker 为普通 3.14 构建，
  `py -3.14 -c "from playwright.sync_api import sync_playwright; ..."` 成功驱动 chromium。
- 该环境限制也同步记入 `m3u-get-down/Design/项目设计文档.md`（§12.2）、
  `m3u-get-down/使用指南.md`（§1）与 `m3u-get-down/版本变更.md`（手动直跑时要用 GIL 构建）。
- **启动脚本也改走 GIL 构建**：新增 `pick_python.py`（复用 `resolve_python()` 单一来源），
  `start_server.bat` 先调它选解释器再启 `server.py`。这样"管理器自身"也默认跑在 GIL 构建上，
  自动改选就从"兜底"变成"主路径"，行为更可预测；显式配置的 `python.python_exe` 仍优先。
  顺带修掉一个潜伏很久的 .bat 编码 bug（cmd 按 cp936 解析 UTF-8 的 .bat，
  中文 `rem` 注释会被撕成命令），详见 §20.8(1)。

## 22. v0.3.0 设计（新增「yt-dlp 下载」方式 + 单文件产物状态判定）

### 22.1 背景与问题

管理器原有三种下载方式（`get` / `batch` / `sniff_list`）都**无法无人值守地下载"单个视频页"**：

- 单视频页 URL 对应的子命令是 `sniff`（带下载），而它 `headless=False` 硬编码——
  固定弹出有头浏览器，且很多站要人在页面上点一次播放才出流；
- 管理器的 Web 界面点不到那个浏览器窗口 → 无法自动化。所以单视频只能走 `get`
  （自己 F12 复制 m3u8 直链）。当年 "放弃" 的原因是**需要人手**，不是代码实现难度。

m3u-get-down **v0.7.0** 起接入 yt-dlp 引擎：`sniff <B站/YouTube 视频页>` 由下载器
自动路由到 yt-dlp，**纯 HTTP（DASH 音视频分离 + ffmpeg 合并）、不开浏览器、无需点击**，
因此"单个视频页"第一次具备了可入队的无人值守路径。

### 22.2 新增下载方式 `ytdlp`（下拉框第 4 项）

- UI 文案：**「yt-dlp 下载：单个视频 / 合集页面 — B站、YouTube 等自动」**。
- 命令：`py -u -m m3u_down sniff "<url>" --auto 1 -o <输出根> [--insecure]`
  - **必须带 `--auto 1`**：管理器没有 stdin，`sniff` 不带 `--auto` 会阻塞在交互式选候选。
    yt-dlp 路径会忽略该参数（路由在嗅探之前发生），无副作用。
  - `--insecure` 与 `get` 一致，跟随 m3u 自己的 `config.json`。
- `?` 气泡（`_YTDLP_HELP_HTML`）：列出常见支持站点（B站 / YouTube / Twitch / TikTok /
  Vimeo / X 等），给出完整清单链接
  `https://github.com/yt-dlp/yt-dlp/blob/master/supportedsites.md`，
  并写明：清晰度默认「优先 ≤720P」、cookie 默认读 Edge、相关配置在
  `m3u-get-down/ytdlp_sites.json`；合集/番剧整季请改用「批量下载」。
- 非 yt-dlp 站点仍会走有头浏览器嗅探（需桌面点播放）——气泡里注明"不推荐"。

### 22.3 单文件产物的状态判定（顺带修正 `get`）

**问题**：yt-dlp / `get` 的单个成品是**扁平文件** `<输出根>/<标题>.mp4`（没有产物目录、
没有 `批量进度.json`），而 `detect_target_dir()` 只做**目录**快照差集 → 判定为
`completed_unverified`「未找到产物目录，无法核实结果」。

**方案**（`M3uDownAdapter`）：

1. 覆盖 `snapshot_dirs()`：除父类记录的目录名外，另用一个**伪键**（`"@files:" + 输出根`）
   记录输出根下现有 `*.mp4` 文件名——伪键不是路径，`find_new_dirs()` 不会误用。
2. `finalize()`：当 `target_dir is None` 且 `exit_code == 0` 时，用伪键差集找**本次新增的
   mp4**；命中则返回 `COMPLETED`，消息 `完成：<文件名>`，progress 用 `kind=single` 结构
   （与 `progress_of_dir` 的单集分支一致）。
3. 失败（`exit_code != 0`）不做该判定：成品文件只在成功后才会被移出临时目录，
   失败时不会产生新 mp4，仍按原逻辑报 `FAILED`。

顺带收益：现有 `get` 方式提交的单视频任务也能正确显示「完成 · 文件名」，
而不是"已完成(未核实)"。

### 22.4 环境自检

`probe()` 增加 `yt_dlp` 检查；缺失时追加一条**提示性** problem（只影响
「yt-dlp 下载」方式，不阻塞其它命令），安装命令 `py -m pip install -U yt-dlp`。
与现有 `pycryptodome` / `playwright` / `pysocks` 的提示方式一致。

### 22.5 不改的部分（明确边界）

- **不加任何新命令行参数/子命令**（如 `route`）：与"给个 URL 就能下"的既有设计一致；
  是否走 yt-dlp 由下载器内部路由决定，管理器不需要预先知道。
- **下载器代码不改**：`ytdlp_sites.json` 是 m3u-get-down 自己的配置文件，管理器不代理它；
  清晰度/cookie 的调整写进 `?` 气泡说明。
- **`build_action`（续跑）保持不变**：仍是 `batch <url> --yes`。对 yt-dlp 的单个视频 URL，
  它会作为 1 条目的合集重下（能跑通）；对 `get`（m3u8 直链）本就不适用——既有边界，
  本次不扩大范围。
- 已知未修：mvffm batch 那条 `completed_unverified` 是**另一个原因**
  （产物目录在任务开始前已存在 → 目录快照差集找不到"新目录"），本次不处理。

### 22.6 验证方案

1. **离线**：`build_launch(mode=ytdlp)` 的 argv 断言（含 `--auto 1`、`-o`、insecure 分支）；
   `snapshot_dirs → 新增 mp4 → finalize` 返回 `COMPLETED`；无新增 mp4 时仍为 `UNVERIFIED`；
   `probe()` 含 yt_dlp 项。
2. **真站**：管理器跑一个 B站单视频任务（队列 → 完成 → 状态显示"完成 · 文件名"）。
3. **回归**：`get` / `batch` / `sniff_list` 三种方式的 argv 与状态判定不变；管理器测试脚本。

- `?` 气泡（`_YTDLP_HELP_HTML`）补充「两个常见坑」：YouTube（cookie 必须自行导出
  `cookies.txt`，或改用 Firefox；JS 运行时已由下载器 v0.7.1 默认预置）与小红书
  （网址要带 `xsec_token`），并在末尾明确“管理器只放简要提醒，
  **详细以 `m3u-get-down/使用指南.md` §5.5 为准**”——不让管理器重复维护一份会过期的知识。
  另在常见支持站点列表里补上小红书。

**实际验证结果（v0.3.0）**：

- 离线：`ytdlp` argv = `m3u_down sniff <url> --auto 1 -o <输出根>`；
  `snapshot_dirs` 快照含伪键 `@files:<输出根>`；无新增 mp4 → `completed_unverified`，
  新增 mp4 → `completed`（消息 `完成：<文件名>`），退出码 1 → `failed`。

  `probe.yt_dlp = true`；popover 含 `supportedsites.md` 链接与 B站/YouTube。
- 真站（按管理器真实 argv 跑）：B站 `BV1xx411c7mD` → 84MB / 512×384 / 2055s /

- 实测发现（已记入两边文档）：YouTube 在本机需登录 cookie，且新版 yt-dlp 还需

## 23. v0.4.0 设计（油猴脚本：从网页直接把任务交给管理器）

### 23.1 需求与背景

用户日常流程是：在网页上看到想下东西 → 切到管理器页面 → 粘贴地址 → 选类型/填参数 → 开始。
希望改成**在网页原地完成**：油猴扩展图标上出现数字（表示本页有可用脚本）→ 点开选中本脚本 →
点菜单项 → 弹面板确认参数 → 提交，任务自动进队列并开始下载。

### 23.2 已确认的决策（用户 2026-10-01 答复）

| 议题 | 结论 |
| --- | --- |
| 入口形态 | **油猴原生菜单**（`GM_registerMenuCommand`），**不做**页面常驻悬浮球；菜单项只要三项：主入口「下载到管理器…」、「管理器设置（地址/令牌）」、「打开管理器页面」 |
| batch 参数 | **方案 A**：集数 = 快捷芯片 + 文本框；线路 = 下拉「自动 / 自定义」。**不做**"解析预览"接口（列为二期，见 §23.10） |
| 提交反馈 | 只提示「已加入任务 #id（状态）」，**不轮询进度**、**不自动打开管理器页面** |
| 自动预选 | 按域名预选下载器与视频模式（见 §23.5），仍可手动改 |
| 生效范围 | **只匹配已知站点**（`@match` 白名单）；脚本里留一行注释掉的 `*://*/*` 通配备选 |
| 存放 | `download-manager/userscript/` |

> 用户明确问过：连续添加多个任务时，会不会每加一个就开一次管理器页面？
> **不会**——「打开管理器页面」是独立菜单项，只有主动点它才打开；提交任务不打开任何页面，
> 面板提交后**保持打开、表单保留**，可以接着改地址提交下一个。

### 23.3 与后端的关系：零改动

这是本方案的关键取舍：脚本只用**已有的**两个接口，后端与前端一行都不动。

| 用途 | 接口 | 说明 |
| --- | --- | --- |
| 提交任务 | `POST /api/tasks` | body `{type, kind:"download", form}`，返回 `{task:{...}}`；同类型已有运行中任务时返回 `queued` |
| 探活/测令牌 | `GET /api/health`、`POST /api/tasks` 的错误码 | health 免鉴权（只验连通），令牌错误由 401 体现 |

两个必须处理的平台事实：

1. **必须用 `GM_xmlhttpRequest`，不能用 `fetch`**：管理器是纯标准库 HTTP 服务，
   响应里**没有 CORS 头**（`httpd.py` 不设置 `Access-Control-Allow-Origin`），
   在 `e-hentai.org` 这类第三方页面上 `fetch('http://127.0.0.1:8765/...')` 会被浏览器拦掉。
   Tampermonkey 的 `GM_xmlhttpRequest` 走特权通道绕过 CORS，代价是头部要声明 `@connect`。
2. **令牌必须手填一次**：`/api/tasks` 要 `X-Auth-Token`（`auth.py`）。
   油猴读不到管理器页面的 localStorage（跨域），因此面板里有设置区，令牌存 `GM_setValue`，填一次长期有效。

### 23.4 文件与结构

```text
download-manager/userscript/
├── download-to-manager.user.js   # 油猴脚本（单文件自包含，便于拷贝安装）
└── 使用说明.md                    # 安装步骤、@connect 说明、令牌怎么填、常见问题
```

脚本内部分层（单文件但职责分明，纯逻辑与 UI 分离以便用 Node 桩测试）：

| 段 | 职责 |
| --- | --- |
| 常量表 `PRESETS` / `EMBEDDED_SITES` | 域名 → 预选下载器/模式；内嵌播放器站点表（决定显示"线路"还是"候选"） |
| 设置读写 | `GM_getValue/GM_setValue`：管理器地址、令牌 |
| `gmFetch()` | `GM_xmlhttpRequest` 的 Promise 包装（含 401 / 连不上 / 400 的分类错误） |
| 纯函数 | `domainPreset()`、`isValidSpec()`、`buildTaskPayload()`（**可被 Node 测试直接调用**） |
| 面板 UI | Shadow DOM 遮罩面板，见 §23.6 |
| 菜单注册 | `GM_registerMenuCommand` 三项 |

### 23.5 域名 → 预选映射（`domainPreset`）

| 域名 | 预选 | 备注 |
| --- | --- | --- |
| `e-hentai.org` / `exhentai.org` | `ehentai` | 地址预填当前页，软校验 `/g/<编号>/<十六进制token>/` |
| `*.als1004.space`（含 punycode 主机） | `ebook` | 地址预填当前页（adapter 接受完整章节列表 URL） |
| `bilibili.com` / `b23.tv` / `acg.tv` / `youtube.com` / `youtu.be` | `video` + `ytdlp` | yt-dlp 引擎站点 |
| `eacg.net` / `ikanbot.com` / `javdock.com` / `mvffm.net` / `movieffm.net` / `youknow.tv` | `video` + `batch` | 自研引擎站点（`sites/*.json`） |
| 其它（仅当用户自己加了 `@match`） | `video` + `batch` | 兜底 |

地址若本身就是 `.m3u8` 直链 → 强制 `video` + `get`（用户从 F12 复制直链时常见）。

### 23.6 面板设计

- **Shadow DOM**：面板挂在一个 `position:fixed` 宿主上，样式写在 shadow root 内，
  避免被站点 CSS 污染（聚合站/贴吧类页面样式千奇百怪，不用 shadow 迟早变形）。
- 关闭：右上角 × 或 `Esc`；打开时地址栏预填当前页 URL。
- 字段随「下载器 + 方式」显隐（`data-show-for` 机制）：

| 组合 | 字段 |
| --- | --- |
| 电子书 | 地址（预填当前页） |
| E-Hentai | 画廊 URL（预填）+ 页码范围（留空=全部） |
| 视频 · get | 地址（预填）+ Referer / Cookie（可留空） |
| 视频 · batch | 地址 + **集数**（芯片+文本框）+ **线路或候选**（见下）+ 每集间隔 |
| 视频 · yt-dlp | 地址（预填） |
| 设置视图 | 管理器地址（默认 `http://127.0.0.1:8765`）+ 令牌 + 「测试连接」 |

**集数输入（本设计的重点）**：快捷芯片 `[全部] [1-6] [1-12] [1-24]` + 一个文本框。
点芯片 = 把对应文本填进文本框（可继续手改，如 `1-12,15`）；文本框是唯一数据源，
提交前用 `isValidSpec()` 校验（`^\d+(-\d+)?(,\d+(-\d+)?)*$`，空串 = 全部）。
这样"选"和"填"是同一个控件，不需要用户理解两种交互。

**线路 vs 每集候选（替用户判断站点类型）**：这两项互斥——
`--line` 只对**内嵌播放器站点**有效（mvffm、ikanbot，页面 JS 里直接写着线路×剧集直链），
`--pick` 只对**需要嗅探的站点**有效。面板据 `EMBEDDED_SITES` 自动切换：

- 内嵌站点（`mvffm.net`/`movieffm.net`/`ikanbot.com`）→ 显示**线路下拉**：
  `自动（默认：探活第一条存活线路）` / `自定义…`（选中后出现文本框，可填 `22` 或 `FLV 22 推薦31`）。
  之所以默认"自动"：下载器本来就会探活 + 失败自动换线，多数时候不需要指定。
- 其它站点 → 显示**每集选第 N 个候选**（数字，默认 1，等价于原有 `--pick`）。

**javdock.com 提示**：该站在 `sites/javdock.json` 里是 `unsupported=true`（滑动窗口 HLS 防下载），
面板给出醒目提示，但不禁用（由下载器自己拒绝，退出码 3、状态 `failed`）。

**提交后**：结果条显示 `✓ 已加入任务 #a1b2 — 排队中/运行中`（含队列位置时一并显示），
面板不关闭、地址之外的表单值保留，方便连续提交；结果条里给一个「打开管理器」链接，
**只有点它才开新标签页**。

### 23.7 容错与体验

| 情况 | 处理 |
| --- | --- |
| 没配令牌 | 直接切到设置视图，并说明去哪里抄令牌（`download-manager/config.json` 的 `server.access_token`） |
| 401 | 提示"令牌无效"并切到设置视图 |
| 连不上 | 提示"管理器似乎没启动（`start_server.bat`）"，给「重试」按钮 |
| 400 `invalid_form` | 原样展示后端的中文错误（如"画廊 URL 格式不正确"） |
| 请求进行中 | 按钮置灰 + "提交中…"，防连点重复建任务 |

### 23.8 边界（明确不做）

- **不提供 `sniff` / `play`**：这两种模式需要你在桌面上手动点播放，从网页触发没有意义
  （与 §3.4 的结论一致）。
- **不做进度轮询/SSE**：面板只报"已加入"，看进度去管理器页面（用户已确认）。
- **不做页面 DOM 解析**：不从当前页面抓剧集链接——那等于在 JS 里重抄一份 batch 的解析逻辑，
  站点改版要维护两处且结果可能与下载器不一致（用户已确认走方案 A）。
- **不改后端**：脚本只用现有接口，管理器即使回退到旧版本脚本也能用（只受接口字段限制）。

   - `domainPreset()` 对 8 个域名 + 未知域名的返回；

   - `buildTaskPayload()` 各组合生成的 `{type, kind, form}` 与后端 `form_schema` 的键**逐一对应**

## 24. v0.4.1 设计（修复"已完成(未核实)"：产物目录定位）

### 24.1 背景与问题（实测驱动）

真机跑 `ikanbot play/432956` 批量第2-3集（往**已存在**的番剧目录续跑），两集都下好了，
管理器却报 **`completed_unverified`「已完成(未核实)」**。查证发现根因比"目录已存在"更深：

1. `Adapter.detect_target_dir(plan, bus)` 的**第一优先级**是"日志里的明确路径"
   （`locate_from_log(bus)`）；
2. 但 `finalize()` 里调用的是 `self.detect_target_dir(plan)` —— **根本没传 bus**
   （`task_manager._on_exit` 传给 `finalize` 的是 `log_text` 字符串）；
3. 于是 `locate_from_log()` 在三个适配器里**全是死代码**，实际只剩"目录快照差集"可用；
4. 差集对"本次新建目录"有效，对**已存在的产物目录**（续跑、补集）必然落空 →
   落到单文件成品差集（batch 产物在子目录里，找不到）→ `completed_unverified`。
   `Adapter.locate_target()`（唯一会传 bus 的方法）**全项目无人调用**。

### 24.2 本次修复（只动 m3u 适配器，最小风险）

1. **从 `finalize` 直接收到的 `log_text` 解析**（不再依赖 bus）：
   `m3u_down batch` 在进入下载循环前会打印一行
   `[批量] 已选 N 集，输出目录: <绝对路径>`（yt-dlp 批量路径同样打印）→

## 25. v0.4.2 设计（输出坞页签：最新在左 + 一键关闭已完成）

### 25.1 需求（用户原话）

> "下载管理器最下面那个输出控制台信息的那个区域，有一个进程标签栏的，现在那个标签栏好像是
> 最新的控制台消息标签入在右边，但这样放的话，如果我要关闭标签栏就很麻烦了，你帮我改两个东西：
> 1. 最新的标签放左边（就是最近新开始的任务的标签）
> 2. 增加一键关闭已完成（或者已停止的任务）的所有标签的功能"

### 25.2 决策

| 议题 | 决策 |
| --- | --- |
| 页签顺序 | **最新在左**。只反转 Map 的插入顺序来渲染 —— 不重排、不跳动（状态更新时位置稳定） |
| 可关闭范围 | 一切**已结束**的任务：`completed` / `completed_unverified` / `partial_failed` / `failed` / `crashed` / `stopped` / `interrupted`；`running` / `queued` **绝不关闭**；状态还没回来的（`''`）也不关，等状态到了自然可关 |
| 当前页签也被关掉时 | 选**顶替它原来那一格**的页签（视觉顺序里的同一下标，越界取最后一个），比"固定选第一个"更符合直觉 |
| 按钮反馈 | 按钮上带可关闭数量（`关闭已完成 (3)`），没有可关的置灰；点完用 toast 提示"已关闭 N 个页签" |

### 25.3 实现（`frontend/js/logview.js` + `frontend/index.html`）

- `orderedIds()`：`Map.keys()` 反转 → 视觉顺序；`renderTabs()` 按它渲染。
  页签栏是 `overflow-x: auto`，所以"最新在左"顺带解决了用户的痛点：
  **最新那个页签永远在最左边、不用横向滚动就能点到并关闭**。
- 选中页签时只做**水平**滚动把它带进视野（直接调 `els.tabs.scrollLeft`），
  不用 `scrollIntoView()`，免得连带把页面纵向滚动。
- 状态来源：每任务的 SSE **首帧必推一次 `status`**（后端 `last_status = None` 起步），
  所以打开一个已结束任务的页签后，按钮的计数会自动更新，**不需要额外请求**。
- 结构上拆成三个函数：`dropTab()`（只关流 + 从 Map 删，不动选中与渲染）、
  `closeTab()`（单个关闭 + 顺位选中 + 渲染）、`closeFinished()`（批量关闭 + 顺位选中 + toast）。
- 「关闭已完成」按钮放在输出坞右侧动作区（清屏/下载日志旁边）。

### 25.4 边界

- 只动前端；静态文件是**按请求读盘**的（`httpd._serve_static`），所以**刷新浏览器即可生效，不用重启服务**。
- 关页签只是不再显示该任务的日志流，**不影响任务本身**（与原有的 `×` 行为一致）；
  日志仍完整留在 `data/logs/<任务ID>.log`，随时可再从任务列表点「日志」打开。
- `failed` / `crashed` / `partial_failed` 也归入"可一键关闭"：用户原话是"已完成（或者已停止的）"，
  这里按"**不再运行的**"理解（更实用）；若想只关"成功结束的"，改一个 `Set` 即可。

### 25.5 验证

1. 无头桩测试 `tests/logview_test.mjs`（仿 `userscript/test_core.mjs` 的桩法，`node` 直接跑，
   不需要浏览器）：页签顺序（最新在左）、`closeFinished()` 只关已结束的、运行中的保留、
   当前页签被关后选中顺位页签、按钮计数与置灰、关完再开新任务仍排最左。
2. 真机：浏览器打开管理器 → 依次点几个任务的「日志」→ 确认最新在左、按钮计数正确 →
   点「关闭已完成」→ 只剩运行中的页签。


## 26. v0.4.3 设计（自动开浏览器 + 打开目录修复 + 输出坞页签）

不在此节定稿，见 §26.6。

### 26.1 需求

   浏览器没开就顺手打开；

### 26.2 `--open` / `--web`：启动后自动开浏览器

- `server.py` 新增 `--open`（别名 `--web`），默认不开；`start_server.bat` 已经 `%*` 透传，
  所以 `start_server.bat --open` 即可。
- 打开时机：**必须等服务套接字真正 listen 之后**，否则浏览器可能先连、看到"无法访问"。
  为此给 `App.serve_forever(host, port, on_ready=None)` 加了一个 `on_ready` 回调，
  在 `_ThreadedHTTPServer(...)` 建好（已监听）后、`serve_forever()` 阻塞前调用；
  `server.py` 传一个启动后台线程调 `webbrowser.open(url)` 的 lambda。
- URL 固定用 `http://127.0.0.1:<port>/?token=<token>`（本机自用；`host` 是 `0.0.0.0` 时也如此）。
- 无默认浏览器 / 无桌面环境时只打印一行提示，不影响服务。

### 26.3 修复「打开目录」跑去「用户-文档」（`backend/fso.py`）

**根因**：`subprocess.Popen(["explorer", "/select," + path])` 会让 `subprocess` 给整个参数
再加一层引号，命令行实际是 `explorer "/select,路径"`；explorer 解析这个形式失败后
**回退到默认目录（用户 → 文档）**。实测：用 `Shell.Application` 枚举资源管理器窗口，
`/select,` 列表形式不产生目标窗口，反而出现/聚焦「文档」。

**修法**（同样实测验证）：

- **目录**（本下载器的产物绝大多数是目录）：直接 `os.startfile(str(dir))`。
  用户点「打开」要的就是"打开这个目录看内容"，比"在父目录里高亮这个文件夹"更直观；
- **文件且 `select=true`**：用 `ShellExecuteW(None, "open", "explorer.exe", '/select,"<path>"', ...)`，
  把 `/select,"路径"` **原样**作为参数串交给 explorer（不经 cmd、不再被 subprocess 加引号）。
  返回码 `<= 32` 视为失败；
- **文件且 `select=false`**：`os.startfile(str(file.parent))`（打开所在目录，不启动文件）。
- macOS / Linux 分支不变（`open -R` / `xdg-open`）。

### 26.4 输出坞页签：`×` 移到最左 + 标签截断 + 开页签即带状态

- **`×` 移到最左**：`renderTabs` 里页签子元素顺序改为 `[×] [运行点] [标签]`
  （原来 `[运行点] [标签] [×]`）。理由：页签是"最新在左"，标签又长，把关闭按钮放右边
  等于永远在视线外。
- **标签截断**：新加 `.tab-label`，`max-width:340px` + `text-overflow:ellipsis`，
  `title` 保留完整文字。否则一个长 URL 会把页签撑得占满整条坞、别的页签全被挤出去。
- **「关闭已完成」为何曾经是灰的**：该按钮只作用于**已打开的页签**；它的可用性来自
  各页签的 `status`，而 `status` 原先**只在 SSE 收到 `status` 帧后才写入**。
  - 若浏览器没连上 SSE、或状态帧没到，页签 `status` 一直是空串 → 按钮永远灰。
  - 修法：`LogView.open(taskId, label, options)` 新增 `options.status`，
    调用方把**任务列表里已知的当前状态**一并传进来（`tasklist.js` 的「日志」、
    `app.js` 提交/`task_started`、action 任务）。已结束的任务一打开页签，
    按钮**立即**可用，不再依赖 SSE。
  - 实测：`LogView.open(id, label, {status:'completed'})` 后立即查询，
    按钮 `disabled=false`、计数 `关闭已完成 (1)`；点左侧 `×` 后计数归零并再次置灰。

### 26.5 验证

2. `--open`：`App.serve_forever(on_ready=...)` 钩子单测触发；用 `BROWSER=echo` 跑

## 27. v0.5.1 设计（视频产物「续跑」地址回填 + hint 回填）

### 27.1 根因

产物列表行的「续跑/补下」经 `runAction`（tasklist.js）组出
`target.url = progress.gallery_url || extra.url || ""`，再进
`m3u.build_action` 取 `target.url`。此前 `scan()` 给目录产物写死

回填，只有 m3u 没做），`progress_of_dir` 也不设 gallery_url → 一律

下载器侧同样缺一环：`批量进度.json` 只有按剧集 URL 的 episodes，没有入口 URL；
`batch` 不接受裸 m3u8，直链任务无命令可重跑。已由 m3u-get-down v0.11.0
补齐（进度顶层 `list_url` + `resume_hint{line,pick}`、`batch` 裸 m3u8 单集模式，
见其设计文档 §25）。

### 27.2 变更（只动 m3u 适配器 + 通用守门）

- **`_source_url_of_dir(path)`（新增）**：三级回填——
  ① 进度 `list_url`（v0.11.0+ 最准）→ ② 简介.md「来源列表页」行
  （复用 `_SOURCE_RE`，覆盖旧版进度）→ ③ 单集 `progress.json` 的
  `playlist_url`（中断残留；成功后下载器会清掉它）。都没有返回 ""。
- **`scan()`**：目录产物 `extra={"url": _source_url_of_dir(child)}`；
  `progress_of_dir` 的 batch/single-in_progress 分支同步带出 `list_url`
  （API 可观察；前端 `runAction` 本就优先读 `progress.gallery_url || …`，
  这里顺手把 `progress.list_url` 纳入同一优先级）。
- **`is_item_dir` 放宽**：含 `progress.json` 的目录也算产物项——此前单集
  get/sniff 中断残留（无 mp4、无批量进度）不可见，续跑无处可点。

  仍不可见：那不是"一项产物"，重提表单即可，文档注明为边界。
- **`build_action` resume 分支**：
  ① 裸 m3u8 + 本目录 progress 正是该直链残留（含 segments、playlist_url 一致、
  无批量进度）→ `get <url> -o <本目录>` 原地续传；
  ② 其余一律 `batch <url> --yes -o <输出根>`，并按产物目录 `resume_hint`
  回填 `--line`（非空才补）/`--pick`（≠1 才补）——不带回会因重探活换线，
  触发下载器"线路变化→重下"把整季已完成集全部重下；
  ③ 两种分支在配置了 insecure 时都带 `--insecure`（原来续跑没带）。
- **前端 `runAction` 守门（通用，四个下载器受益）**：target 无 url 且无
  book_id/book_arg（如已完成的散文件，本来也无事可续跑）→ 直接 toast 提示，
  不调后端（后端只会报"缺少地址"，信息更差）。
