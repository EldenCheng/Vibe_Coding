# 讨论记录

> 格式：背景 / 备选方案 / 最终决定 / 理由。新决策确认后追加在最顶部。

## 2026-09-24 v0.3.0 功能范围（后处理 / 站点配置 / failover / 自检 / 路线图）

### 决策 1：单集下载（get/sniff）后处理

- **背景**：单集与 batch 后处理不一致——成品永远叫 output.mp4、目录名是整页
  标题、切片/清单/进度文件不清理。
- **备选方案**：① 自动清洗命名 + 默认清理 + `--keep` 保留；② 保持 output.mp4
  只清理；③ 下载前交互询问文件名。
- **最终决定**：方案 ①。
- **理由**：无人值守场景（挂机批量、将来 Web 远程）不能依赖交互；`--keep`
  保留排查现场的能力；清洗名基于站点规则可精准提取《作品名 第NN集》。

### 决策 2：站点配置形式

- **背景**：解析规则按 youknow 硬编码；eacg.net 实测发现其线路1集表残缺
  （第08集缺失且错位），"线路号升序"通用规则在 eacg 会选到坏线路。
- **备选方案**：① sites.json 单文件；② sites/ 目录每站一文件；③ Python
  适配器模块（每站一个 .py）。
- **最终决定**：方案 ②，配置字段为正则/参数（URL 模式、线路偏好、集名/标题/
  简介清洗等），未匹配站点回退通用引擎。
- **理由**：加新站不用改代码；分文件在站点变多后更清爽；通用引擎兜底保证
  未配置站仍可用；Python 适配器留给 JSON 规则确实不够表达的站点再议。

### 决策 3：failover 与完整性自检纳入 v0.3.0

- **背景**：youknow 全季实测 3/18 集瞬时失败（CDN 超时、切片 IncompleteRead）
  需手动重跑；单集失败只能等下次续跑。
- **备选方案**：① v0.3.0 一并实现（换线路重试 + 续跑大小校验 + ffprobe 合并
  校验）；② 留到 v0.4。
- **最终决定**：方案 ①，与站点配置同期实现。
- **理由**：failover 依赖"每集保留备选线路列表"，正好是站点配置层要产出的
  数据，分开做要碰两遍同样的代码。

### 决策 4：eacg.net 真站验证范围

- **备选方案**：① 全流程 + 仅第1集；② 全季 12 集；③ 只测解析。
- **最终决定**：方案 ①。
- **理由**：验证全链路足够；全季约 2.5GB 属重复劳动，用户自行跑。

### 决策 5：Web 远程管理列入远期路线（v0.5+）

- **背景**：用户提出下载机无人值守需求——网页输入网址/改配置、后端下载并
  实时回传日志、失败可远程重下、下载列表管理。
- **最终决定**：v0.4 先做追更/刮削/队列，v0.5+ 做 Web 版；v0.3.0 起核心逻辑
  保持"库函数优先、CLI 薄壳"，进度状态统一落盘（progress.json / 批量进度.json），
  为 Web 后端直接包一层做准备。
- **理由**：架构上先解耦，后续 Web 化不必重构。

## 2026-09-24 v0.2.0 三项功能设计（批量下载相关）

### 决策 1：简介页格式

- **背景**：batch 命令需从列表页抓番剧资讯生成简介页。
- **备选方案**：① Markdown；② HTML（可看封面图）；③ Markdown + 封面图落盘。
- **最终决定**：Markdown（封面用图片链接）。
- **理由**：用户选择；轻量可读可编辑，文本工具即可维护。

### 决策 2：批量下载的选集方式

- **背景**：调研发现列表页同模板链接 348 条（含其他番剧与重复），去重过滤后才
  是真实集数，需防误下。
- **备选方案**：① 列清单确认 + 可输入范围，`--yes` 跳过；② 全自动不确认。
- **最终决定**：确认 + 可选范围（回车全下 / `1-12,15` 范围 / q 退出）。
- **理由**：用户选择；确认步骤防止解析误差导致误下几十集；`--yes` 保留脚本化通道。

### 决策 3：成品文件组织

- **背景**：批量下载多集的目录结构需定义。
- **备选方案**：① 扁平：`downloads/番剧名/第01集.mp4` + 简介.md 同级；② 每集一个子目录。
- **最终决定**：扁平结构。
- **理由**：用户选择；追番浏览直观。每集下载的中间工作目录放在
  `番剧名/_work/集名/`，成功后成品移出并清理，避免集间续传数据串台。

### 决策 4：配置与代理（用户提出，方案直接确认）

- **背景**：用户要求线程数可改、可设代理、统一配置文件。
- **最终决定**：项目根 config.json（沿用仓库 fetech_xs 惯例），优先级 CLI > config > 默认；
  首次运行自动生成；代理同时作用于 requests 与 Playwright 浏览器。
- **理由**：与仓库现有项目一致；浏览器与下载路径走同一代理才能保证嗅探和下载
  出口一致；进度条与下载间隔默认值（60s）按用户要求。

## 2026-09-24 项目启动技术选型（四项合并记录）

### 决策 1：下载引擎

- **背景**：需求 2 要求流式下载切片并断点续传，需要选择自研还是封装现成工具。
- **备选方案**：① 纯自研 Python；② 封装 yt-dlp / N_m3u8DL-RE；③ 自研为主 + 外部工具接口。
- **最终决定**：纯自研 Python（requests + ThreadPoolExecutor）。
- **理由**：与嗅探/请求头继承衔接最紧密；断点续传、加密、请求头完全可控；
  代码可读可改；无外部 exe 依赖。

### 决策 2：嗅探浏览器形态

- **背景**：需求 1 要求从播放页拿到 m3u8，需决定浏览器自动化形态。
- **备选方案**：① 有头浏览器；② 无头全自动。
- **最终决定**：有头浏览器。
- **理由**：很多站点需要手动点击播放/通过人机验证才触发 m3u8 请求，
  有头模式下用户可直接操作页面，嗅探成功率远高于无头。

### 决策 3：入口范围

- **背景**：嗅探（给播放页 URL）、直链（给 m3u8 URL）、播放器模式三种入口是否第一版全做。
- **备选方案**：① 三种全做；② 先做嗅探 + 播放器兜底，直链后置。
- **最终决定**：三种全做。
- **理由**：直链模式是嗅探失效时的最后兜底（用户可手动 F12 复制），
  实现成本低（复用 parser/downloader），兜底性最好。

### 决策 4：是否集成 yt-dlp

- **背景**：yt-dlp 直接支持数千站点，可作首选尝试。
- **备选方案**：① 第一版集成；② 第二版再集成。
- **最终决定**：第一版不集成。
- **理由**：保持依赖简单、路径清晰；先验证自研链路完整性，
  yt-dlp 作为二期加速通道（设计文档 §9 已预留）。

## 2026-09-24 DRM 能力边界

- **背景**：需求 3 提到"版权限制不能下载"，需明确工具能力边界。
- **备选方案**：① 尝试一切手段包括绕过 DRM；② 明确划分：伪限制（Referer/UA/Cookie 校验）用请求头继承解决，真 DRM（Widevine/FairPlay）明确报错不支持。
- **最终决定**：方案②。
- **理由**：用户确认理解：真 DRM 下解密密钥在浏览器 CDM 黑盒内申领，
  明文不经过网络，技术上无法在合规前提下获取；且绕过涉及法律风险。
  AES-128（HLS 常见弱加密）密钥随清单公开下发，完全可支持。
  播放器模式对真 DRM 无效（网络层抓到的仍是密文），工具会检测并明示。
